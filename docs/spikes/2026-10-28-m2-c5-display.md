## Decisions (2026-10-28)

Taken with you before the build (design §10):
- **LVGL renders the S3 panels**, with a desktop (Mac) build of the same LVGL for previews (your proposal).
- **The display API has primitives and UI layouts:** `clear`, `text`, `fill_rect`, `set_brightness`, and `ui_load` / `ui_set` with labels, buttons, bars, sliders, arcs, switches and rects.
- **The C3 OLED keeps a small built-in renderer:** a 5×7 font, primitives only; `ui_load` answers `UNSUPPORTED`.
- **Basic touch is in C5:** `fr.touch`, id 0x0008 (0x0007 stays free).
- **PSRAM is on for the S3 display profiles** (`s3l-pad`, `s3t-pad`), holding LVGL's pool and the shadow framebuffers.
- **A second S3 board joins:** your Waveshare ESP32-S3-Touch-LCD-2, as pad-s3t.

Taken by the lead on the bench (proposed, with T-DISPLAY's numbers): the latency rule's bracket.

## What was built (brief)

Design §1–§8 list the files. As built:
- **Contract:** `fr.display` 1.0 (0x0003) and `fr.touch` 1.0 (0x0008); message types in capability YAML (`UiLayout`, `UiWidget`, ≤ 24 widgets); explicit `bulk: true` commands (`ui_load`, `snapshot`, `snapshot_read`), which the hub's router sends BULK only, never over a gateway.
- **LVGL 9.6.0, pinned on both sides:** the IDF registry's `lvgl/lvgl ==9.6.0~1` (component hash `7d82410747bb…`) for the boards; the GitHub v9.6.0 archive (SHA256 `b20ee3acc1bb…`) for the Mac. One `lv_conf.h`: RGB565, Montserrat 14/20/28, the label, button, bar, slider, arc, switch and obj widgets, no float or vector, no animations or transitions, the default theme pinned. Every option the board would otherwise take from menuconfig is set explicitly (41 options); `node tools/display/lv-conf-check.mjs` diffs the board's LV_* macros against the Mac's: identical.
- **`LvglBackend`** (`fr_ui`): one `fr_ui` task (priority 4, 8 KB stack, core 0); commands queued from dispatch (16 deep); the shadow and frozen framebuffers in PSRAM; LVGL's pool 64 KB in PSRAM; touch as an atomic latest point plus one queue marker, so a release is never dropped.
- **`MonoBackend`** (C3): a 1-bit framebuffer, the 5×7 font, a dirty-page flush of one page per timer firing.
- **Drivers:** `st7789_spi` (SPI2, DMA, 40 MHz; the backlight on LEDC timer 3 / channel 7; `backlight_active` high or low, added on the bench; `idle_high` pins held high), `ssd1306_i2c` (hwprobe's SSD1306B init), `cst816_i2c` (probes every 5 s for 60 s and on interrupts; selftest detail "absent" while nothing answers); one shared I2C bus per pin pair; one shared GPIO ISR-service installer.
- **Core task stack 16 KB** on display profiles: decoding a `ui_load` takes about 5.3 KB, measured with `-fstack-usage`.
- **Heap telemetry:** HEARTBEAT `free_heap_kb`, the `alive heap=` line and diag `info` `heap` are internal RAM now; `psram_free_kb` separately.
- **Desktop renderer** `tools/display` (`fr_display_render`, built by `node tools/display-build.mjs`). Hub ops `display_render` (a Mac preview; the hub re-encodes the renderer's PNG so it is byte-identical to a snapshot's) and `display_snapshot` (the board's real framebuffer: `snapshot`, then 1 KB `snapshot_read` chunks, CRC-checked, a per-device lock, a 60 s total budget, `out` under FR_HOME). `fr display window` (an SDL2 window, the mouse as the finger). `input_simulate` for touch `{x, y, gesture}`. A dashboard display card (snapshot, a layout preview, click to tap).

## The new board: Waveshare ESP32-S3-Touch-LCD-2

Read by the lead from Waveshare's schematic `ESP32-S3-Touch-LCD-2-SchDoc.pdf`:
- **ESP32-S3R8**, 16 MB flash, 8 MB octal PSRAM (AP 3 V). Confirmed at boot: "Found 8MB PSRAM device", memory test OK.
- **LCD:** ST7789T3, 240×320, on SPI: SCLK 39, MOSI 38, DC 42, CS 45. LCD_RST goes through R16 "NC/0R", so it is not a GPIO in practice.
- **Backlight:** GPIO1 through an SS8050 NPN, high = on; confirmed on the glass.
- **Touch:** CST816D on I2C SDA 48 / SCL 47, INT 46, shared with the QMI8658 IMU (INT1 GPIO3).
- **TF card:** on the LCD's SPI (MISO 40, CS 41); CS 41 is now held high (`idle_high`).
- **Camera** on 2, 4, 6–17, 21; **BAT_ADC** GPIO5 through 200 k / 100 k (×3); BOOT GPIO0; native USB 19/20.
- **The bench unit has no touch controller.** No I2C ACK at 0x15 and 0 interrupts after a finger tap; you then found a sticker covering "Touch": a non-touch unit (MAC `30eda02a26bc`, in the board file's note). The touch path is tested by injected taps, which go through the firmware's `TouchService` and LVGL, and on the Mac with the mouse. The board entry keeps `touch.tp`, since the touch SKU has the CST816D.

## Regressions

- **T-INPUT sim:** passed, 170/170 on all five pads (pad-c3, pad-c3b, pad-c6, pad-s3, pad-s3t), 0 late.
- **T-NN** `--phase running --sim`: passed, 10/10 over ESP-NOW, rtt p50 5.06 ms, p90 6.19 ms.
- **T-FLOOD:** passed: `gw-c6` 1000/1000, pad-c3 999/1000 (the cut-off node), pad-c3b, pad-c6, pad-s3 and pad-s3t 1000/1000; 0 duplicates; 2.65 seeds per broadcast.
- **T-HIL: 2 of 3 runs FAILED on pad-s3's LED rule,** one frame of 70 each: "want lit 0x400840, got lit 0x202020" and "want 0x202020, got 0x100830".
  - **Decoded by the lead:** the LED showed exactly the commanded colour (0x2040C0 at brightness 64 is GRB 0x100830). The board's STATE came 5.5 ms after the LED frame (hub µs 960,030 for the frame, 965,533 for `status.on`), past the 5 ms pairing tolerance, so the frame was paired with the previous state.
  - **Cause:** the `fr_net` hub-link task (priority 11) was created unpinned and could preempt the core task (priority 10, which owns core 1 on the S3) between the LED write and its STATE.
  - **Fix:** `fr_net` pinned to core 0, with Wi-Fi and lwIP, on dual-core targets (`hub_link.cpp`). pad-s3 redeployed (`s3l-pad` `016c729d8c9a`): **T-HIL 4/4 passed**, pad-s3 LED `state_to_change` p99 938 / 457 / 1,164 / 712 µs (2,198 µs before, with the outlier excluded). pad-s3t was redeployed with it. The fixture is unchanged by this: with its radio off it has no hub-link task.

## The review round

**Shape:** one pass, two reviewers (hub and codegen; firmware and LVGL), then two fix agents; the lead fixed the bench items.

- **Hub and codegen: 2 major, 4 minor, all fixed.**
  - Major: the PNG bytes differed between Node's zlib and macOS's libz, so `display_render` and `display_snapshot` could not be compared as files: the hub now re-encodes the renderer's frame with its own encoder. The renderer's staleness list lacked `fr_caps` and `fr_proto`: one shared list now (`RENDERER_SOURCES`).
  - Minor: a snapshot over a gateway-only link froze a frame no read could fetch (`snapshot` is `bulk` now, refused before the freeze); concurrent snapshots of one device (a per-device lock); no total deadline (`total_timeout_s`, 60 s); a timed-out renderer build left the compilers running (the process group is killed).
  - Policy: `out` of the display ops limited to under FR_HOME.
- **Firmware and LVGL: 0 blocker or major, 4 minor, all fixed.** A full queue could drop a touch release and leave LVGL pressed (atomic touch state); the TF card's CS 41 was not held (`idle_high`); menuconfig leaked into LVGL's options despite `LV_KCONFIG_IGNORE` (each set explicitly, and the checker); heap telemetry included the PSRAM (internal figures now).
- **The lead's bench list:** the boot error "GPIO isr service already installed" (one shared installer); the absent touch controller (clean probing and an "absent" selftest); T-GW-LINK's cleanup signal bug (fixed with the gate fixes).

## Findings and open items

1. **Rendering does not move input latency.** On pad-s3, `text` and `set_brightness` at 10 Hz read 4.51 and 4.59 ms against idle 5.73 and 5.03 ms; idle runs alone differ by 0.7 ms, so one idle run cannot carry a 1 ms rule. The bracketed rule is proposed.
2. **The LCD-1.9's backlight is active-low;** the Touch-LCD-2's NPN switch is active-high. `backlight_active` in the board's `displays` entry carries it ([04 §4.3](../spec/04-boards.md)).
3. **An unpinned `fr_net` task could split an LED write from its STATE on the S3** by more than T-HIL's 5 ms pairing tolerance. Pinned to core 0 on dual-core targets; T-HIL 4/4.
4. **Internal RAM headroom on the S3 display profiles is about 27–30 KB** (30,436 B on pad-s3, 26,696 B on pad-s3t), with LVGL's pool and framebuffers in PSRAM and LVGL's pool at about 7 KB of 64 KB. Watch it before adding to those profiles.
5. **The `fr_ui` stack** has 3,676–4,360 B of 8 KB left at its lowest.
6. **Images grew to 74.5–74.8 % of the slot** on the S3 display profiles (63.2 % on the C3).
7. **Proposed, awaiting your approval:** T-DISPLAY's numbers, the bracketed latency rule among them.
