# Checkpoint C2 — local capabilities on the C6 (2026-10-21)

**Covers:** roadmap checkpoint C2 ([11](../spec/11-roadmap.md)) and gate T-CODEC ([05 §5.18](../spec/05-network.md)). Design and contracts: [docs/design/c2-local-capabilities.md](../design/c2-local-capabilities.md).

**Device:** ESP32-C6 Super Mini `58e6c5d55e64`, profiles `c6-pad` (WS2812 on GPIO8) and `c6-pad-mono` (plain LED on GPIO15). The C3 (`c3o-pad`) builds but was not attached; its on-board run is still open.

## Gate T-CODEC

| Check | Result |
|---|---|
| Golden vectors | C++ and TS produce identical bytes for every vector: every class, every system message, every capability member, serial lines in both directions, plus decode-only and error cases (`schema/vectors/`) |
| Fuzz, TS | 10⁶ cases per decoder target, no throw (≈ 2 min) |
| Fuzz, C++ (ASan + UBSan) | 10⁶ cases per decoder target, no failure (≈ 3 min) |
| Cross-language parity | the 57 targets that exist on both sides reach identical fuzz digests at 10⁶ |
| Suites | vitest 378 tests; host C++ 126 tests |

## On the board

| Step | Result |
|---|---|
| Builds (debug, test hooks on) | `c6-pad` 16.9 % of the app slot, `c6-pad-mono` 15.6 %, `c3o-pad` 15.1 %; no compiler warnings |
| Boot | the banner keeps the C1 format and appends `caps=2 epoch=N`; the epoch increments on every boot (persisted in `nvs:fr_boot`) |
| Frames | the hub decodes every `@fr1:` line into readable log lines (`@fr1 EVENT boot.click {"count":1} (src=fffe seq=… epoch=… port=1)`) |
| `diag info`, `caps`, `selftest`, `stats`, `mark`, `log`, `reboot` | answer as specified; `selftest` reads the WS2812 data line and drives/reads back the GPIO15 LED |
| `call status.blink {count, on_ms, off_ms, color}` | RESULT ok, then `effect_done` exactly `count × (on+off)` later (0.9 s and 4.0 s measured) |
| `call status.set` / `toggle` | STATE `on`/`color` frames; the steady blue `set` was confirmed by eye |
| `inject boot click / double_click / long_press` | `down, up, click{1}`; two press pairs then `click{2}`; `down, long_press{640}, up{640}`, no click |
| Real BOOT presses (3) | `down`, `up{held_ms 288/349/516}`, `click{1}` each; 7 interrupts for 3 presses (contact bounce), all absorbed by the debounce |
| Errors | out-of-range args, unknown keys, unknown instance or command, malformed JSON and strings holding U+0000 all answer `ok:false` with a code; `fr diag` exits 1 |
| `c6-pad-mono` | the same firmware drives the GPIO15 LED (`traits: mono`) with no code change |
| `reboot` (`esp_restart`) | `rst:0xc (SW_CPU)`; the USB port stays enumerated and the whole boot log is captured |

## Findings

1. **Flash picked a release build.** `fr flash --profile` chose the newest artifact of any build type; it now picks the newest debug artifact, as 06 §6.4 says.
2. **The hub used its own copy of the generator.** `fr build` now runs `fr gen firmware` from the build's `source_dir`, so a codegen edit (or another checkout) is never built with a stale generator.
3. **System ports were unnamed.** Frames on port 241 (`diag.mark`) now decode by name.
4. **Event time.** `EVENT`/`STATE` `t_us` is now the edge time from the ISR, not the time the core task sent the frame (needed by T-LAT).
5. **`diag log <tag> D` did nothing.** The compiled-in maximum log level equalled the default; debug builds now allow DEBUG at runtime.
6. **Silent board after the Mac slept.** At 02:35 UTC, during the night, the C6 stopped producing output (no heartbeat, no diag answers) while the hub still showed the port open, and one boot (epoch 6) happened without any captured output. The power log shows a maintenance wake from sleep at 02:38. A hub-side reset recovered it. The cause is not reproduced; the open sequence was ruled out (serialport sets DTR and RTS with one `TIOCMSET`). Mitigation: the hub now treats a poll tick more than 10 s late as a system resume and reopens every open port. C3's 1 s HEARTBEAT will make silence detectable within seconds.
7. **One BOOT press left no trace.** The first real press (before the interrupt counter existed) produced no events, while three later presses worked. Not reproduced; the button driver's `selftest` now reports interrupts since boot, so the next miss can be told apart from a lost delivery.

## Not covered

- `c3o-pad` on the C3 board (not attached).
- The hub sending ENV CMD frames over serial (node side is implemented and covered by golden vectors; the hub side is C3).
- `fr.node.describe` (needs the descriptor type; C3) and diag answers above ~195 B over a link (`Reply` capacity; C3).
