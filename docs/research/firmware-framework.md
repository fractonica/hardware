# firmware-framework

## SUMMARY
The recommended foundation is native ESP-IDF v6.1 using idf.py and the classic CMake build system (v1). Code is C++ built with GCC 15.2 at the IDF default -std=gnu++26, with exceptions and RTTI left off. As of 2026-10-20, v6.1 (released 2026-08-27) is the latest stable ESP-IDF; v6.1.1 does not exist yet. v6.0.3 and v5.5.6 are the latest patch releases of the older lines. Under Espressif's support policy (12 months service, then 18 months maintenance), v5.5 (released 2025-07-21) has moved into maintenance and is no longer recommended for new projects. v6.1 stays in service until about 2027-08 and is supported until about 2029-02. Because the project starts from scratch, none of v6's breaking removals cost anything: legacy drivers, legacy mbedTLS calls, Newlib (replaced by picolibc), and warnings now becoming errors. Moving to v6 also brings three features we use directly: CMakePresets multi-config builds (idf.py --preset), a built-in MCP server (idf.py mcp-server), and the newer toolchain. The ecosystem has settled on v6.1: PlatformIO's official platform 8.0.0 (released 2026-10-19) targets IDF 6.1, Arduino-ESP32 4.0.0-RC1 is built on IDF 6.1, LovyanGFX has supported IDF 6.x since 1.2.27, and the espressif/esp-now component fixed its IDF 6 compile issue in 2.5.3. Arduino (standalone or via PlatformIO), Rust (esp-hal 1.2 is stable, but esp-radio and its ESP-NOW driver are still 1.0.0-beta.1), and Zephyr (ESP-NOW exists only as a board sample) are rejected as the foundation. Arduino stays available only as an opt-in backend inside an individual driver component. The firmware lives in a monorepo with hardware-agnostic framework components, a driver library (one IDF component per hardware implementation, each with a driver.json manifest), and board manifests (board.json, the single source of truth for target, flash, console and capability-to-driver bindings, compiled into board glue code at configure time). Apps are thin IDF projects. Builds form an app × board × profile matrix, and every build goes through one CMake helper, so CMakePresets (for humans and IDEs) and the pcfw agent CLI produce identical results. An agent drives builds through pcfw: a sanitized environment, a pinned IDF tag and commit (or a Docker image pinned by digest), per-target dependency lock files, reproducible-build mode, JSON results with exit codes, and an artifact manifest.json that the hub uses to flash or OTA-update a device.

## RECOMMENDATION
Primary stack: ESP-IDF v6.1, pinned to the tag plus its commit SHA, with toolchain esp-15.2.0_20251204 (GCC 15.2.0). CI uses the Docker image espressif/idf:v6.1@sha256:81893c71bb5e570088901f21def8684c25cd2a9020281bd01b843a7655edb18c. Builds use the classic build system v1, not the v2 preview. Code is C++ at the IDF default gnu++26; framework code is limited to C++23 features, with -fno-exceptions and -fno-rtti (the IDF defaults).

Pinning and upgrades:
- Bump only to v6.1.x patch tags, through a PR that runs the full build matrix plus a hardware smoke test.
- If v6.1 has a blocking bug, fall back to v6.0.3.
- Evaluate v6.2 when it ships.
- Never track a release branch.

Dependency locking: registry components are pinned with ~x.y.z, and each app commits one lock file per target via `idf_build_set_property(DEPENDENCIES_LOCK dependencies.lock.${IDF_TARGET})`.

Flash and boot layout (frozen from day one):
- Partition table offset 0x10000.
- Two OTA slots, with bootloader app rollback enabled.
- A dedicated `pc_ident` NVS partition for identity and alias, written by the hub with parttool.

Repo layout: `firmware/{cmake, config, partitions, components (pc_*), drivers (drv_*), boards (<id>/board.json), apps (<app>/), tools/pcfw, test}`.

Build matrix and agent interface:
- The matrix is app × board × profile. Valid pairs are where the board's capabilities cover what the app requires.
- Builds of different apps run in parallel; builds of the same app run one at a time.
- Agents build only through `uv run pcfw build --app A --board B --profile P --json`, which wraps `idf.py -C/-B/-D` in a clean environment and emits a JSON result plus an artifact `manifest.json`.
- Generated per-app CMakePresets.json files give humans and IDEs the same builds via `idf.py --preset <board>-<profile>`.

Arduino libraries are allowed only through the espressif/arduino-esp32 component, inside a dedicated `drv_*_arduino` driver component, once Arduino 4.0 is stable.

## RATIONALE
1. **Support lifecycle.** ESP-IDF supports each minor release for 30 months: 12 months of service, then 18 months of maintenance. Only in-service releases are recommended for new projects.
   - v5.5 shipped on 2025-07-21 and is now in maintenance.
   - v6.1 shipped on 2026-08-27 and is in service until about 2027-08.
   - Starting on 5.5 would mean an immediate v6 migration later (drivers, mbedTLS 4/PSA, picolibc, Kconfig v3, GCC 15 warnings). Starting fresh on v6.1 costs nothing.
   - Choosing v6.1 over v6.0.3 avoids v6.1's own breaking changes later: LCD FourCC color formats, MQTT moved to the registry, GPIO macro renames.

2. **The project's hard criteria are first-class in ESP-IDF.**
   - **One codebase for C3, C6 and S3:** IDF_TARGET selects the chip, and per-target sdkconfig defaults are supported.
   - **ESP-NOW and Wi-Fi station on one radio:** shared channel. The off-channel APIs `esp_now_switch_channel_tx` and `esp_now_remain_on_channel` are present in v6.1 and v5.5.6, but not in the local v5.5.1.
   - **OTA with rollback:** `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` plus `esp_ota_mark_app_valid_cancel_rollback()`.
   - **Modular, versioned driver library:** components, Kconfig, the component manager with path, git and registry dependencies, conditional rules, and lock files.
   - **Headless, reproducible builds:** `idf.py`, `APP_REPRODUCIBLE_BUILD`, a multi-arch Docker image with ccache enabled, `flasher_args.json`, `size --format json2`, and `merge-bin`.
   - **Multi-board builds from one tree:** `SDKCONFIG_DEFAULTS` lists, `-B`, `-DSDKCONFIG`, `MINIMAL_BUILD`, and v6 presets.

3. **Agent-first.** v6 ships an MCP server, but it is thin: build, set-target, flash, create and clean, with no monitor and no awareness of presets or boards. We use it only as a baseline. Our own deterministic CLI (pcfw) is the contract that agents and the hub call.

4. **Ecosystem convergence on v6.1.**
   - PlatformIO official 8.0.0 targets IDF 6.1.
   - Arduino 4.0.0-RC1 is built on IDF 6.1. The Arduino 3.3.12 component manifest also allows IDF up to (but not including) 6.2.
   - LovyanGFX 1.2.27+ supports IDF 6.
   - espressif/esp-now 2.5.3 fixed its IDF 6 compile issue.

5. **Why the alternatives fail at least one hard criterion.**
   - **Arduino standalone:** precompiled IDF libraries mean a fixed sdkconfig and no per-board Kconfig. Rollback, partition and coexistence tuning are not first-class, and there is no component versioning.
   - **PlatformIO:** adds an extra layer that historically lagged badly (the official platform stayed on Arduino 2.0.17 until 2026-10-19).
   - **Rust:** esp-radio and ESP-NOW are still beta, and S3 (Xtensa) needs the espup compiler fork.
   - **Zephyr:** ESP-NOW is only a sample and OTA goes through MCUboot, so it is not aligned with the ESP-NOW-first design.

6. **Board manifests compiled into glue code** give a single source of truth that agents, the hub and the build all read. This enforces the rule that "high-level logic never touches hardware": apps depend only on `pc_caps` interfaces, and only the generated `pc_board` component knows which driver backs each capability.

## ALTERNATIVES
- **ESP-IDF v6.1 native (idf.py, build system v1), C++ gnu++26/C++23 subset** — verdict: RECOMMENDED primary stack.
- **ESP-IDF v5.5.6 (stay on 5.5.x)** — verdict: Fallback only, if a hard v6 incompatibility is found in a must-have dependency.
- **ESP-IDF v6.0.3** — verdict: Emergency fallback if v6.1 has a blocking bug.
- **Arduino-ESP32 3.3.x standalone (arduino-cli / Arduino IDE)** — verdict: Rejected as foundation.
- **Arduino as an ESP-IDF component (espressif/arduino-esp32)** — verdict: Allowed only as an opt-in backend inside a dedicated drv_*_arduino driver component, never in framework core. The framework sets FREERTOS_HZ=1000 globally so this stays possible.
- **PlatformIO (official platform-espressif32 8.0.0 or pioarduino 55.03.312 / 61.04.00-RC1)** — verdict: Rejected as primary. Users may still use it for throwaway sketches outside the framework.
- **Rust no_std (esp-hal 1.2 + esp-radio + esp-rtos/embassy)** — verdict: Rejected for now. Revisit for node firmware once esp-radio reaches 1.0.
- **Rust std (esp-idf-svc / esp-idf-hal / esp-idf-sys)** — verdict: Rejected.
- **Zephyr RTOS** — verdict: Rejected: the design is ESP-NOW-first and OTA-first.
- **ESP-IDF build system v2 (cmakev2)** — verdict: Do not use. Keep components v2-friendly (no early-eval tricks) so a later migration is cheap.

## RISKS
- v6.1 is a .0 minor release (no 6.1.1 yet), so we are exposed to early regressions in Wi-Fi, ESP-NOW or coexistence on C6/C3/S3. → Pin the tag and commit in idf-version.lock. Gate every IDF bump with the full build matrix plus a hardware smoke test (ESP-NOW broadcast and unicast, Wi-Fi STA, OTA with rollback) on all three boards. Keep v6.0.3 as the documented fallback, and run a nightly non-blocking canary build against the espressif/idf:release-v6.1 Docker tag.
- Third-party components (registry or Arduino) may not yet compile under v6: warnings are now errors, picolibc differs, legacy drivers are removed, and mbedTLS 4 is in place. → Wrap every third-party dependency in a drv_* component and relax warnings only for that component with target_compile_options(... PRIVATE -Wno-error=...). Vendor patched copies with override_path under firmware/third_party/. CONFIG_LIBC_NEWLIB remains a last-resort global switch. Do not add Arduino until 4.0 is stable.
- Bootloader and partition table cannot be safely changed in the field (bootloader OTA has no fallback on C3/C6/S3), so a bad initial layout is permanent. → Freeze layout v1 now with headroom: table offset 0x10000 (allows a bootloader up to 64KB, enough for future secure boot), 192KB pc_store, a 24KB pc_ident partition, and per-flash-size CSVs. Version the layout in a CSV header comment and fail CI if a frozen CSV changes. Use IDF bootloader images only from the pinned IDF, and test app OTA against the bootloader actually deployed.
- ESP-NOW and Wi-Fi STA share one radio channel, so if the AP changes channel, ESP-NOW peers become unreachable until they follow. → This belongs to the networking spec, but the firmware foundation must provide two things. First, the AP channel is a hub-level configuration value (fixed channel recommended). Second, use IDF ≥ 6.0 / 5.5.6 APIs (esp_now_switch_channel_tx and esp_now_remain_on_channel) for off-channel discovery or recovery. Document WIFI_PS_NONE for low-latency nodes.
- Serial port contention: Chrome's Web Serial currently holds /dev/cu.usbmodem1101, and the hub, agents and idf.py monitor could all compete for ports. → pcfw never opens a port the hub reports as leased. Port ownership belongs to the hub's device broker, and pcfw flash is a dev-only command that asks the hub for a lease first. Flashing from inside Docker on macOS goes via RFC2217 exposed by the hub.
- Host environment contamination makes builds non-deterministic: radioconda's python3, ninja and esptool 5.1 come first on PATH, host CMake is 4.1.1, and multiple IDF installs exist. → pcfw runs idf.py in a sanitized subprocess (bash --noprofile --norc, minimal PATH, explicit IDF_PATH/IDF_TOOLS_PATH, activation via export.sh or the EIM activate script). pcfw doctor checks that `idf.py --version` and `git -C $IDF_PATH rev-parse HEAD` match idf-version.lock and refuses to build on a mismatch.
- Parallel builds of the same app for different targets race on the shared apps/<app>/managed_components directory. → pcfw takes a per-app file lock, so builds of different apps run in parallel and builds of the same app run one at a time. CI uses one job per app, or separate checkouts.
- Board codegen (board.json + driver.json generating C++ glue at configure time) adds machinery that could become a source of bugs. → The generator uses only the Python standard library (json, no PyYAML), runs on the IDF venv Python that idf.py passes in as -DPYTHON, and is covered by golden-file tests in CI. Generated files go to the build dir and are never committed. JSON Schemas for board.json and driver.json are validated by pcfw before any build.
- C3 boards with chip revision below v0.3 will not boot images built with the default minimum revision (ESP32C3_REV_MIN_3 in both 5.5 and 6.1). → The hub records chip revision (esptool chip-id) at first flash. board.json can override min_chip_rev, and pcfw warns on a mismatch.
- Docker builds on macOS are slower because of bind-mount I/O, which hurts the agent's edit-build loop. → Use native builds (pinned IDF at ~/esp/v6.1/esp-idf plus ccache) for the local dev and agent loop. Docker, pinned by digest, is the reference for CI and reproducibility checks. Measure both in the PoC and record the results with pcfw doctor --bench.

## OPEN QUESTIONS
- Which exact ESP32-S3 board is it? Options include ESP32-S3-DevKitC-1 v1.0 (LED on GPIO48) or v1.1 (LED on GPIO38), its module variant (e.g. N8R2, N8R8, N16R8), an S3 Super Mini/Zero, or something else. This sets the flash size, PSRAM mode (octal reserves GPIO35-37), LED pin, and which USB port carries the console.
- Is the C3 a plain Super Mini (blue LED on GPIO8, active-low) or a 'Super Mini Plus' (WS2812 on GPIO8)?
- May I install ESP-IDF v6.1 side by side at ~/esp/v6.1/esp-idf (git clone plus install.sh for esp32c3, esp32c6 and esp32s3, plus ccache), or would you prefer the EIM installer (brew install eim; eim install -i v6.1)? Should v5.5.1 and v5.3.2 stay installed?
- How important are Arduino libraries to you, and which ones? The answer decides whether we plan an arduino-as-component backend (waiting for Arduino 4.0 stable on IDF 6.1) or stay pure ESP-IDF plus registry components and LovyanGFX.
- Is the hub only a computer service (Node/web dashboard), or should there also be an ESP32 'hub bridge' firmware app (e.g. an S3 acting as a USB/Wi-Fi to ESP-NOW gateway)? A bridge adds an app to the matrix and affects the latency design.
- Can the Wi-Fi access point the nodes join be locked to a fixed channel? ESP-NOW and the STA connection must share that channel.
- What OTA security level do you want during prototyping: plain HTTP on the LAN with SHA-256 verification against the hub manifest, HTTPS with a pinned hub certificate, or signed images (secure boot v2) from the start?
- Is there any interest in Rust node firmware later? If so, we keep the wire protocol and the board.json/driver.json schemas language-neutral, which is recommended anyway.

## VERIFY: holds=True
### Challenge
The strongest case against the recommendation has three parts. (1) It picks v6.1, eight weeks old, over v6.0.3 for reasons that do not hold. The 'v6.1 breaking changes' it cites (MQTT, FourCC, GPIO macros) also appear in the v6.0 release notes, and the official 6.0→6.1 migration guide lists only three small items. So 6.0.3 vs 6.1 is close to a coin flip, and the real argument for 6.1 is the extra ~5 months of service. (2) The surrounding tooling is very large for a prototyping framework: board.json/driver.json codegen at CMake configure time, the pc_configure macro, a pcfw CLI with about 12 subcommands, generated and committed CMakePresets, per-target lock files, per-app file locks, three CI tiers and a Docker mode. Several of its premises fail under verification: MINIMAL_BUILD does not keep unused drivers out of dependency resolution, layered sdkconfig defaults do not re-apply to an existing sdkconfig, and committed presets are auto-selected by idf.py. Its 'single deterministic path' therefore has real holes. (3) If the user values Arduino peripheral libraries, stable Arduino (3.3.12) is still on IDF 5.5, so v6 delays that ecosystem until 4.0 is final. None of these makes a different foundation materially better. Native ESP-IDF is the only option that meets every hard criterion: one tree for C3, C6 and S3, first-class ESP-NOW alongside Wi-Fi STA, OTA with rollback, Kconfig, the component manager, and headless reproducible builds. Within v6.x, 6.1 is the reasonable pin, since moving between 6.0 and 6.1 is cheap either way. A simpler variant is worth considering. For the PoC, implement only `pcfw build/flash/doctor` and boardgen, and have pc_configure add only the driver components a board binds to EXTRA_COMPONENT_DIRS (boardgen already knows them). pcfw should always invoke `idf.py --preset`, or presets should not be committed in the app directory. Board choice could alternatively be a Kconfig choice plus per-board defaults fragments, which menuconfig, the VS Code extension and idf-build-apps understand natively. Keep board.json as the agent/hub-facing source and generate those fragments from it. Defer Docker mode, the CI tiers and presets sync until there is more than one app.

### Missed
- sdkconfig staleness: sdkconfig.defaults layers apply only to a new sdkconfig or to keys not yet set (build-system.rst:1087; reproducible-builds.rst says to delete sdkconfig after changing defaults). An incremental `pcfw build` after editing board.json, a profile or sdkconfig.framework silently keeps the old flash size, partition table, PSRAM and console settings. pcfw needs to hash every layer input plus the generated sdkconfig.board, store the hash in the build dir, and delete <build>/sdkconfig when it changes. v6.1 also offers `idf.py refresh-config --policy` for Kconfig default changes.
- The component manager resolves and downloads the dependencies of every component on the component path, regardless of MINIMAL_BUILD. Putting all of drivers/ in EXTRA_COMPONENT_DIRS means every app downloads LovyanGFX, arduino-esp32 and its many dependencies once those drivers exist, records them in its lock file, and fails on version conflicts between unrelated drivers. The fix is to add only the bound drv_* directories, or to give the generated pc_board an idf_component.yml with `path:` dependencies.
- A committed CMakePresets.json in apps/<app> makes v6.1 idf.py auto-select the 'default' or first preset whenever --preset is omitted, and pass it to CMake. pcfw must pass --preset explicitly every time and scrub IDF_PRESET from its environment, or the presets must not live in the project directory.
- v6.1 changed `idf.py flash` to fast reflash by default, using *_flashed.bin state in the build directory. A hub flashing many devices from one build dir should use `idf.py flash -a`, or esptool driven by the manifest, to avoid odd state across devices.
- Build-tool pinning: IDF documents that reproducibility depends on the CMake and Ninja versions. The v6.1 tools.json marks cmake and ninja as on_request, and the local PATH puts Homebrew cmake 4.1.1 and radioconda ninja first. Docker uses idf_tools cmake and Ubuntu ninja-build. Native and Docker ELF SHAs can therefore differ, so `pcfw doctor` must install and pin cmake and ninja via idf_tools.py and check their versions.
- USB HID vs. the serial control channel: on S3, TinyUSB (USB OTG) and USB-Serial/JTAG share one PHY, so turning an S3 node into a USB HID/gamepad input device removes the native-USB serial agent channel. C3 and C6 have only USB-Serial/JTAG and cannot act as USB HID devices at all. This matters for the 'custom input devices' goal.
- Native USB-Serial/JTAG drops off the bus during deep sleep, and in light sleep unless configured otherwise. Agent serial control and monitoring of sleeping nodes therefore needs a Wi-Fi/ESP-NOW path, and C6 GPIO12/13 and C3 GPIO18/19 must stay reserved.
- Identity provisioning via parttool requires download mode, a port lease and the non-default `--partition-table-offset`. Runtime provisioning through pc_ctl (serial, Wi-Fi or ESP-NOW) writing the pc_ident NVS partition is simpler, works over the air, and is easier for agents. An NVS schema/namespace version is also needed for pc_ident.
- Offline and reproducible dependency fetching: configure a component registry mirror (`local_storage_url` / IDF_COMPONENT_LOCAL_STORAGE_URL), and have pcfw's sanitized environment scrub or pin the IDF_COMPONENT_* variables.
- A frozen bootloader plus IDF bumps means newer apps run on an older bootloader. The matrix should include an 'OTA from the oldest deployed bootloader/app' test, and watch IDF's app/bootloader compatibility notes.
- The C6 Super Mini has a second plain LED on GPIO15, a strapping pin. Clone boards vary in flash size and LED wiring, so the hub should verify flash size and chip revision with esptool at first flash rather than trusting board.json.
- FREERTOS_HZ=1000 for 'input latency granularity' is weak reasoning. A GPIO ISR plus a task notification is not bound to the tick. A 1000 Hz tick costs CPU and power on battery nodes; keep it only if the Arduino component is actually planned.
- pc_store uses the littlefs partition subtype, which is valid (0x83), but needs the joltwallet/littlefs registry component; the spec does not list it.
- C++ policy drift: the IDF compiles with -std=gnu++26 while the framework is limited to C++23. Add a CI job that compiles pc_* with -std=gnu++23 (or a clang-tidy check), or the limit will not hold.
### Spec errors
- §4.7 partition CSVs: trailing inline comments on data rows (`0x6000 # identity/...`, `0x1D0000 # 1856K`, `0x30000 # 192K assets`) are not supported. gen_esp32part.py strips only lines that start with '#', and running IDF v5.5.1's tool on the CSV fails with 'Error at line 6: Invalid field value 0x6000 # identity/alias/...'. Comments must go on their own lines. With the comments removed, the 4MB, 8MB and 16MB layouts all validate at --offset 0x10000.
- §4.7 identity provisioning command: `parttool.py --port <p> write_partition --partition-name pc_ident --input ident.bin` is missing `--partition-table-offset 0x10000`. parttool defaults to PARTITION_TABLE_OFFSET = 0x8000 in both v5.5.1 and v6.1, so it would read the wrong location.
- §4.3 rule 'MINIMAL_BUILD ON ensures only what main requires is compiled, so the whole drivers/ directory can sit on the component path': compile scope is correct, but the component manager still processes every driver's idf_component.yml (BUILD_COMPONENT_TARGETS is passed before trimming), downloading and locking all of their dependencies for every app.
- §4.5 and §4.9 'Both paths go through pc_configure, so their outputs are identical': with a committed apps/<app>/CMakePresets.json, plain `idf.py -C ... -B ... -D... build` (pcfw's documented command) auto-applies the first or 'default' preset. pcfw must pass `--preset <board>-<profile>` explicitly.
- §4.6 'app layers cannot override flash size, PSRAM or partitions' and the §4.9 determinism list: this is true only for a fresh sdkconfig. Defaults files are not re-applied to keys already in an existing sdkconfig, so pcfw must invalidate <build>/sdkconfig whenever any layer input changes, not only on --clean.
- §4.11: 'Off-channel APIs esp_now_switch_channel_tx and esp_now_remain_on_channel are available in IDF ≥ 6.0' should be 'IDF ≥ 5.5.2 (and all v6.x)'. They are present in v5.5.2 through v5.5.6 and absent in v5.4.4 and v5.5.1.
- §4.1 'The ecosystem has converged on 6.1: PlatformIO official 8.0.0': IDF 6.1 support shipped in platform-espressif32 7.1.0 (2026-08-31), and 8.0.0 only adds Arduino 3.3.12, which is on IDF 5.5.5. Stable Arduino has not converged on 6.1; only 4.0.0-RC1 has.
- Rationale (summary, not §4.1): 'Choosing v6.1 over v6.0.3 avoids v6.1's own breaking changes later (LCD FourCC, MQTT, GPIO macros)' is wrong. Those changes are also in the v6.0 release notes, and the official 6.0→6.1 migration guide lists only the LCD DPI callback deprecation, the UART wakeup API, and idf.py fast reflash.
- Report key fact (not in the spec text): 'esp-radio is still 1.0.0-beta.1 (2026-09-22)'. crates.io shows 1.0.0-beta.2 (2026-09-17), and esp-hal's latest is 1.2.2 (2026-09-18), not 1.2.0.
- §4.4 C6 board.json: reserved_gpio [8,9,12,13] omits GPIO15, a C6 strapping pin that also drives the plain status LED on common C6 Super Mini boards. The C6 strapping set is 4, 5, 8, 9 and 15.
- §4.4 S3 board description has no `console` field. The DevKitC-1 has both a UART-bridge port (UART0) and a native USB port (GPIO19/20), and the choice decides whether serial control works (the secondary console is output-only). The N16R8 id is still unconfirmed.
- §4.9 Docker/native equivalence: the claim that the hub can compare ELF SHA-256 across builds ignores IDF's statement that CMake and Ninja versions affect output. Native builds (Homebrew cmake 4.1.1, radioconda ninja) and the Docker image (idf_tools cmake, Ubuntu ninja-build) are not pinned to the same versions.
- §4.9 flashing: the spec does not address v6.1's new fast-reflash default for `idf.py flash`. Pass `-a/--all`, or flash the manifest files with esptool, so multi-device flashing from one build dir is predictable.
- §4.6: `CONFIG_ESP_TASK_WDT_EN=y` is redundant because it is already the default (v6.1 esp_system/Kconfig:297-300). This is harmless. The FREERTOS_HZ=1000 justification ('input latency granularity') is technically weak.
