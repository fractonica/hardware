# hub-host

## SUMMARY
Recommendation: build the hub as one TypeScript process on Node 24 LTS, using Fastify 5 with ws for HTTP and WebSockets, serialport 13 for serial ports, better-sqlite3 13 for storage and bonjour-service for mDNS. Flashing goes through a small Python sidecar ("pytools") that uses esptool's public Python API (esptool 5.6.0, pinned and managed by uv). Firmware builds use native ESP-IDF on the Mac; the espressif/idf Docker image is supported only for builds. Bun is out: serialport's native binding calls libuv's uv_default_loop, and as of 12 Oct 2026 Bun 1.4.2 still panics on it (oven-sh/bun#18546). Docker Desktop on macOS cannot pass serial ports through. Espressif's RFC2217 workaround explicitly does not support the native USB-Serial/JTAG boards the user owns (C3, C6, S3 Super Minis). So the hub must run natively and own every serial port itself. The flashing sidecar is preferred over parsing CLI output because esptool v5 changed its message wording and moved errors to stderr, and its own docs recommend the API. The API's logger is a single global, so each flash job runs in its own process anyway. All shared types live in one Zod 4 protocol package that feeds the dashboard, the JS SDK, MCP tool schemas and OpenAPI, plus a small binary-frame table that generates both TS codecs and a C header for firmware. Node 24 can run the hub's .ts sources directly through pnpm's symlinked workspaces (checked locally on 24.11.1), so the hub needs no build step in development. There are two macOS findings that change the design. First, Local Network Privacy (TN3179) blocks a hub launched from VS Code, the Claude desktop app or a launchd agent (e.g. brew services) from sending UDP, mDNS or outgoing TCP until the user approves it; accepting incoming TCP and receiving UDP unicast are not gated, so nodes should open the connections to the hub. Second, Wi-Fi modem sleep is on by default and adds up to a DTIM interval (about 100 ms) of latency, so low-latency nodes must call esp_wifi_set_ps(WIFI_PS_NONE). Estimated button-to-browser latency: about 4–5 ms median through a USB ESP-NOW gateway, about 4–8 ms over direct Wi-Fi with power save off, and over 100 ms with the default power save.

## RECOMMENDATION
Runtime and stack:
- Node 24 LTS 'Krypton' (24.22.0 is current; Node 26 also works) running TypeScript directly with type stripping, `erasableSyntaxOnly` enabled.
- Fastify 5.12 with @fastify/websocket 11 (built on ws 8.22) for REST and WebSockets on one port, @fastify/static for the dashboard and for OTA files (needs Range support), and fastify-type-provider-zod 7 with @fastify/swagger for OpenAPI generated from Zod.
- serialport 13.0.0 (N-API prebuilds include darwin-universal and linux-arm64), kept behind a SerialTransport interface.
- better-sqlite3 13.0.3 (prebuilds bundled, no install script), in WAL mode.
- bonjour-service 1.4.4 behind a pluggable Advertiser, which can switch to dns-sd or avahi.
- pytools: a Python sidecar (uv venv, esptool==5.6.0, esp-idf-nvs-partition-gen, esp-idf-panic-decoder) speaking JSON-lines, one process per job.
- BuildRunner with three modes: native IDF (environment from export.sh, captured once and cached), EIM (`eim run`), or Docker (espressif/idf:vX.Y).
- Dashboard: React 19 + Vite 8 + TanStack Router/Query/Virtual + Zustand + Tailwind 4 + xterm.js 6 (WebGL) for logs, served by the hub on the same origin.
- MCP: @modelcontextprotocol/server 2.x, over stdio (`propriocept mcp`) and Streamable HTTP at /mcp.
- Repo tooling: pnpm 11 workspaces with catalogs and `allowBuilds` for @serialport/bindings-cpp, tsdown for publishable libraries, TypeScript 7 for typechecking, Vitest 5, Biome 2.

Process model: one hub process whose main thread owns every serial file descriptor, the UDP and TCP sockets, the HTTP/WS server, SQLite and the in-memory event bus. Builds, flashing, NVS generation and panic decoding run as child processes managed by a job runner with resource locks (per port, per device, per build directory, and a CPU semaphore). External tools get a port only through an explicit lease API. The event bus is a custom MQTT-style topic trie (`device/<id>/event/<cap>/<evt>` and so on). Every event gets a hub-wide sequence number and a hub timestamp in µs. There are three delivery classes: 'event' (never dropped), 'state' (last value cached) and 'stream' (logs, which may be dropped or coalesced). Each client has a bounded queue with backpressure, a bounded window can be replayed on reconnect, and each message is serialized once and sent to every subscriber. Monorepo packages: protocol, hub-server, dashboard, sdk, mcp, cli, pytools, plus firmware/ (ESP-IDF components, board profiles, node and gateway apps, generated C header). Make the USB ESP-NOW gateway the default low-latency link, keep Wi-Fi direct (node-initiated TCP/WS for control, UDP for inputs) as the second link, and deduplicate on (origin, msgId). Distribution: run from a repo clone now, then `npx propriocept` (Node >= 24, no compiler needed), then a Homebrew tap. A Node single-executable build is deferred because that feature is still 'Active development' and native addons must be unpacked to a temp file before loading.

## RATIONALE
1) Language fit. The dashboard, the generated game SDK and the MCP server are all TypeScript, so a TS hub has one source of truth for protocol types (Zod 4, with JSON Schema, OpenAPI and MCP schemas generated from it) and no cross-language codegen except the firmware C header. Agents (Claude Code, MCP clients) work most fluently in TS and React. MCP TS SDK v2 (released 2026-07-27) accepts Zod 4 schemas through Standard Schema.

2) Node, not Bun or Deno. serialport's binding calls uv_poll_init(uv_default_loop()) (bindings-cpp src/poller.cpp). Bun does not implement libuv, and the tracking issue is still open, with a serialport panic reported on Bun 1.4.2 on 12 Oct 2026. Node 24 is LTS, type stripping is stable from 24.12, and http noDelay defaults to true (since v18).

3) Native hub. Espressif's IDF Docker docs say serial passthrough is not possible on Docker for Mac. esptool's remote-port docs say USB-OTG and USB-Serial/JTAG are not supported over rfc2217:// or socket://. All three of the user's boards use USB-Serial/JTAG, so flashing must happen on the host. Builds can still run in the multi-arch espressif/idf image.

4) Flashing through the esptool API in a sidecar. Espressif recommends the API over log parsing, because v5 rewords messages and sends errors to stderr. The API offers connect_esp, run_stub, attach_flash, write_flash and reset_chip, plus a TemplateLogger whose progress_bar hook can be turned into JSON progress events. The logger is global (`log.set_logger`), so concurrent jobs need separate processes no matter which language the hub uses. ESP-IDF 5.5 pins esptool ~=4.11, so the hub carries its own pinned esptool v5 rather than relying on IDF's. It flashes from build/flasher_args.json, which every IDF version produces.

5) Identification without disturbing the device. USB-Serial/JTAG boards report VID 0x303A, PID 0x1001 and a USB serial number equal to the MAC (ioreg on this Mac shows "1C:DB:D4:16:BA:34"). serialport.list() on macOS returns that serialNumber plus locationId from IOKit, so the hub can key devices by MAC without opening the port.

6) Latency. Measured ESP-NOW one-way latency is about 2.4 ms (RTT/2) against about 105–113 ms for UDP over Wi-Fi in a 2026 study. The power-save setting was not reported, but the result matches IDF's statement that modem sleep (default WIFI_PS_MIN_MODEM) delays receive by up to the DTIM period. A USB gateway gives deterministic latency with no access point involved.

7) macOS Local Network Privacy shapes the link design: node-initiated connections work whatever app launched the hub.

8) Every native dependency ships N-API prebuilds for darwin-arm64 and linux-arm64, so `npx` and Raspberry Pi installs need no compiler.

## RISKS
- serialport may stagnate (no release since Dec 2024); a future Node or macOS change could break it. → N-API is ABI-stable across Node majors. Keep all serial I/O behind a `SerialTransport` interface with a mock implementation (@serialport/binding-mock) and a documented fallback (a pytools 'serial-bridge' subcommand using pyserial, or a small Rust helper using serialport-rs) speaking the same JSON/binary pipe. Pin versions; run nightly hardware-in-the-loop tests.
- macOS Local Network Privacy silently blocks hub-to-node UDP sends and mDNS when the hub is started from VS Code, the Claude desktop app or a launchd agent (brew services). → Make the design work without that permission: nodes initiate TCP/WS to the hub (accepting is not gated), inputs arrive as UDP unicast to the hub (receiving is not gated), and the USB gateway path needs no LAN at all. `propriocept doctor` detects the launching app and tests a UDP connect. Document granting access in System Settings and setting AssociatedBundleIdentifiers for a LaunchAgent. Recommend starting the hub from Terminal.app during development.
- USB-Serial/JTAG ports vanish on reset, deep sleep or USB pin misuse, so logs are lost and handles go stale. → Key devices by MAC (USB serial number), not by path. Reopen with backoff (50 ms to 2 s, for up to 10 s) after a disconnect or a flash. Show 'recovering' state in the dashboard. Board profiles mark pins that must never be reconfigured, and docs give the BOOT-button recovery procedure.
- Port contention: Chrome Web Serial (which currently holds /dev/cu.usbmodem1101), idf.py monitor or the IDF MCP flash_project can open the same port, and flock is only advisory. → Before opening, check holders with `lsof -t <port>` and report the holding PID and app name. Expose a lease API (POST /api/ports/:id/lease) so external tools borrow the port explicitly. Agent skill docs say to never call idf.py flash or monitor directly while the hub runs.
- Opening or closing a port toggles DTR/RTS and resets the board unexpectedly (UART-bridge auto-reset circuits, or the USB-Serial/JTAG reset logic). → After open, explicitly set dtr:false and rts:false (behaviour per board profile) and keep hupcl configurable. Resets happen only through an explicit 'reset' action. Verify per board in spike S1.
- esptool's Python API carries no explicit stability promise; low-level ESPLoader methods (read_mac, change_baud, get_chip_description) are 'not public'. → Pin esptool==5.6.0 in the pytools lock file. Confine all esptool calls to one adapter module with contract tests. Fall back to the CLI if an import fails. Upgrade deliberately, with hardware tests.
- Wi-Fi power save (default WIFI_PS_MIN_MODEM) adds about 100 ms of latency and jitter to hub-to-node commands. → Firmware node profile defaults to WIFI_PS_NONE for powered devices. Nodes report their PS mode in HELLO and the dashboard warns. Measure latency continuously through ping/echo and show p50/p99 per link.
- Event-loop stalls (synchronous SQLite, large JSON, log bursts) add latency to input events. → Publish before persisting; batch SQLite writes on setImmediate or a 50 ms flush; serialize each envelope once; cap and coalesce stream-class traffic; watch perf_hooks.monitorEventLoopDelay and alert above 5 ms p99; keep CPU-heavy work (builds, image hashing over 1 MB, panic decoding) in child processes.
- Chrome LNA and mixed-content rules block games served from public https origins from reaching ws://hub. → The hub can serve apps on its own origin (/apps/<name>). The SDK defaults to same-origin or the hub's .local name or IP literal (which are exempt from mixed-content once permission is granted). Document the permission prompt; optionally offer wss with a locally trusted cert later.
- TypeScript 7 has no stable compiler API until 7.1, which affects codegen tools. → Make Zod schemas the single source of truth and write custom generators that read Zod or frame tables at runtime, rather than parsing TS types.
- The Python dependency complicates one-command install. → `propriocept doctor --fix` bootstraps ~/.propriocept/pytools with `uv venv` and `uv pip sync` from a lock file, falling back to python3 -m venv and pip. Long term, consider shipping pytools as a PyInstaller binary, or using espflash for basic flashing.

## OPEN QUESTIONS
- Is the Mac the only hub for the foreseeable future, or do you want an always-on Raspberry Pi/Linux hub soon? This decides whether Homebrew or a systemd/Pi image comes first in packaging.
- Default link for the first proof of concept: a USB ESP-NOW gateway node plugged into the hub (lowest, most deterministic latency, no router involved), or nodes joining your Wi-Fi and talking to the hub directly? I recommend gateway first, with Wi-Fi direct also supported.
- Will games run from public https sites, or can they be served by the hub or localhost? Public origins require Chrome's Local Network Access prompt and a .local hostname or IP.
- Is a Python sidecar (managed by uv) acceptable for flashing via esptool, or must the hub install as pure Node? Pure Node would mean esptool-js through a shim or the espflash binary, both weaker.
- Which ESP-IDF line should firmware standardize on: 5.5.x (installed now, latest 5.5.6) or 6.1 (latest; uses esptool v5 and adds `idf.py mcp-server`)? The hub supports both, but board profiles and CI need one default.
- Dashboard framework preference: React 19 (recommended for agent fluency and ecosystem) or Svelte 5?
- Security for v1: LAN-only and open, or a hub token for REST/WS/MCP from the start? I recommend a token that is auto-generated and stored in ~/.propriocept/hub.json and the SDK manifest.
- Which ESP32-S3 board do you have: native USB only, or one with an extra UART bridge (CH343/CP210x)? This affects identification and auto-reset handling.

## VERIFY: holds=True
### Challenge
The strongest case against: the hub needs two runtimes (Node plus a Python venv) and two native addons, and the serial addon (serialport/bindings-cpp) has had no release since Dec 2024 and no commits since Dec 2025. The planned fallback, pyserial, is even staler (2020). Meanwhile every hardware-intimate tool is Python: esptool, NVS gen, the panic decoder, esp-idf-monitor and idf.py. A Python hub (FastAPI + pyserial-asyncio + esptool in-process with a contextvar-dispatching logger) would remove the sidecar and its IPC. A Rust hub (axum + serialport-rs 4.10.1, which is active, + espflash as a library) would give a single binary with no Python.

Neither is materially better for this project, though. The consumer-facing surfaces (dashboard, generated game SDK, MCP) are TS. The serial layer is small and can sit behind an interface. Flashing still has to follow esptool, Espressif's reference.

The recommendation therefore holds, with these changes:
- Target Node 26. It becomes Active LTS on 2026-10-28; Node 24 enters maintenance today. Keep engines >=24.12.
- Use pnpm 12, or deliberately pin 11.
- Make the serial plan-B a napi-rs addon over serialport-rs rather than a pyserial bridge.
- Bootstrap pytools with `uv sync --frozen` and a uv-managed Python 3.12. System python3 is 3.9.6, below esptool 5.6.0's minimum of 3.10.
- Use IDF-native app signing instead of a custom ed25519 manifest.
- Drop the custom bonjour-service advertisement as the primary discovery path in favour of the Mac's own LocalHostName.local, which mDNSResponder answers and Local Network Privacy does not gate.
- Align the ESP-NOW framing and flooding with Espressif's esp-now component, which already provides TTL forwarding, dedupe, retransmit and OTA.
### Refuted/uncertain
- [uncertain] Because the esptool logger is global, concurrent jobs need separate processes whatever language the hub uses.
  → This is overstated. A custom TemplateLogger could dispatch on contextvars or threading.local, so multiplexing in one process is possible. One process per job is still the better choice for isolation and SIGTERM cancellation. (https://docs.espressif.com/projects/esptool/en/latest/esp32/esptool/scripting.html)
- [uncertain] Node 24.11.1 runs .ts files from pnpm-symlinked workspace packages (default realpath resolution).
  → Not re-run, because I was barred from writing files. It is consistent with Node's realpath resolution and its node_modules check. For publishing, use conditional exports (e.g., a 'development' condition pointing at src/*.ts and default pointing at dist). (https://nodejs.org/api/typescript.html)
- [refuted] Button-to-browser latency is over 100 ms with the default power save.
  → Modem sleep delays reception at the station, i.e. hub-to-node commands. A node-to-hub UDP input is sent immediately and is not held for DTIM. Spec section 18 scopes this correctly; the summary does not. Commands still need PS_NONE. (~/esp/v5.5.1/esp-idf/docs/en/api-guides/wifi.rst L1805)
- [uncertain] USB-Serial/JTAG limitations: the device disappears in deep sleep or on USB pin reconfiguration (recover with GPIO9 low plus reset), there is a 50 ms stall when the host does not read, and it re-enumerates in about 1 s after a chip reset.
  → Deep sleep, pin reconfiguration, the 50 ms stall and the light-sleep replug are confirmed. Re-enumeration after reset is undocumented: esptool says RTS over USB-Serial/JTAG is a core reset, which may keep the USB link. Treat the 1 s figure as a spike S1 measurement, not a fact. (https://docs.espressif.com/projects/esp-idf/en/latest/esp32c6/api-guides/usb-serial-jtag-console.html ; https://docs.espressif.com/projects/esptool/en/latest/esp32c6/esptool/advanced-options.html)
- [uncertain] All three of the user's boards use USB-Serial/JTAG, so flashing must be on the host.
  → True for the C3 and C6 Super Minis. Many S3 boards (e.g., DevKitC-1) also have a CP210x/CH343 UART port, and S3 apps may run TinyUSB (USB-OTG) with a different PID. The report rightly lists this as an open question. (https://docs.espressif.com/projects/esptool/en/latest/esp32/remote-serial-ports.html)
- [refuted] v1 OTA uses an ed25519-signed manifest the node verifies (spec section 8).
  → IDF 5.5's mbedTLS 3.6.4 has no EdDSA implementation (no eddsa or ed25519 in library/*.c), so this would need libsodium. IDF's native alternative: CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT plus SECURE_SIGNED_ON_UPDATE_NO_SECURE_BOOT (RSA-3072/ECDSA), which esp_ota_ops verifies automatically with no eFuse burning. (~/esp/v5.5.1/esp-idf/components/mbedtls/mbedtls/library (no EdDSA); components/bootloader/Kconfig.projbuild L497-602)
### Missed
- Node 24 enters Maintenance LTS on 2026-10-20 and Node 26 becomes Active LTS on 2026-10-28 (EOL 2029-04-30 vs 2028-04-30). A greenfield project should default to Node 26 while keeping 24.12+ supported.
- Raspberry Pi must run a 64-bit OS. Node 24 and 26 have no official linux-armv7l builds, and better-sqlite3 13.0.3 has no linux-arm prebuild and no compile fallback (gypfile:false). serialport does ship armv7.
- ESP-NOW and Wi-Fi share one radio and channel. A peer's channel must equal the device's current channel, and a STA's channel is the AP's. Nodes on the router plus the USB gateway must therefore follow the router's channel, and router auto-channel changes silently break ESP-NOW. The hub must provision and track the channel per network (esp_now.rst L95).
- ESP-NOW limits that affect the hub's routing table and security design: at most 20 paired peers, at most 17 encrypted (default 7; ESP_NOW_MAX_ENCRYPT_PEER_NUM 6 in esp_now.h), and broadcast/multicast cannot be encrypted. The net_key must therefore drive app-layer authentication (e.g., HMAC plus replay counter) for floods. The v2 payload is 1470 B (v1 250 B).
- Espressif's esp-now component (espressif/esp-now 2.5.3, active Sep 2026) already implements broadcast forwarding with forward_ttl/forward_rssi, dedupe by 'magic', retransmit_count, ACK, security, provisioning, debug-log forwarding and batch OTA (espnow_ota). The hub's frame table and Phase-2 ESP-NOW OTA should align with it or adopt it rather than reinvent it.
- Modem sleep delays only downlink (hub to node). Uplink inputs are not held for DTIM, so the PS_NONE requirement applies to command/effect latency and to TCP ACK-dependent flows, not to UDP input events.
- Discovery under Local Network Privacy: when the hub is launched by Claude desktop or VS Code, bonjour-service cannot send or receive multicast and `dns-sd -R` registration is also gated. The Mac's own `<LocalHostName>.local` is answered by mDNSResponder (a launchd daemon, exempt). Write hub_url as that name (from `scutil --get LocalHostName`), not a raw DHCP IP and not 'propriocept.local'. If a JS responder is still wanted, @homebridge/ciao (1.3.12, Aug 2026) is maintained; multicast-dns has not been released since 2022.
- The macOS Application Firewall (socketfilterfw), when enabled, can block inbound TCP/UDP to the node binary independently of Local Network Privacy. `doctor` should check it.
- On this Mac, /usr/bin/python3 is 3.9.6 and esptool 5.6.0 requires Python >=3.10. Bootstrap must use `uv python install` or uv-managed Python, and the venv fallback needs a version check.
- flasher_args.json from IDF <=5.5 carries esptool v4 values ('default_reset', 'hard_reset', '--flash_mode'). esptool 5.6.0's reset_chip raises FatalError on 'hard_reset', and connect_esp treats any value other than exact 'no-reset' as a reset. The flash plan must normalize '_' to '-'.
- OTA 'from the ground up' depends on the first serial flash: an OTA-capable partition table (two_ota needs about 3.06 MB of a 4 MB part with 1 MB slots), CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE, and firmware that delays esp_ota_mark_app_valid_cancel_rollback() until the hub acknowledges HELLO. Otherwise the orchestrator's 'rollback takes over' never triggers. Board profiles must encode flash size and partition plan.
- OTA validation should also compare min_chip_rev_full/max_chip_rev_full (image header offsets 15 and 17) with the device's chip revision, not just chip_id.
- Gateway latency budget: the gateway must use native USB (USB-Serial/JTAG or TinyUSB CDC). FTDI-type bridges add a default 16 ms latency timer, which would blow the 4-5 ms target. Device-side USB-Serial/JTAG writes need explicit flushes for small frames.
- The MCP Streamable HTTP endpoint inside Fastify needs @modelcontextprotocol/fastify (2.0.1) or @modelcontextprotocol/node (2.1.1). @modelcontextprotocol/server ships only the web-standard transport.
- IDF 6's `idf.py mcp-server` flash_project(port) will fight the hub for ports. The hub should either proxy or replace it (exposing equivalent tools), and agent skills must say so. It also requires EIM >=0.8.1 with the mcp feature.
- A token in `?token=` on WS leaks into logs and history. The C2S 'hello' already has a token field, so authenticate in the first message (or Sec-WebSocket-Protocol) instead.
- The ports table keyed by `path` contradicts the risk mitigation of keying by MAC/USB serial. macOS usbmodem names derive from the USB location and change when the board moves between sockets.
- Chrome 147+ prompts for LNA on WebSocket connections from public origins. Third-party reports say Chrome 148+ also checks a header on the 101 response (unverified). This should be in the hub's WS upgrade handling if public-origin games are supported.
- tsconfig: Node's recommended config uses rewriteRelativeImportExtensions without allowImportingTsExtensions. The latter is redundant and, in TS 5.x, required noEmit or emitDeclarationOnly (low confidence for TS 7). Keep the base config typecheck-only (noEmit).

Espressif documents disappearance only for deep sleep, light sleep and USB pin reconfiguration, and esptool calls an RTS reset a core reset. Mark it TBD pending spike S1.
- Section 12: `ports` uses `path TEXT PRIMARY KEY`, contradicting the stated rule to key devices by MAC/USB serial and not by path. usb_serial should be the stable key.
- Section 17.1 lists iTerm among gated launchers as fact. TN3179 exempts only 'Command-line tools run from Terminal or over SSH' and does not say how third-party terminals are treated. Mark it unverified (spike S5).
