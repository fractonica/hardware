# ota-identity

## SUMMARY
I grounded this design in the local ESP-IDF v5.5.1 sources (Kconfig, headers, gen_esp32part, the NVS tools, the esptool 5.1 source and the Arduino-ESP32 3.3.4 platform.txt) and in current Espressif docs and repos. Every board uses the same partition scheme: two OTA slots with app rollback and no factory app. The head of flash follows Arduino's fixed offsets (otadata at 0xE000, ota_0 at 0x10000), and a read-only 16 KB NVS identity partition ("fctry") sits in the last 16 KB of flash. I checked all three CSVs (4/8/16 MB) with gen_esp32part. Max app size per slot is 1920 KB, 3 MB and 4 MB. Device identity is the 6-byte factory eFuse MAC. That MAC is also the Wi-Fi STA / ESP-NOW source address and the USB-Serial/JTAG descriptor serial number, so the hub can identify a plugged-in board without opening the port. The hub assigns the alias and per-device key and writes them as an nvs_partition_gen image in the same esptool write-flash call as the firmware. This identity survives OTA and app reflashes, and the hub registry can restore it after a full erase. Over Wi-Fi, a node gets updates by HTTP pull into one shared "ota_sink" built on esp_ota_ops, after the hub sends an HMAC-authenticated offer that pins the image digest. The same sink serves the ESP-NOW relay path (espnow_ota, or a custom bitmap-NACK broadcast) and later delta OTA. After reboot, the new image must pass a health check before it marks itself valid; any reset or failed check before that rolls it back automatically. For the lab, secure boot and flash encryption stay off, because they burn eFuses irreversibly. Signed apps without secure boot is an opt-in hardening profile. The hub runs a pinned esptool ≥5.2 through its Python API with a JSON logger, because esptool v5 says log-parsing is not recommended. Several gotchas were confirmed in source: on the C6, esp_efuse_mac_get_default() writes 8 bytes. Serial app-only flashes must also rewrite otadata. Arduino's upload recipe hard-codes 0xE000 and 0x10000, and its merged .bin is padded to full flash size, so flashing it would wipe the identity partition.

## RECOMMENDATION
1) One partition profile per flash size (4 MB, 8 MB, 16 MB, schema v1), all with the same head: nvs at 0x9000 (20 KB), otadata at 0xE000, ota_0 at 0x10000, two equal OTA slots, coredump 64 KB, and the read-only NVS "fctry" in the last 16 KB of flash. No factory app. These bootloader settings are fixed at the first serial flash: CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE=y, anti-rollback off, secure boot off, flash encryption off.
2) Identity: device_id = 12 lowercase hex characters from esp_read_mac(ESP_MAC_EFUSE_FACTORY). short_id = the last 3 bytes, for display only. alias is an RFC 1123 label assigned by the hub. The hub registry is the source of truth; fctry is the on-device copy, written at flash time. A runtime alias override goes in RW nvs, and the newer timestamp wins.
3) Provisioning: the hub finds the board by USB VID 0x303A / PID 0x1001 (serial number = MAC) and probes it with esptool flash-id plus get-security-info. It upserts the registry entry, generates fctry.bin (nvs_partition_gen, 0x4000) with the lab Wi-Fi credentials, hub URL and a 32-byte per-device key, and writes bootloader, partition table, ota_data_initial, app and fctry in one esptool write-flash. Fallbacks: Improv-Serial re-provisioning and trust-on-first-use adoption for devices flashed elsewhere.
4) OTA: the hub pushes an HMAC-signed ota.offer (fw_id = appended image SHA-256, size, URL). The node pulls the image over plain HTTP into a shared ota_sink (esp_ota_begin with the known size, then write, then esp_ota_end, then a digest check against the signed fw_id). An optional deferred commit allows switching many devices at once. After reboot the image is PENDING_VERIFY; a health check with a 60 s deadline marks it valid, otherwise it rolls back. ESP-NOW-only nodes are updated through a gateway via espnow_ota (with a digest check in its FINISH hook) or a custom bitmap-NACK broadcast using ESP-NOW v2 frames. Delta OTA (esp_delta_ota) comes in phase 2, for the ESP-NOW path only.
5) Fleet: content-addressed artifact store plus a per-build manifest.json (target, chip_id, board, hw_profile, partition profile, fw_id, sha256, esp_app_desc fields, a custom pc_app_desc at bin offset 288). Deployments are reconciled toward a desired state: canary, then waves, with max_parallel, soak time and a failure ratio that pauses the rollout. A USB-attached gateway is updated over serial; a wireless gateway is updated last.
6) Security level L0 (default): HTTP, a per-device HMAC on control-plane commands, digest pinning, no TLS. Level L1 (opt-in): CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT. Never burn secure boot or flash-encryption eFuses on lab devices.
7) Tooling: the hub owns its own uv venv pinned to esptool 5.6.x and esp-idf-nvs-partition-gen 0.3.x. It calls them through a Python sidecar using esptool.cmds plus a custom logger that emits JSON lines; the CLI with NO_COLOR=1 and regex parsing is the fallback. It never relies on the IDF-bundled esptool 4.11.

## RATIONALE
Two OTA slots with bootloader rollback give the safest update on chips without ROM bootloader recovery. In ESP-IDF 5.5.1, SOC_RECOVERY_BOOTLOADER_SUPPORTED exists only for C5 and C61, so the bootloader and partition table on the C3, C6 and S3 must be treated as serial-only and frozen now. A factory app would take a third of a 4 MB flash and add little in a lab where every device can be reflashed over USB. Arduino-ESP32 3.3.4 hard-codes boot_app0 at 0xE000 and the app at 0x10000 in its upload recipe. Matching those offsets makes Arduino, PlatformIO and idf.py flashes all safe. Putting fctry at the end of flash keeps it outside every area those tools write (the exceptions are a full-flash-padded merged .bin and erase-flash, and the hub registry repairs both). The factory MAC is the right identity because the code shows the STA MAC equals the base MAC, which is also the ESP-NOW source address. The USB-Serial/JTAG serial number is that same MAC, so no new ID has to be assigned. One trap: esp_efuse_mac_get_default() returns an 8-byte EUI-64 on the C6, which is why the identity code uses ESP_MAC_EFUSE_FACTORY. Writing identity as a flash-time NVS image needs no runtime protocol, is deterministic and agent-friendly, and survives OTA. The readonly partition flag (IDF ≥ 5.2) stops app bugs from corrupting it. HTTP pull through esp_ota_ops instead of esp_https_ota means one sink serves every transport. That sink can check compatibility from the first chunk (esp_app_desc_t and the custom descriptor at fixed offsets), and it supports a deferred commit. It also needs neither TLS nor CONFIG_ESP_HTTPS_OTA_ALLOW_HTTP, which only gates esp_https_ota. Pinning the digest inside an HMAC-authenticated offer gives authenticity without TLS or key infrastructure. Over Wi-Fi the radio is not the bottleneck: the ESP32-C3 docs give up to 20 Mbit/s TCP, and flash erase/write dominates. That is why delta OTA only pays off on ESP-NOW, at about 214 kbps open-air per Espressif's FAQ. Secure boot and flash encryption burn eFuses irreversibly and complicate reflashing, so they are wrong for prototyping.

## ALTERNATIVES
- **Partition: two OTA slots, no factory (Arduino-compatible head, fctry at end of flash)** — verdict: RECOMMENDED
- **Partition: factory (1MB rescue) + ota_0/ota_1 (1408K each) on 4MB** — verdict: Rejected for lab; reconsider only for untethered field units
- **Identity partition in the fixed head (e.g. 0x12000) instead of end of flash** — verdict: Rejected; Arduino compatibility matters more
- **Identity provisioning: NVS image written by hub at flash time** — verdict: RECOMMENDED (primary)
- **Identity/Wi-Fi via first-boot Improv-Serial** — verdict: Secondary path for re-provisioning and for devices flashed outside the hub
- **BLE/SoftAP provisioning (esp_prov / network_provisioning)** — verdict: Out of scope for lab; product-phase only
- **Wi-Fi credentials in Kconfig/sdkconfig** — verdict: Dev-only fallback (CONFIG_PC_WIFI_* in a git-ignored sdkconfig.defaults.local)
- **OTA transport: node HTTP pull via esp_http_client + esp_ota_ops (custom ota_sink)** — verdict: RECOMMENDED
- **esp_https_ota with CONFIG_ESP_HTTPS_OTA_ALLOW_HTTP** — verdict: Acceptable alternative; not preferred
- **ESP-NOW OTA via espressif/esp-now espnow_ota** — verdict: Use if the networking layer adopts esp-now; otherwise reimplement the same algorithm on our protocol with ESP-NOW v2 frames
- **Delta OTA (espressif/esp_delta_ota, detools+heatshrink) in v1** — verdict: Phase 2, ESP-NOW path only
- **Security: secure boot v2 + flash encryption** — verdict: Never on lab devices (L2, product phase)
- **Security: signed apps without secure boot (CONFIG_SECURE_SIGNED_APPS_NO_SECURE_BOOT)** — verdict: Opt-in L1 profile
- **Hub flashing via esptool CLI + regex log parsing** — verdict: Fallback only; primary is the esptool.cmds Python API with a JSON logger
- **Browser flashing (esptool-js / Web Serial)** — verdict: Optional dashboard convenience, not the core path

## RISKS
- Bootloader and partition table cannot be safely updated over the air on C3/C6/S3 (no ROM recovery), so a later layout or bootloader-config change means a USB reflash of every device. → Freeze profile v1 now, with rollback ON from the first flash, generous slots and a spare storage partition. Version profiles (pc-4mb-v1). The hub provides a 'migrate-layout' serial job that reads back fctry, rewrites it at the new offset and verifies it.
- Third-party flashing (Arduino merged .bin padded to flash size, erase-flash, 'Erase all flash' option) wipes the fctry identity. → The registry is the source of truth. A node with no fctry announces itself as unprovisioned with its MAC, and the hub re-provisions it automatically (serial) or re-adopts it (network). The hub never flashes padded merged images; it uses multi-file write-flash or a hex merge.
- Calling esp_efuse_mac_get_default() with a 6-byte buffer on the ESP32-C6 overflows it (the call writes 8 bytes) and yields an EUI-64 instead of the MAC. → Expose a single pc_id_get_mac() wrapper using esp_read_mac(..., ESP_MAC_EFUSE_FACTORY); add a CI grep/lint banning direct esp_efuse_mac_get_default and esp_base_mac_addr_set in framework code.
- False rollbacks: the new image cannot reach the AP or hub during the health window (AP reboot, DHCP slowness), or a serial monitor attaches with DTR/RTS reset while the image is PENDING_VERIFY. → 60 s default health deadline (configurable). The hub-ack bit is required only when the hub was reachable before the update. The rollback reason is reported. The hub monitor opens ports without toggling DTR/RTS and blocks reset-on-attach while a job is in VERIFYING.
- Serial port contention: Chrome Web Serial currently holds /dev/cu.usbmodem1101, so esptool cannot open it. → The hub is the single owner of serial ports, with explicit monitor-to-flasher handoff. The dashboard consumes the hub's WebSocket log stream instead of Web Serial. On open failure the hub reports E_PORT_BUSY with the owning process when possible.
- Auto-reset into download mode fails if the firmware repurposes the USB D-/D+ pins, sleeps, or crash-loops early. → The hub detects connect failures (exit code 2 plus 'Failed to connect'), sets the device to needs_manual_boot, and shows the steps: hold BOOT (GPIO9 on C3/C6, GPIO0 on S3), tap RESET, retry. The framework forbids reconfiguring the USB-JTAG pins unless the board profile opts in.
- Flash erase/write during OTA disables cache and stalls the radio and ISRs, adding latency jitter to the realtime input network, especially on single-core C3/C6 and on relay nodes. → A node in DOWNLOAD/VERIFY advertises busy:ota and the mesh excludes it from re-broadcast duty. Rollouts use max_parallel and can be scheduled outside interactive sessions. Bulk pre-erase at esp_ota_begin(size) concentrates the stall at the start.
- ESP-NOW OTA security: espnow_ota responders accept pre-auth requests and set the boot partition without checking the announced digest. → Start the responder only after an HMAC-authenticated ota.espnow.accept naming the initiator MAC and fw_id. In the FINISH hook, compare esp_partition_get_sha256(update) to fw_id and, on mismatch, call esp_ota_set_boot_partition(running) and report. Or implement our own transport over ota_sink.
- In the L0 lab profile, Wi-Fi credentials and dev_key are plaintext in fctry; anyone with physical access can dump them and forge OTA commands for that device. → Per-device keys limit the blast radius. Document L0 as LAN/lab-only. L1 adds signed apps so a leaked dev_key cannot install unsigned images. The hub supports key rotation (id.rotate_key over an authenticated channel).
- esptool and NVS-generator version drift (IDF env pins esptool 4.11; PATH has 5.1; latest is 5.6; log format changed between v4 and v5). → Hub-managed uv venv with exact pins (esptool==5.6.x, esp-idf-nvs-partition-gen==0.3.x). Use the Python API with a JSON logger. Contract tests decode generated fctry images with nvs_tool.py and parse probe output from recorded fixtures.
- Unknown S3 variant (flash size, octal vs quad PSRAM) can lead to flashing an incompatible profile or build. → Mandatory probe (flash-id plus chip features such as 'Embedded PSRAM 8MB'). Board profile is selected by the user or agent once and stored in the registry and fctry. The hub's compatibility gate refuses target, board or flash-size mismatches unless forced.
- A 64 KB coredump partition may truncate dumps of large S3 apps with many tasks. → 64 KB is the IDF template default and fine for C3/C6; profile v1 keeps it uniform. If truncation shows up, coredump moves to 128 KB in pc-8mb/16mb-v2 (taken from storage) via a serial migration.

## VERIFY: holds=True
### Challenge
The strongest case against the recommendation is that its identity layout is not as toolchain-portable as claimed.

1. **Arduino compatibility is overstated.** Matching the Arduino head offsets (0xE000 / 0x10000) does not make Arduino flashes safe. Every Arduino upload rewrites the bootloader at 0x0 and the partition table at 0x8000. A sketch built with the default Arduino scheme replaces the table, so fctry is no longer listed. That scheme also places coredump at 0x3F0000-0x400000, which covers fctry at 0x3FC000, and the Arduino libs have coredump-to-flash enabled. One crash then erases the identity physically.

2. **Older toolchains reject the CSV.** IDF 4.4, IDF 5.0-5.1, Arduino 2.x (PlatformIO espressif32@6.12 Arduino), Arduino 3.0.x-3.2.0 and the local pioarduino 51.03.03 all fail at build time on the 'readonly' flag. IDF 4.4 / Arduino 2.x also reject 'littlefs'. The fctry design therefore really requires IDF >= 5.2 or Arduino >= 3.2.1, plus the framework CSV in every sketch. The hub should read and verify the partition table at 0x8000 before any OTA.

3. **Frozen is overstated.** IDF 5.5 can OTA the bootloader and partition table without a recovery bootloader (partitions_ota example), at the cost of a brick window during the final copy. "USB reflash of every device" is the safe path, not the only one.

4. **Scope is heavy for a button-plus-LED PoC.** HMAC offers, deferred atomic commit, canary/wave rollouts, ESP-NOW relay OTA, delta OTA and coredump upload are a lot to build at once. It should be phased: v1 is serial provision, HTTP-pull OTA with rollback and health check, and MAC identity.

**Alternatives considered:**
- A fixed-offset read-only fctry in the head: nvs 0x9000/0x4000 plus fctry 0xD000/0x1000. It passes gen_esp32part 5.5.1, nvs_partition_gen accepts 0x1000 for read-only, and the offset is the same on every flash size. However, it sits inside Arduino's default nvs range, so it is a trade-off, not a clear win.
- Runtime-only adoption: MAC identity, alias and key delivered by trust-on-first-use, Wi-Fi via Improv. This is simpler but less deterministic for agents.
- ESPHome: it has OTA, a dashboard, Improv, Web Tools and ESP-NOW. But it is configured through YAML codegen, which conflicts with the custom HAL, the JS-codegen and ESP-NOW re-broadcast requirements.

None of these is materially better. The core choices still stand: factory-MAC identity, two OTA slots with rollback and no factory app, an HTTP-pull ota_sink with digest pinning, and lab security L0/L1. They hold once the corrections below are applied.

### Missed
- Arduino and PlatformIO uploads rewrite the bootloader (0x0) and partition table (0x8000) on every flash. A sketch on Arduino's default scheme (default.csv: coredump 0x3F0000/0x10000) loses fctry from the table and overlaps it physically, and coredump-to-flash is enabled in the Arduino libs. The framework must ship partitions.csv in every sketch folder or board definition, and the hub should read back 0x8000 and compare it to the profile before OTA or provisioning.
- IDF 5.5 supports unsafe OTA of the bootloader and partition table on C3/C6/S3 (esp_ota_begin on BOOTLOADER/PARTITION_TABLE types, examples/system/ota/partitions_ota). A layout migration can happen over the air with a brick-on-power-loss window. It does not have to be a USB reflash of every device.
- Any reset during PENDING_VERIFY rolls the image back. That includes an esptool probe (the CLI fallback runs flash-id and get-security-info, which means two default-resets), a USB re-plug or power-cycle within the 60 s window, and a user pressing RESET. The PoC input is the BOOT strapping pin (GPIO9 on C3/C6, GPIO0 on S3), so holding the input button through a power-on or RESET puts the node into ROM download mode and the OTA job times out. The hub should detect a node stuck in download mode over USB and reset it.
- Mixing esp_ota_write() and esp_ota_write_with_offset() on one handle corrupts the write pointer. with_offset adds its size to wrote_size, and esp_ota_write and esp_ota_end write at wrote_size. Non-sequential transports must use with_offset exclusively; it also asserts a pre-erased partition.
- esp_ota_resume() exists in IDF 5.5.1, so a resumed HTTP Range download after a reboot needs no custom code. Pre-erasing 1-2 MB at esp_ota_begin(size) on single-core C3/C6 means seconds of flash operations with the cache disabled, which disrupts ESP-NOW and Wi-Fi. OTA_WITH_SEQUENTIAL_WRITES spreads the erases out instead.
- The ESP-NOW source MAC equals device_id only on WIFI_IF_STA; the SoftAP interface uses base+1. A custom base MAC (esp_base_mac_addr_set or CONFIG_ESP_MAC_USE_CUSTOM_MAC_AS_BASE_MAC) also breaks the STA==factory assumption.
- espnow_ch stored in fctry means nothing while the STA is associated, because the AP dictates the channel and ESP-NOW must match it. It should be derived at runtime and stored only for ESP-NOW-only nodes.
- An S3 app using USB-OTG/TinyUSB (Arduino 'USB Mode: USB-OTG') changes VID, PID and serial number, so mapping a USB port to a MAC without opening it fails. UART-bridge S3 DevKits expose two ports per board.
- C3 Super Mini clones commonly fail to associate or drop Wi-Fi at the default TX power (community reports suggest about 8.5 dBm). The board profile should carry a tx_power cap, otherwise HTTP OTA success rates suffer. This is medium confidence, from community sources only.
- Rotating dev_key cannot write to fctry: the readonly flag is enforced by esp_partition. The RW override namespace needs dev_key plus a timestamp, or rotation needs a serial identity reflash.
- pyserial on macOS and Chrome Web Serial set DTR/RTS when a port opens, and on USB-Serial/JTAG RTS is a core reset. The hub monitor must set dtr and rts to False before open() to avoid resets during PENDING_VERIFY.
- IDF 5.5 pins esp-idf-nvs-partition-gen ~=0.1.9; the hub's 0.3.x is two minor versions ahead. The planned nvs_tool round-trip contract test should run on the 0.3.x output against the IDF 5.5 runtime.
- The orchestrator context says the IDF Python env is py3.12, but locally it is idf5.5_py3.10_env (Python 3.10), alongside an older idf5.3_py3.9_env.
- Arduino nodes auto-mark the app valid in initArduino() unless verifyRollbackLater() returns true. The framework's Arduino shim must override it, or the health check is bypassed.
- Browser flashing (esptool-js / ESP Web Tools) consumes binary parts with offsets, not Intel HEX. A Web Tools manifest with separate parts serves the 'no identity' merged image better than merge-bin --format hex.
### Spec errors
- Section 7.2.2: 'The readonly flag needs IDF >= 5.2 or Arduino-ESP32 3.x ... so it stays valid on older toolchains that ignore the flag'. This is wrong. Arduino-ESP32 has the flag only from 3.2.1 (3.0.x-3.2.0 lack it). Older gen_esp32part raises InputError "CSV flag column contains unknown flag 'readonly'", so the build fails. IDF 4.4 / Arduino 2.x additionally reject subtype 'littlefs'; use 0x83 for portability.
- Spec header: 'Changing these decisions later means a USB reflash of every device' is overstated. IDF 5.5 supports unsafe OTA of the bootloader and partition table (partitions_ota example; esp_ota_begin accepts BOOTLOADER/PARTITION_TABLE types).
- Section 7.2.1 rule 2 and the 'Arduino-compatible' claim: matching offsets alone is not enough. Arduino's default.csv puts coredump at 0x3F0000/0x10000, overlapping fctry at 0x3FC000, and every Arduino upload rewrites 0x8000. Compatibility requires shipping the framework CSV with every sketch.
- Section 7.5.1: 'Wi-Fi gives >= 20 Mbit/s TCP' should read 'up to 20 Mbit/s TCP' (ESP32-C3 Wi-Fi guide).
- Section 7.5.2 pc_ota_write: 'in-order: esp_ota_write; else esp_ota_write_with_offset' is unsafe. with_offset increments wrote_size, which shifts later esp_ota_write and esp_ota_end positions. Use esp_ota_write_with_offset exclusively (after the size-based pre-erase) or esp_ota_write exclusively.
- Section 7.3.1: 'device_id equals the ESP-NOW source MAC' holds only when ESP-NOW sends on WIFI_IF_STA and no custom base MAC is set.
- Section 7.3.1 alias regex ^[a-z][a-z0-9-]{0,30}$ allows a trailing hyphen, so it is not a valid RFC 1123 label. Use ^[a-z]([a-z0-9-]{0,29}[a-z0-9])?$. Hyphens also need mapping for JS identifiers in codegen.
- Section 7.3.3: storing espnow_ch in fctry conflicts with the rule that ESP-NOW must use the associated AP's channel. It should be runtime-derived.
- Section 7.3.3 / 7.7: id.rotate_key has no storage location. fctry is readonly at runtime (esp_partition rejects writes) and pc_ovr holds only alias and ovr_ts.
- Section 7.7 / key_facts: 'Secure Boot v2 makes the bootloader non-OTA-upgradable' is wrong. SB v2 accepts an updated bootloader signed with the matching key; only SB v1 forbids bootloader updates.
- Section 7.8 regex table example 'Features: Embedded Flash 4MB (GD)': esptool's C6 get_chip_features() omits embedded flash, so use 'Detected flash size:' for the C6.
- Section 7.8 API list: connect_esp exists only in esptool >= 5.4.0. That is fine under the 5.6 pin, but the PATH radioconda 5.1.0 cannot run the sidecar.
- Section 7.8 CLI fallback probe: running flash-id and get-security-info as separate commands resets the chip twice. On a device in PENDING_VERIFY this triggers a rollback, so the CLI path should be blocked during VERIFYING, as the monitor already is.
- Section 7.8 'browser/archive image WITHOUT identity (sparse hex)': esptool-js and ESP Web Tools flash binary parts with offsets, not Intel HEX. Use a multi-part manifest.
- Section 7.2.3 'CONFIG_ESP_TASK_WDT_PANIC=y # a hang during PENDING_VERIFY -> reset -> rollback': the TWDT watches only idle tasks and subscribed tasks, so a blocked or deadlocked task does not trigger it. The health-deadline timer is the real guard.
