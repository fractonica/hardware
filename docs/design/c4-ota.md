# C4 OTA: implementation design

> **Folded into the spec on 2026-10-22:** the §8 decisions and the notes added during implementation now live in [docs/spec](../spec/README.md) (mainly 03, 05, 06, 08 and 09; also 02, 04, 07, 10 and 11), and C4's open items for later checkpoints are listed in [11 §11.4](../spec/11-roadmap.md). This note is kept as the implementation record.

Checkpoint C4 ([11 §11.4](../spec/11-roadmap.md)): HTTP pull + rollback. Gates **T-OTA** and **T-PROV** ([10 §10.5](../spec/10-testing.md)).

Source of truth: spec 06 §6.1–6.8 (flash layout, identity, OTA transports, `ota_sink`, health gate, hub job and rollout, artifacts), 03 §3.4–3.5 and §3.8 (`fr_worker`, boot sequence, fault builds), 05 §5.7 (OTA class messages), 08 §8.2, §8.6 and §8.10 (listener 7422), 09 §9.4–9.5 (`ota_deploy`, `ota_status`, `deploy`), 10 §10.5 (T-OTA, T-PROV). This note fixes what the streams share and decides what the spec leaves open; §8 lists the decisions to fold back. Sections 2–4 describe C4 as built (the streams' choices reconciled by the integrator); fold §8 into the spec when T-OTA and T-PROV pass on target.

## 1. Scope

In:
- **Firmware:** `fr_app_desc` (06 §6.8); `fr_worker` task; component `fr_ota` (CHECK, sequential sink, HTTP pull with Range and in-boot retries, resume after reboot, VERIFY, STAGED/COMMIT, BYE `ota` + restart, health gate with `CORE | CAPS | NET | HUB_ACK` and `hub_seen`, rollback detection and report, `ota_busy`); OTA class frames on port 240; fault builds (`CONFIG_FR_TEST_FAULT_HEALTH`).
- **Hub:** node HTTP listener `0.0.0.0:7422` (`GET /ota/<fw_id>.bin` with Range, gated by an outstanding OFFER to the requesting node's IP); the OTA orchestrator (per-device job state machine per 06 §6.7, retries 5/15/45 s, `ota.job.state` events); ops `ota_deploy`, `ota_status`, `deploy`; `fr build --fault health`; artifact ingest of `fr_app_desc`; transport `auto | serial | wifi`.
- **Gates:** T-OTA (Wi-Fi OTA to both boards, a health-fault image rolls back with the reason, a power cut mid-download resumes or retries) and T-PROV (provision each board from blank in ≤ 60 s; identity survives an app reflash and an OTA; a rename propagates).

Out: ESP-NOW relay OTA (M2+), delta OTA (M3), canary/waves and atomic COMMIT across devices (M3; the hub never sets DEFER_COMMIT and never sends COMMIT in M1), crash reports and core-dump upload (`POST /node/v1/coredump`, `crash_list`, `crash_get`: next checkpoint that needs them; the coredump partition stays), signed images (L1).

## 2. `fr_app_desc` (foundation)

```c
#define FR_APP_DESC_MAGIC   0x46524144u  /* "FRAD" */
#define FR_APP_DESC_VERSION 1
#define FR_APP_DESC_OFFSET  288u         /* image offset: right after esp_app_desc_t (32 + 256) */
typedef struct {
    uint32_t magic;            /* FR_APP_DESC_MAGIC */
    uint8_t  version;          /* FR_APP_DESC_VERSION */
    uint8_t  proto_major, proto_minor, reserved;
    uint32_t catalog_hash;     /* fr gen catalog hash */
    char     board[32];        /* CONFIG_FR_BOARD */
    char     profile[32];      /* CONFIG_FR_PROFILE */
    char     part_profile[16]; /* CONFIG_FR_PART_PROFILE */
    uint8_t  fault;            /* FR_APP_DESC_FAULT_NONE 0, FR_APP_DESC_FAULT_HEALTH 1 */
    uint8_t  reserved2[19];
} fr_app_desc_t;               /* 112 B; _Static_assert'ed */
```

- `fr/app_desc.h` is plain C; the one definition is `extern "C"` in `fr_core/src/app_desc.cpp` (so `catalog_hash` is the generated `fr::cap::kCatalogHash`), `section(".rodata_custom_desc")`, `used`, linked with `-u fr_app_desc`. IDF v6.1 places `.rodata_custom_desc` right after `.rodata_desc` in `.flash.appdesc` (all targets), so it lands at **image offset 288**; the C++ and TS tests share golden bytes.
- The hub ingest parses it into the manifest (`app_desc: {board, profile, part_profile, catalog_hash, fault}`, `fault` the raw byte) and fails the build with `BUILD_FAILED` if the magic is missing at 288 or board, profile, part_profile, fault or catalog_hash differ from the build (the error lists each field).
- The node CHECK (§3) reads the incoming image's `fr_app_desc` from its first 400 bytes (`kCheckBytes` = 288 + 112).

## 3. Node: `fr_ota`

Component `firmware/components/fr_ota`; `src/core/` is host-buildable (state machine, CHECK, resume bookkeeping, health gate) over four interfaces; `src/esp/` implements three of them, and `fr_core` the fourth (`Host`).

```cpp
namespace fr::ota {
class Flash {   // esp: esp_ota_begin/resume/write/end, set_boot_partition, partition sha256, otadata
  Status begin(uint32_t size, uint32_t resume_off);   // OTA_WITH_SEQUENTIAL_WRITES; resume via esp_ota_resume
  Status write(std::span<const uint8_t>);             // sequential only
  Status finish(std::span<uint8_t, 32> sha_out);      // esp_ota_end (invalid_args: does not verify) + sha256
  Status set_boot();
  void abort();
  Status read(uint32_t offset, std::span<uint8_t>);   // the resume CHECK reads the slot back
  Status mark_valid();                                // esp_ota_mark_app_valid_cancel_rollback
  void rollback();                                    // ..._invalid_rollback_and_reboot; returns only if impossible
  RunningInfo running() const;  // fw_id, version, pending_verify, last invalid fw_id, chip id/rev, slot size/addr, crashed
};
class Fetch {   // HttpGet: HTTP/1.1 GET over BSD sockets (lwIP on target, POSIX in fr_net_node) with Range, 10 s timeouts
  Status start(const char* url, uint32_t from_byte);
  std::expected<size_t, Err> read(std::span<uint8_t>);   // 0 = done
  void close();
};
class Store {   // nvs:fr_ota: job, fw, size, off, hub_seen, slot (u32), state (u8: 0 download, 1 installed, 2 health_timeout)
  bool load(Record&); Status save(const Record&); Status save_off(uint32_t); Status save_state(RecState); Status clear();
};
class Host {    // fr_core: Net::send_ota, the TCP session's hub endpoint, BYE ota + restart
  Status send(uint8_t kind, std::span<const uint8_t> body, bool ack_req);
  bool endpoint(Endpoint&);
  void restart();
};
class Ota {     // owned by fr_core; driven on the core task, heavy work posted to fr_worker
  bool bind(const Deps&);   // core, worker, flash, fetch, store, host, ident, fault_health, health_deadline_ms
  void on_boot();           // boot step 2: PENDING_VERIFY handling, deadline, rollback report
  void on_frame(uint8_t kind, std::span<const uint8_t> body, net::OtaReply& reply);   // OFFER, COMMIT, ABORT
  void health_set(uint32_t bits);   // kHealthCore | kHealthCaps | kHealthNet | kHealthHubAck
  bool busy() const;                // HEARTBEAT ota_busy
  bool pending_verify() const;      // HELLO ota_state
};
}
```

- **Threads.** `Ota` runs on the core task. Everything that blocks or writes flash (HTTP, the slot, otadata, `nvs:fr_ota`) runs on `fr_worker` (one task, priority 5, 6 KB stack, a queue of 8; `FakeWorker` in host tests), one download step per worker job; when the queue is full the step runs inline rather than stall. Results come back through a mailbox of atomics the core task reads when the worker pokes it (`Core::post`) and at the latest at Ota's own 1 s tick, so a lost poke only delays. Ota's tick and health deadline share one Core timer: the 28-timer pool is now 4 runtime + 1 spare + 23 for services.
- **Frames** (05 §5.7, port 240, cls OTA; `Net` routes cls OTA to `Host::ota_frame`, `fr_core` forwards to `Ota`): hub → node `OFFER` (ACK_REQ), `COMMIT {job_id}`, `ABORT {job_id}`; node → hub `ACCEPT {job_id, code: 0 fresh | 1 resumed}`, `REJECT {job_id, code}`, `STATUS {job_id, state: 1 downloading | 2 staged | 3 rebooting, bytes}` (every ≥ 5 % or 1 s while downloading, once per later phase; the last before BYE `ota` is state 3 with bytes = size), `RESULT {job_id, outcome: 0 success | 1 failed | 2 rolled_back, fw_id_prefix, reason}` (failed: 1 download (HTTP failed after the re-issues), 2 digest, 3 flash; rolled_back: 1 health_timeout, 2 crash, 3 unknown). An OFFER that the OFFER alone decides (a REJECT, an ACCEPT again for a re-sent OFFER of the running job) is answered through Net's `OtaReply`, which Net caches so a DUP OFFER gets the same answer; otherwise ACCEPT/REJECT goes out with `Host::send` once the first 400 bytes are read. ACCEPT, REJECT and STATUS carry no ACK_REQ; RESULT does (Q1: the hub ACKs it). `Net::send_ota` uses TCP, else serial (also while the TCP session is silent, 05 §5.10), never UDP; an OFFER that came over serial is answered over serial. An ABORTed attempt gets no ACCEPT, REJECT or RESULT. An OFFER with an empty `job_id` or an undecodable body gets no answer.
- **CHECK** (06 §6.6) before the first flash write; REJECT codes: `1 busy` (a job running, or an ABORTed one still winding down; the app is PENDING_VERIFY; no TCP session to download over; a full `fr_worker` queue; a rollback or mark-valid in flight), `2 chip` (chip id and revision from image header bytes 12/15/17, IDF's max-revision rule), `3 identity` (board/profile/part_profile ≠ `fr_ident`, unless FORCE), `4 size`, `5 same_fw` (fw_id = running or = last invalid, unless FORCE), `6 downgrade` (the image's own `esp_app_desc_t.version` at offset 48 against the running one, leading semver only; a non-semver label never counts; ALLOW_DOWNGRADE lifts it), `7 bad_image` (fw_id ≠ 32 bytes, size < 400, `hash_appended` ≠ 1, no esp_app_desc or `fr_app_desc` magic). size and same_fw are decided from the OFFER; bad_image, chip, identity and downgrade from the image's first 400 bytes.
- **URL:** `http://<hub_ip of the current TCP session>:7422/ota/<lowercase hex fw_id>.bin` (the IP the TCP link is connected to, not a fresh mDNS lookup).
- **Download:** `fr::ota::HttpGet` (`src/http/`, one source for lwIP and POSIX; `EspFetch` is a logging wrapper, and fr_net_node's fetch wraps it too): HTTP/1.1 GET to a dotted IPv4 with `Connection: close` and `Range: bytes=N-`; a 206 must carry a Content-Range that starts at the offset asked for, a 200 to a Range request is skipped up to it; the body is Content-Length long or runs to the close; chunked encoding is refused; `kHttpTimeoutMs` (10 s) bounds the non-blocking connect and every send and receive. Whole 4 KB chunks to flash; a failed read or connect re-issues `Range: bytes=<received>-`, at most 5 times per job; `off` (a whole 4 KB multiple) is saved every 64 KB, and only after those bytes are in flash. An OFFER of the same fw, size and slot with a whole-sector `off` and a record still in the download state resumes through `esp_ota_resume` (after a reboot, or a hub retry in the same boot); CHECK runs again on the descriptor read back from the slot.
- **VERIFY:** `esp_ota_end` must validate the image and the partition's sha256 must equal the OFFER's `fw_id`, else `RESULT failed (2 digest)`.
- **Commit:** without DEFER_COMMIT → `state installed` saved, set boot partition, STATUS rebooting, BYE `ota` on every session, restart 250 ms later (RESULT comes after the reboot); with it → STATUS staged until COMMIT.
- **ABORT** (`checking` or `downloading`): the worker sees it at its next step and the job is `aborting` until then (it can sit in a 10 s read). A re-OFFER meanwhile, its own job_id's included, gets REJECT busy, and the aborted attempt sends nothing more: no deferred ACCEPT, no REJECT, no RESULT (whatever way the worker ended it). Two more cancel checks catch an ABORT that lands during the finish step: after VERIFY, before staging or installing (the resume offset stays), and in `install()` after saving `installed`, just before `set_boot` (the record goes back to `state download`, with `off` 0: the next attempt starts over). An ABORT while `esp_ota_set_boot_partition` itself runs is past the point of no return: the node sends STATUS rebooting and restarts into the image (pointing the boot partition back at the running slot would leave that image PENDING_VERIFY on the next boot). A staged job's ABORT drops it (the slot is never booted), also one that races the worker's staged end.
- **Health gate** (`on_boot`): a PENDING_VERIFY app gets a 60 s deadline. Bits: `CORE` and `CAPS` (fr_core's `run_ports`: boot complete, every bound capability's init succeeded), `NET` (link changes, plus a 250 ms poll while still required), `HUB_ACK` (a WELCOME that gives a link its session; required only if the installing job set `hub_seen`). All required bits → mark valid, HELLO `ota_state` switches to valid, then `RESULT success` once a WELCOME has arrived. Deadline → `state health_timeout` saved, then rollback and reboot. **Fault build:** `CONFIG_FR_TEST_FAULT_HEALTH=y` (or an image whose `fr_app_desc.fault` is 1) never sets `CAPS`; it logs `ota: fault build (health)`.
- **Rollback report:** on boot, rolled_back when the record's state is not download, the running fw is not the record's, and the last invalid partition's sha equals the record's fw (the state check avoids a false report when power was cut between saving `installed` and set_boot). `RESULT rolled_back {fw_id_prefix: the invalid image's, reason}` after the first WELCOME: 1 from `state health_timeout`, 2 when the reset reason was PANIC, INT_WDT, TASK_WDT or WDT, else 3. Each report is sent once, then the record is cleared: "sent" means `Net::send_ota` accepted it, so a RESULT lost with its TCP session leaves the hub to its own rules (§4).
- **Never** during PENDING_VERIFY: accept an OFFER (REJECT busy). If no rollback is possible (no other valid app), the image stays PENDING_VERIFY and REJECTs busy until a serial flash.
- **fr_core:** Ota is bound and `on_boot()` runs in `start()` as boot step 2, before the board takes its timers; the running fw_id comes from Ota's `RunningInfo` (the image is hashed once).

## 4. Hub

- **Listener 7422** (`packages/hub/src/ota/http.ts`): `node:http` bound to the node host (`0.0.0.0`; `--node-host`) and `--node-http-port` (default 7422; tests 0). `GET` and `HEAD /ota/<fw_id>.bin`: 404 unless a Wi-Fi child is OFFERED or DOWNLOADING that fw_id to the device whose live TCP session (`router.tcpAddress`) comes from the request's source IP; one range (`bytes=a-`, `a-b`, `-n`) answers 206 with Content-Range, a range outside the image or several ranges 416; the app blob streams from the artifact store; bytes served count as progress when exactly one child matches (else progress comes from STATUS only). `POST /node/v1/coredump/...` answers 501; every other path 404. A failed bind does not stop the hub: the `listening` line carries `node_http_error`, `hub_status` warns, Wi-Fi children fail `no_http_listener` (not retried).
- **Orchestrator** (`packages/hub/src/ota/orchestrator.ts`): ota_deploy starts a parent job (kind `ota`, no lock) and one child job (kind `ota`) per device. A Wi-Fi child holds `device:<id>` for its whole run. States `QUEUED → OFFERED (ACCEPT ≤ 10 s) → DOWNLOADING (no progress 15 s: stalled) → [STAGED] → REBOOTING (back online ≤ 60 s) → VERIFYING (RESULT success ≤ 70 s) → SUCCEEDED`; terminal `FAILED(code)`, `ROLLED_BACK {reason}`, `TIMED_OUT {code, needs_serial_recovery}`, `CANCELLED`.
  - **Retries:** an attempt that fails retryably publishes `QUEUED {code, message, attempt}` and the next attempt starts after 5/15/45 s (3 retries); `FAILED` is published only when final. A REJECT is final except `busy`. After an ACCEPT timeout, a stall or a cancel the hub sends ABORT. A REJECT busy that answers the next OFFER, the first one after that ABORT, does not count: the node is still ending the aborted attempt (§3), so the same attempt goes again after the same wait (`QUEUED {code: busy}` says so in `message`), once per ABORT.
  - **Stall:** the deadline restarts whenever the node's STATUS bytes grow (DOWNLOADING or STAGED) and on every chunk 7422 serves it, bytes served again after a Range re-issue included (the socket's flow control paces the stream to the node). `bytes` keeps the most, for display and events. A stream left from an earlier attempt feeds nothing into the next.
  - **Did the node install it?** Only the node's own word counts: STATUS rebooting or BYE `ota` (REBOOTING), or every byte in its STATUS (a device that then goes away is treated as rebooting). What 7422 served says nothing here: it runs ahead of the node by the socket buffers between them (100 KB and more), so a power cut late in a download would otherwise look like a reboot. A device that goes away mid-download is `FAILED device_offline` (retried; the next OFFER resumes). A retry that finds the device already on the target fw_id (its last STATUS and BYE lost) goes straight to VERIFYING instead of offering the image again, but only when an earlier attempt reached DOWNLOADING, STAGED or REBOOTING, or the device was not on the target when planned: a forced reinstall of the running image offers it again.
  - **VERIFYING:** `device.online` with the new fw_id carries HELLO `ota_state`; `pending_verify` waits for RESULT success (≤ 70 s; a RESULT success that arrives before device.online is kept), `valid` is confirmed at once. Offline again in VERIFYING replaces the deadline with 60 s to come back: missing it is `TIMED_OUT not_back_online` (`needs_serial_recovery`); a confirm timeout while online is `TIMED_OUT not_confirmed` (no recovery needed).
  - **Rollback:** RESULT rolled_back in OFFERED, DOWNLOADING, STAGED, REBOOTING or VERIFYING ends the job at once with its reason; so does one for a Wi-Fi child waiting out its retry backoff (it wakes the backoff: ROLLED_BACK instead of another OFFER, which would only get REJECT same_fw). Back on another fw_id after it installed the image (REBOOTING after STATUS rebooting or BYE `ota`, or VERIFYING) waits 5 s for that RESULT, else `ROLLED_BACK unknown`; back on another fw_id when it never said it installed is `FAILED device_offline` (retried).
  - **STATUS** phase 3 enters REBOOTING without waiting for the BYE; phase 2 enters STAGED with the stall deadline still running (no DEFER_COMMIT in M1, so a node stuck there is ABORTed and retried).
  - **Cancel** (job_cancel, a parent's cancel, hub stop): ABORT to a node in OFFERED, DOWNLOADING or STAGED, then CANCELLED. A node that reported every byte may be setting its boot partition, past its last cancel check (§3): the child waits `abortGraceMs` (3 s) for STATUS rebooting or BYE `ota`, and with one follows that boot as usual (REBOOTING, VERIFYING, SUCCEEDED: the cancel came too late, and the jobs say what happened); else CANCELLED. A serial child cancels its flash job, also one that flash_start returns after the cancel.
  - **Serial** (`via serial`, and `auto` when the hub holds the device's USB port open; never a fault build: `auto` picks Wi-Fi for it, a named one with `via serial` makes the op INVALID_ARGS, and one a profile gets through `builds` skips that device with `fault_needs_wifi`, since a serially flashed image is never PENDING_VERIFY): the child takes no lock itself, because its `flash_start {plan: app}` job takes `port:<id>` and `device:<id>`; states QUEUED → DOWNLOADING (the flash job) → REBOOTING (new fw_id online ≤ 60 s) → SUCCEEDED or TIMED_OUT; no RESULT (a serial image is not PENDING_VERIFY, so a reset in that window is harmless).
  - **Records:** every transition is persisted in `ota_jobs` (db.ts; `json` the record ota_status answers) and the child job's stage, and published as `ota.job.state {job, parent, state, via, attempt, bytes, size, code?, message?, reason?, needs_serial_recovery?}` (`message` with `code` on FAILED and QUEUED; `deploy` shows it as the device's error) (DOWNLOADING also every 10 %). A hub start marks rows a stopped hub left unfinished `FAILED hub_restarted`. A Wi-Fi SUCCEEDED records the full fw_id, profile and board in the registry (`markImageFlashed`).
- **Router:** OTA frames over UDP or off port 240 are dropped (`ota_dropped`); OTA frames with ACK_REQ are ACKed (duplicates too). `sendOta`, like commands, PINGs, ACKs and the `get_state` and TIME resyncs, uses TCP, else serial, and serial while nothing came over TCP or UDP from a device that has both for more than 2 heartbeat intervals (`wifiSilentX10` 20; each session keeps its `lastRx`, and the node's UDP counts for its TCP session), back to TCP as soon as Wi-Fi carries. Presence counts frames from any link, and the node sends its heartbeats on every session, so a USB node whose Wi-Fi stalls stays online through its USB line (05 §5.10). `info().links` lists the links best first; `udp_blocked` is not raised while TCP is silent too (no firewall). HELLO `ota_state` is in `HelloSeen`, `device_get`'s `router.ota_state` and `device.online` fields; RESULT success for the running image's prefix sets it `valid` (the node HELLOs only on a new session).
- **Ops** (`packages/protocol/src/ops/ota.ts`, handlers `packages/hub/src/ota/ops.ts` and `deploy.ts`):
  - `ota_deploy {selector, build?, profile?, via: auto|serial|wifi = auto, max_parallel = 4, on_failure: halt|continue = continue, force?, allow_downgrade?, dry_run?, wait_s}`. Artifact: `build`, else the newest debug artifact of each device's registry profile (or `profile`); never a fault build implicitly. `auto`: serial if the device's USB port is open, else Wi-Fi (Wi-Fi for a fault build). `already_current` when the device runs that fw_id (HELLO prefix or registry, ≥ 16 hex; unless force). Devices that cannot be updated (`no_profile`, `no_artifact`, `target_mismatch`, `not_attached` for serial) are skipped and count as FAILED with `skipped: true`; when every device is skipped the op throws the first one's error, and an unknown named build fails the op. The dry run answers each device's action, transport, build, warnings and locks. The parent result is `{job, devices, counts}`; if any device did not update, the job fails with `OTA_ROLLED_BACK` when every failure is a rollback, else `OTA_FAILED`, the same result in `details`, and a `flash_start` remediation for devices that need serial recovery. `on_failure: halt` stops new devices before the failing child frees its slot (they end `CANCELLED halted`). CLI `fr ota <selector> [--build|--profile] [--via] …`.
  - `ota_status {job?|selector?}` → by job (parent: its children plus the parent's rows for devices that got no child; child: itself), by selector (each device's newest), or the newest 50; rows carry `timings_ms {offer, download, reboot, verify, total}`. CLI `fr ota status [selector] [--job J]`.
  - `deploy {selector, source_dir, build_type = debug, via = auto, fault?: health, expect_log? | expect_event?, expect_timeout_s = 30 (≤ 110), dry_run?, wait_s}` (no `profile`: it builds per registry profile). One parent job of kind `deploy` (no lock); per profile, in parallel: `build_start` (with `fault`), then devices already on the new fw_id are `already_current` and not handed over, the rest go to one `ota_deploy` per profile (`id:a,id:b`, that build, `via`). Each device is followed through `ota.job.state` (matched on `parent`), then `wait_for_device` (≤ 60 s) on the new fw_id, then `expect_log` (substring) or `expect_event` since the device last went down (the latest of REBOOTING over Wi-Fi, the start of a serial DOWNLOADING, the first ROM boot banner on its USB log, or device.offline unless a banner already marked that reboot). `expect_log` needs every device that would be updated (one with a profile) on a USB port the hub holds open (not closed, leased or held by another program), the only source of its log lines: a node on Wi-Fi alone sends no LOG frames in M1. Otherwise the op is INVALID_ARGS before any job starts, a dry run too, naming each device and its port state (`details.no_log_source`), with an `expect_event` (e.g. `node.boot`) deploy as the remediation that keeps build_type, via and fault. (Later: once nodes send LOG frames over TCP, the router can feed them to the log store and this rule can relax; today fr_net sends none, so the router has nothing to ingest.) A fault deploy goes over Wi-Fi only (`via serial` is INVALID_ARGS: a serial image never rolls back) and expects `rolled_back`. Result `{source_dir, build_type, fault?, via, builds[], results[], summary, duration_ms}`, a row per device `{device, alias, profile, build_id, fw_id, via, outcome: updated|already_current|rolled_back|failed, state, code?, reason?, needs_serial_recovery?, duration_ms, expect: matched|timeout|skipped, since?, ota_job?, error?}` (`needs_serial_recovery` with `TIMED_OUT not_back_online`, the row error ending "it needs a serial flash"). The job completes only when every device ends as asked and every expectation matched; else it fails with `BUILD_FAILED` only when nothing but builds went wrong. Otherwise the devices that did build decide: `OTA_FAILED` (a device failed, or a fault build was kept), `OTA_ROLLED_BACK` (a normal build rolled back) or `TIMEOUT` (only expectations missed); the message also names the profiles that did not build and the devices that missed their expectation. The body is in `error.details`; the remediation has `job_logs` for each failed build, `ota_status` and `logs_read` for the first device that went wrong, and `flash_start {device, plan: app}` for every device that needs serial recovery. Cancelling it cancels the build and OTA jobs it started. CLI `fr deploy <selector> [--build-type] [--via] [--fault health] [--expect-log PAT | --expect-event TYPE] [--expect-timeout S] [--dry-run]`.
  - `wait_for_device` gains `ota_state` (with `state: online`: the HELLO ota_state, valid once RESULT success arrived).
  - `hub_status` gains `ota {http_port, listen_error, active}` and a warning while 7422 is not bound.
- **Fault builds** (03 §3.8): `build_start {fault: 'health'}` (debug only; release is INVALID_ARGS). `fr gen firmware --fault health` writes `<build>/fr_gen/sdkconfig.fault` (`CONFIG_FR_TEST_FAULT_HEALTH=y`, Kconfig in fr_ota, depends on `FR_TEST_HOOKS`) after the build-type layer and before `sdkconfig.local`, and removes a stale one without `--fault`; both staleness hashes include it. The build goes into `<profile>-debug-fault`, build_id `node/<profile>/debug-fault/<fw12>`; the manifest keeps `build_type: debug` and gains `fault: "health"`; the `artifacts.fault` column keeps fault builds out of every newest-artifact pick (flash, provision, OTA, deploy). `fr artifacts ls` is a table (BUILD, BUILT, SOURCE) with fault builds after all normal ones, marked in a FAULT column with a footnote (they never pass their health check, roll back after an OTA, and are used only when named with `--build`); an empty store prints a `fr build` hint.
- **Version label** (spec 06 §6.8): the manifest `version` is the image's own version without a trailing `-dirty`, plus `-dirty.<fw_id[0:8]>` when the tree is dirty at ingest (the tree's git state decides, not IDF's configure-time describe), else plain.
- **SleepGuard** holds while a node session is up or any OTA child is not finalized (`OtaService.active()`).
- **Errors:** `OTA_FAILED`, `OTA_ROLLED_BACK` (CLI exit 8); job kinds `ota`, `deploy`.
- **Image size:** the pull is `HttpGet` over lwIP sockets, so esp_http_client, http_parser, tcp_transport and esp-tls leave the component list, and `CONFIG_ESP_HTTP_CLIENT_ENABLE_HTTPS` leaves `sdkconfig.framework`. mbedTLS stays (wpa_supplicant needs it); its SSL and x509 members are still loaded for wpa_supplicant's `tls_mbedtls.c` but every section of them is garbage-collected (0 bytes in the map's memory map). `HttpGet` itself is about 5 KB of flash, plus a 512 B response-head buffer in .bss; a GET allocates no heap. Debug images, of the 1,966,080 B slot: c6-pad 1,317,984 → 1,204,448 B (67.0 % → 61.3 %), c6-pad-mono 1,294,224 → 1,180,688 B (65.8 % → 60.1 %), c3o-pad 1,196,976 → 1,083,680 B (60.9 % → 55.1 %): about 111 KB less each, more than the 97 KB the HTTP stack alone took, because some libc stdio and PSA crypto code drops out with it. C4 now costs about 32–35 KB per image over C3 (c6-pad 59.5 % → 61.3 %, c3o-pad 53.5 % → 55.1 %, c6-pad-mono 58.3 % → 60.1 %).

## 8. Decisions to fold into the spec

1. `fr_app_desc_t` layout (112 B with `reserved2[19]`, magic `FRAD`, version 1), defined `extern "C"` in fr_core's C++, at image offset 288; the ingest check (magic and every field, `BUILD_FAILED`); manifest `app_desc` (raw `fault` byte) and `fault`.
2. REJECT codes 1–7 with what `busy` and `bad_image` cover, and the version rule (the image's own esp_app_desc version, leading semver only).
3. The OTA URL uses the IP of the node's TCP session.
4. OFFER is answered by an ACCEPT/REJECT OTA frame (not RESULT), cached by Net for a DUP OFFER; OTA frames never ride UDP; ACCEPT/REJECT/STATUS without ACK_REQ, RESULT with it (the hub ACKs); `OTA.COMMIT` and `OTA.ABORT` carry `job_id`; an ABORTed attempt gets no ACCEPT, REJECT or RESULT, and a re-OFFER while it winds down gets REJECT busy; cancel checks after VERIFY and before set_boot; an ABORT during set_boot is past the point of no return (STATUS rebooting follows); an OFFER that came over serial is answered over serial.
5. Wire values: ACCEPT code 0 fresh / 1 resumed; STATUS state 1 downloading / 2 staged / 3 rebooting; RESULT failed reasons 1 download / 2 digest / 3 flash; rollback reasons 1 health_timeout / 2 crash / 3 unknown, reported once after the first WELCOME ("once" = handed to Net).
6. `nvs:fr_ota` keys `job, fw, size, off, hub_seen, slot, state` and the rollback-detection rule (state ≠ download, running ≠ fw, last invalid = fw); range re-issues per job; `off` saved after the bytes are flashed.
7. `fr_ota` interfaces as §3 (Flash read/mark_valid/rollback, Store, Host, `Ota::bind`), `fr_worker` (priority 5, 6 KB, queue 8; inline step when full), Ota's timer from the Core pool (4 runtime + 1 spare + 23), HELLO `ota_state` valid after mark-valid.
8. Hub job semantics: QUEUED with the code between attempts; a busy REJECT right after the hub's own ABORT is not counted (once per ABORT); the stall rule (node STATUS growth, or any chunk 7422 serves); the node's word decides "installed" (never bytes served); a retry that finds the image installed confirms it, unless no earlier attempt reached DOWNLOADING and the device ran the target when planned (a forced reinstall); RESULT rolled_back ends the job in OFFERED and between attempts; a cancel with every byte at the node waits `abortGraceMs` for its word that it installed anyway; ROLLED_BACK rules and the 5 s reason grace with `unknown`; back on the old image without having installed it is a retryable FAILED; the VERIFYING offline rule and `TIMED_OUT not_back_online | not_confirmed`; STATUS phase handling; the serial child's lock rule; skipped devices; `ota_jobs` and `FAILED hub_restarted`; the parent result and its error codes.
9. Listener 7422: GET and HEAD, single range, 416, 404 gate by OFFER and source IP, 501 for the coredump route (crash reports deferred), a failed bind keeps the hub up (`node_http_error`, `hub_status` warning, `no_http_listener`).
10. `ota_deploy` / `ota_status` / `deploy` parameters and results as §4 (`already_current`; `auto` transport rule; `expect_timeout_s`; expect_log and expect_event exclusive; expect_log only for devices on a USB port the hub holds open (INVALID_ARGS with an `expect_event` remediation otherwise); fault builds over Wi-Fi only, for `ota_deploy` too (`auto` picks Wi-Fi, `via serial` INVALID_ARGS, `fault_needs_wifi` for a per-profile build); deploy's error code (`BUILD_FAILED` only when builds alone failed) and `needs_serial_recovery` rows with a `flash_start` remediation per device; "since the device came back"; deploy has no `--profile`, so 09 §9.5's CLI tree drops it), `wait_for_device {ota_state}`, `hub_status.ota`, the `*_timeout_s` → `--*-timeout` CLI flag rule.
11. Router: HELLO `ota_state` in device_get, `device.online` and `wait_for_device`; RESULT success makes it valid; `ota_dropped`.
12. Fault builds: `artifacts.fault`, build dir `<profile>-debug-fault` and build_id `node/<profile>/debug-fault/<fw12>` with `build_type: debug`, the layer order (after the build-type layer, before `sdkconfig.local`), written by `fr gen firmware --fault`.
13. Errors `OTA_FAILED`, `OTA_ROLLED_BACK` (exit 8); job kinds `ota`, `deploy`; `ota.job.state` fields.
14. The pull is `fr::ota::HttpGet` over BSD sockets, not esp_http_client (§3, §4 "Image size"): esp_http_client, http_parser, tcp_transport and esp-tls leave the image, and `CONFIG_ESP_HTTP_CLIENT_ENABLE_HTTPS` leaves `sdkconfig.framework`.
15. Already in the spec: a USB node's link rules (05 §5.10–5.11: HEARTBEAT and PONG on every session; both ends on serial while TCP is silent for more than 2 intervals; a serial request answered on serial; `device_get` links best first; no `udp_blocked` while TCP is silent), `net ip_block <s>` and `hooks.ip_block` (09 §9.7), the version label (06 §6.8). Still to fold: deploy's rules of item 10 into 09 §9.4–9.5, and `fr artifacts ls` (fault builds last, a FAULT column) into the CLI tree.
