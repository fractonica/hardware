# 04 — Boards: verified hardware facts, manifests, detection

Confidence: **H** = official document or schematic, or two or more independent sources. **M** = one good source plus a consistent secondary. **L** = community only; verify on the bench. Pin facts are cross-checked in [research/boards.md](../research/boards.md).

## 4.3 Board manifest (`hardware/boards/<id>.board.yaml`, schema `fractonica/board@1`)

A manifest holds hardware facts only. Which driver backs which capability is chosen in a profile ([03 §3.6](03-firmware.md)); the manifest's `defaults` give the out-of-the-box profile.

```yaml
schema: fractonica/board@1
id: esp32c6-supermini
name: ESP32-C6 Super Mini
idf_target: esp32c6
flash: { size: 4MB, mode: dio, part_profile: fr-4mb-v1 }
psram: null
usb: { kind: usb_serial_jtag, vid: 0x303A, pid: 0x1001, bcd_device: 0x0102, serial_is_mac: true, pins: [12, 13] }
console: usb_serial_jtag
buttons:
  boot: { gpio: 9, active_level: low, pull: external, strapping: true, deep_sleep_wake: false, confidence: H }
leds:
  rgb:    { gpio: 8,  kind: ws2812, color_order: GRB, count: 1, strapping: true, confidence: H }
  status: { gpio: 15, kind: gpio, active_level: high, strapping: true, confidence: M }
pins:
  reserved: { usb: [12, 13], flash: [24, 25, 26, 27, 28, 29, 30], not_bonded: [10, 11] }
  strapping: [4, 5, 8, 9, 15]
  strapping_levels: { 4: none, 5: none, 8: high, 9: high, 15: none }   # level each needs at reset (high|low|none)
  free: [0, 1, 2, 3, 14, 18, 19, 20, 21, 22, 23]
rf: { max_tx_power_qdbm: null }                              # TX cap in 0.25 dBm (8–84); null: driver default (4.6)
test_pin: 20                                                 # free GPIO for the T-LAT loopback rig (diag pin_pulse, 4.6); omit or null: none
resources: { rmt_tx: 2, ledc_timers: 4, ledc_channels: 6 }   # peripheral budget for validation
defaults:                                                    # default profile bindings
  boot:   { cap: fr.button, driver: button_gpio, bind: buttons.boot }
  status: { cap: fr.led,    driver: led_ws2812,  bind: leds.rgb }
detection:
  usb: { vid: 0x303A, pid: 0x1001, bcd_device: 0x0102 }
  esptool: { chip_type: '^ESP32-C6FH4 \(QFN32\)', flash_size: 4MB }
  probe: { leds: [rgb, status] }
sources:
  - https://documentation.espressif.com/esp32-c6_datasheet_en.pdf
  - https://mischianti.org/esp32-c6-supermini-high-resolution-pinout-datasheet-schema-and-specs/
```

The validator (`fr gen firmware`) enforces the following:
- No driver may claim a `reserved` pin (in particular the USB D−/D+ pins; touching them makes the board unflashable until BOOT+RST), and no pin is claimed twice.
- Any binding on a strapping pin produces a warning that names the level the pin needs at reset (`pins.strapping_levels`). That covers outputs, pull-down inputs and external loads.
- The peripheral budget (RMT channels, LEDC timers and channels, against `resources`) and `fr_core`'s pools (23 timers for services, 8 input slots; [03 §3.4](03-firmware.md)) are not exceeded.
- The driver supports the target and accepts the board entry's `kind` (an entry without `kind` is kind `gpio`); config keys and values are known and well-typed ([07 §7.8](07-capabilities-sdk.md)); instance names are snake_case, ≤ 31 characters and not reserved ([03 §3.6](03-firmware.md)).
- `test_pin` (since C6), when set, is in `pins.free`, not `reserved`, and claimed by no instance of the profile, since debug builds drive it ([4.6](#46-quirks-and-rules)); on a strapping pin it gets the strapping warning, and on a strapping pin that must be low at reset it is an error, since a test pin's line pulls it up (since M2-C1). A profile with `test_pin: none` drives no test pin, so its instances may use the board's.
- **Bare-pin binds** (since M2-C1, for the HIL fixture's lines): `bind: gpio.<n>` names a pin, not a board entry. It is valid only for a driver with `binds: gpio`, whose config field `from: bind` takes the pin (the profile cannot set it). The pin must be in `pins.free`; a strapping pin is an error, not a warning. An `fr.fixture` line that drives (`open_drain`, `nfet_gate`) is an error on a `pins.power_up_glitch` pin ([design m2-c1-hil](../design/m2-c1-hil.md) D11 item 7). Its `drive`, `decode` and `pull` must be ones its driver takes (`fixture_ws2812_rx`: `decode: ws2812`, `drive: none`, no pull; `fixture_gpio`: no `ws2812`, a pull only with `drive: none`).
- **Profile rules** (since M2-C1). At most 16 instances: fr_core's board instance table (`kMaxInstances`, `fr_core/include/fr/core.hpp`) leaves out the rest. A `role: fixture` profile needs `test_pin: none` and `net: {radio: off}`, and only a `role: fixture` profile may set `radio: off`: the hub knows a radio-off device by its HELLO role alone, and the build manifest does not carry `net`.
- **Driver `sdkconfig` lines** (since M2-C1): Kconfig lines a driver needs, rendered into `sdkconfig.board` of every profile that binds it. A `CONFIG_FR_*` symbol, a symbol listed twice, and two drivers setting one symbol to different values are errors. `fixture_gpio` lists `CONFIG_ESP_TIMER_SUPPORTS_ISR_DISPATCH_METHOD=y` and `CONFIG_ESP_TASK_WDT_PANIC=y`.
- **Header facts** (since M2-C1): each GPIO sits on at most one header position, and `en_access` names an `EN` position in `headers`.
- **ADC1 and the battery** (since M2-C3, [design m2-c3-inputs](../design/m2-c3-inputs.md) D3, D11): an `adc_oneshot` bind must be in the board's `pins.adc1` (never an ADC2 pin, so not GPIO5 on the C3) and not the `battery` pin, within `resources.adc1_channel`. An optional `battery: {gpio, divider, low_mv}` names the battery input; codegen renders it as `kBattery` for the vitals' HEARTBEAT `vbat_mv` ([05 §5.7](05-network.md)). Only `waveshare-esp32s3-lcd19` has one (§4.2).
- **Displays and touch** (since M2-C5, [design m2-c5-display](../design/m2-c5-display.md) D7, D9). A `displays.<name>` entry gives `kind`, the bus pins, `rst` and `backlight` (each may be `null`: none), `width`/`height` (native), `column_offset`/`row_offset`, an optional `rotation`, and two keys from the M2-C5 bench and review: **`backlight_active: high | low`** (default high; the LCD-1.9's is `low`), the level that lights the backlight, and **`idle_high: [gpio…]`**, chip selects of other devices on the panel's bus (the Touch-LCD-2's TF card CS 41) that the driver drives high before the bus comes up; they stay in `pins.reserved` and are claimed by no instance. A `touch.<name>` entry gives `kind`, `sda`, `scl`, `int`, `rst` and `address`. A driver may claim the pins its own board entry reserves (`pins.reserved.display`, `.touch`); an `fr.touch` instance's `display` config must name a port of the profile's `fr.display` instances.
- **A profile's `psram: on`** (since M2-C5, [design m2-c5-display](../design/m2-c5-display.md) D3; `s3l-pad`, `s3t-pad`): `CONFIG_SPIRAM` in the board's PSRAM mode (`CONFIG_SPIRAM_MODE_OCT` for octal) with `CONFIG_SPIRAM_USE_CAPS_ALLOC`, so only `heap_caps_malloc(MALLOC_CAP_SPIRAM)` reaches it (LVGL's pool and framebuffers) and nothing else moves out of internal RAM. Refused on a board with `psram: null`. Without it, or with `off`, nothing is rendered. A profile with an `fr.display` instance also gets `CONFIG_FR_CORE_TASK_STACK=16384` ([03 §3.4](03-firmware.md)).
- The HIL bench file (`hardware/bench/<name>.bench.yaml`) is checked against the manifests and profiles by `fr gen --check`, and `fr gen firmware` refuses a profile that a failing bench names ([10 §10.5](10-testing.md), T-HIL).
- All problems are reported together; warnings are returned alongside the result.

What `fr gen firmware` carries from the board and drivers (since C6):
- **`test_pin`** → `CONFIG_FR_TEST_PIN` in `sdkconfig.board` (Kconfig in `fr_core`, −1..48, default −1 = none) and `test_pin` in `fr_manifest.json` (null without one). Since M2-C1 the effective `test_pin` comes from the profile: `test_pin: none` emits no `CONFIG_FR_TEST_PIN` (it stays −1) and a null manifest `test_pin`, whatever the board has (`s3k-fixture`). The build ingest copies it into the artifact manifest (`ArtifactManifest.test_pin`, an integer 0..48 or null; absent for builds from before C6; [06 §6.8](06-identity-ota.md)). `board_list` reports it per board, and diag `info` reports the running image's (−1 without one; [09 §9.7](09-agent-api.md)).
- **Traits** → each cap instance's `traits` in `fr_manifest.json` (`ManifestCap.traits`: a record of bool, number or string; null or absent when unknown): the capability's defaults (or zero values), then the driver's `driver.yaml` `traits:` (`led_gpio {color: mono, dimmable: false}`, `led_ws2812 {color: rgb, dimmable: true}`), then what the service derives from its config (`fr.button`: `long_press`, `multi_press_max`) ([07 §7.8](07-capabilities-sdk.md)). The `/app` welcome, `capability_list` and the dashboard take traits from there (null: the dashboard shows every trait-gated member).
- **Profile `role` and `net.radio`** (since M2-C1) → `CONFIG_FR_ROLE` (the HELLO role: node 0, gateway 1, fixture 2; [05 §5.7](05-network.md)) and, for `radio: off`, `CONFIG_FR_NET_RADIO=n` (no Wi-Fi, no ESP-NOW: a serial-only node). Without them nothing is rendered.

**Bench facts in the manifest** (since M2-C1, [design m2-c1-hil](../design/m2-c1-hil.md) D5). The HIL bench validator and the fixture's pin plan read them. The fixture's manifest and the three DUT manifests carry them (`pins.power_up_glitch` the two S3 manifests only):
- `headers`: per header, pin 1 first, each entry a GPIO number or a pin name (`3V3`, `5V`, `GND`, `EN`); an optional `confidence` for the set (M on the C3 and C6 boards, from espboards.dev).
- `boot_uart_tx`: the UART TX the ROM log prints on at every boot (C3 21, C6 16, S3 43); the bench never wires it.
- `en_access`: where EN reaches a header, `<header>-<pin>` (the fixture J1-3, pad-s3 J6-11), or none (C3, C6).
- `pins.power_up_glitch`: the pins that drive a level for about 60 µs at chip power-up (S3 datasheet Table 2-2: GPIO1–20). No driving fixture line goes on one, so the fixture's BOOT lines sit on J3's glitch-free GPIO39–42.
- `resources.rmt_rx`: RMT RX channels for the budget (C3 2, C6 2, S3 4).

The PSRAM mode and voltage are to be checked against the device later, at provisioning, against what esptool reported ([06 §6.4](06-identity-ota.md); not done yet, [11 §11.4](11-roadmap.md)). The first PSRAM board, `waveshare-esp32s3-lcd19`, records `psram: {size: 8MB, mode: octal, voltage: 3.3V}`; its M1 profile left SPIRAM off. Since M2-C5 `s3l-pad` and `s3t-pad` turn it on (`psram: on`, above), so the check is now needed; it is still open ([11 §11.4](11-roadmap.md)). Both boards booted with it (the Touch-LCD-2: "Found 8MB PSRAM device", memory test OK). The fixture's `s3k-fixture` keeps it off.

## 4.4 USB-Serial/JTAG behaviour the hub must handle

| Event | Reset kind | USB device | Straps re-sampled |
|---|---|---|---|
| esptool USJ reset into the loader, `--after hard-reset`, or an RTS pulse from the hub | core reset; the USJ itself is not reset | stays enumerated (measured at checkpoint C1: C3 `rst:0x15 (USB_UART_CHIP_RESET)`, C6 `rst:0x15 (USB_UART_HPSYS)`; the port never closed) | no |
| Blank or erased flash: the ROM prints `invalid header: 0xffffffff` until its watchdog fires | C6: `rst:0x7 (TG0_WDT_HPSYS)` about every 0.7 s, ~270 lines per cycle | stays enumerated (C6, measured at C1) | no |
| `esp_restart()` (including the reboot after OTA) | CPU reset | stays enumerated (measured at checkpoint C2 on the C6: `rst:0xc (SW_CPU)`; the whole boot log is captured) | no |
| RST button, power-on, brownout, RTC watchdog | chip reset | re-enumerates | **yes** |
| Deep sleep | USJ powered down | disconnects; reconnects on wake | — |
| Firmware touches the USB pins or disables the USJ | — | disappears until BOOT+RST | — |

Rules:

- **Identity is the MAC** (USB serial number), never the `/dev/cu.usbmodemXXXX` path. On macOS the path comes from the USB location ID, so it changes when you move the board to another socket. The hub re-resolves paths on every hotplug.
- **Open ports with DTR and RTS deasserted.** On USJ, RTS drives a core reset. A careless open can reset a node, and that rolls back an image that is still pending verification ([06 §6.6](06-identity-ota.md)).
- **Always attach a reader.** USJ output blocks for 50 ms and is then dropped when no host reads it.
- **After macOS sleep** (observed once, at C2). Overnight, a C6 stopped producing output (no liveness log, no diag answers) while the hub still showed its port open, and one boot happened with no output captured. The Mac's power log shows a maintenance wake from sleep minutes later. A hub-side reset recovered it. The cause is not known and was not reproduced; the hub's open sequence was ruled out (serialport sets DTR and RTS with one `TIOCMSET`). Mitigation: the hub treats a poll tick more than 10 s late as a system resume and reopens every open port ([08 §8.3](08-hub.md)). Since checkpoint C3 the 1 s HEARTBEAT makes such silence visible within seconds: the hub takes the node offline after 3.5 s ([05 §5.11](05-network.md)).
- **The console is the native USJ** on every USJ-only board (`CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG=y`). As the secondary console it would be output-only, with no command input from agents. DevKitC-1 boards keep UART0 as their primary console.
- **One serial channel carries logs, machine frames and diag commands.** They are separated by line framing. The `fr_serial` task is the only reader and writer ([05 §5.12.3](05-network.md), [03 §3.4](03-firmware.md)).

## 4.5 Detection pipeline

| Stage | Opens the port? | What it does |
|---|---|---|
| A. Passive | no | Enumerate USB with VID, PID, bcdDevice, serial and location ID (IOKit / `system_profiler SPUSBHostDataType -json`; udev on Linux). `303A:1001` + 0x0101 means C3 or S3; 0x0102 means C6; CP210x or CH34x means an S3 DevKit UART port. A MAC already in the registry means done. |
| B. Self-report | no (reads the serial stream) | Framework firmware sends HELLO with `mac`, `chip`, `chip_rev` and `board_hash` (FNV-1a 32 of the board id, [05 §5.7](05-network.md)). The hub matches `board_hash` against known manifests and reads the board id from `fr.node.describe`, and flash size plus PSRAM size and mode from diag `info`. Done. |
| C. Active probe | yes (lease, resets the chip) | esptool 5.6: `esptool.cmds.detect_chip` and `detect_flash_size`, plus the `ESPLoader` methods `get_chip_description()`, `get_chip_features()` and `read_mac('BASE_MAC')`. Yields package, embedded flash/PSRAM, revision and flash size. esptool ≥ 5.2 is needed for C6 embedded-flash reporting. |
| D. Match | no | Match the results against every manifest's `detection` block: 0 candidates means ask, offering `generic-<target>`; 1 means done; more than 1 means stage E (M2) or asking the user (M1). |
| E. Disambiguate (M2) | yes | Flash the generic firmware, blink each candidate LED pin, and ask the user or agent which one lit (S3 Super Mini vs S3-Zero; DevKitC-1 v1.0 vs v1.1). |
| F. Persist | no | Store `board_id`, `confirmed_by` (`self-report`, `probe` or `user`) and the probe facts per MAC. |

**Two S3R8 boards on one bench** (since M2-C1). The HIL fixture (`esp32s3-devkitc1-n16r8`) and pad-s3 (`waveshare-esp32s3-lcd19`) match the same USB and esptool rules (S3R8 QFN56 v0.2, 16 MB, 8 MB PSRAM, bcdDevice 0x0101). So provisioning a new S3 passes `--profile`: with no `--profile` and no registry entry, a chip with several profiles' artifacts is refused with the candidates (`registry/provision.ts`). The registry remembers each device's profile afterwards. The fixture fence refuses a fixture build on any device but the bench's fixture, and any other profile on the fixture ([09 §9.2](09-agent-api.md)).

Since M2-C5 a third S3R8 is on the bench, pad-s3t (`waveshare-esp32s3-touch-lcd2`, the same chip, flash and PSRAM), so the same `--profile` rule applies to it (`s3t-pad`). Its manifest's I2C probe (CST816D at 0x15) would tell it from the LCD-1.9, but not on a non-touch unit like the bench's, where nothing answers there.

## 4.6 Quirks and rules

- **BOOT as the PoC input.** After reset, the BOOT pin is an ordinary input (internal pull-up, active-low).
  - **Holding it during a chip reset** (power-on, RST, brownout, RTC watchdog) boots ROM download mode. The node then vanishes from Wi-Fi, but its USB still enumerates.
  - Holding it during `esp_restart()` or an OTA reboot is safe.
  - The hub flags "USB present but no HELLO for 5 s" as a likely download-mode state and shows a recovery hint (release BOOT, tap RST; or `esptool --after watchdog-reset` on C3/S3).
  - **GPIO9 cannot wake the C3/C6 from deep sleep.** Battery input devices need another pin (C3: GPIO0–5; C6: GPIO0–7).
- **`test_pin`: the T-LAT loopback output** (since C6; [05 §5.18](05-network.md)). One free GPIO per board, from the manifest (validated as in §4.3): `esp32c3-oled042` GPIO10, `esp32c6-supermini` GPIO20, `waveshare-esp32s3-lcd19` GPIO16 (wired to the HIL fixture since M2-C1); the fixture board (`test_pin: null`) and other boards have none.
  - **Open-drain, never pushed high.** Debug builds (`FR_TEST_HOOKS`) release it before making it an output and keep it released at idle (high-Z, no internal pull); it is low only during diag `pin_pulse <us 10..100000>` ([09 §9.7](09-agent-api.md)), whose own one-shot `esp_timer` releases it. The high comes from what the line reaches: the other board's BOOT pull-up on the M1 rig, the fixture's internal pull-up on the HIL bench (about 45 kΩ, inferred). Why: the rig wires it to another board's BOOT pin, a strapping pin that must read high whenever that board resets (so it is never low outside a pulse, boot included), and a pushed high would short a pressed BOOT button. Release builds never touch it. `pin_pulse` answers `busy` while a pulse runs, `unsupported` without a `test_pin`.
  - **The M1 rig (C6 to M1; retired at M2-C1).** A's `test_pin` → B's BOOT (GPIO9), plus a **GND jumper** between the boards. The bench pair wired both directions: pad-c6 GPIO20 → pad-c3b GPIO9 and pad-c3b GPIO10 → pad-c6 GPIO9. Since the pins idle released, wiring live boards is safe: GND first; remove the signal lines first and GND last, before unplugging either board; a 1 kΩ series resistor per signal line is optional. B's BOOT must read released at idle (`diag selftest boot`; the T-LAT harness checks it).
  - **On the HIL bench** (since M2-C1, [design m2-c1-hil](../design/m2-c1-hil.md) D10, §6). The two cross-jumpers and their GND jumper are off. Each DUT's `test_pin` goes through 1 kΩ to its own fixture input (`drive: none`, `pull: up`), so nothing is merged and `pin_pulse` samples are taken on all DUTs at once. A line low at idle means that DUT is unpowered or stuck (`bench_get` `line_low`, that DUT only). `t-lat.ts` is skipped while the bench file wires these pins. T-LAT moves to the fixture at M2-C8 ([design m2-c1-hil](../design/m2-c1-hil.md) §7 item 4); its new method and pass text for [05 §5.18](05-network.md) and [10 §10.5](10-testing.md) wait for your approval ([11 §11.6](11-roadmap.md) M2-C8). In M2-C1's passing T-HIL runs the four lines gave `pin_pulse 1000` widths p50 1,038–1,102 µs (p99 ≤ 1,197 µs) in run 3 and p50 1,037–1,224 µs (p99 ≤ 1,802 µs) in run 4, all within the p90 1,000 ± 500 µs gate, and none went low across a reboot ([11 §11.6](11-roadmap.md)).
- **Weak C3 RF.** The TX cap is the manifest field `rf.max_tx_power_qdbm` (0.25 dBm units, 8–84). `fr gen firmware` writes it into `sdkconfig.board` as `CONFIG_FR_WIFI_MAX_TX_POWER_QDBM`, and `fr_net` calls `esp_wifi_set_max_tx_power()` right after `esp_wifi_start()` (the driver refuses it earlier). Heartbeats report RSSI and TX failures so the cap can be tuned ([05 §5.7](05-network.md)).
  - **C3 OLED board #2** (`1cdbd4175cc4`) never finished WPA2 authentication at full TX power (measured at checkpoint C3): the driver looped `init → auth → init (0x200)`, and the AP never answered. Capped at 34 (8.5 dBm), it associated on the first attempt. Board #1 (`1cdbd416ba34`) joined at full power in C1, so this is per-board RF spread, not something every unit of the board shows. 34 is now the `esp32c3-oled042` manifest default ([spike](../spikes/2026-10-21-c3-hub-link.md)).
  - **Marginal at the cap** (measured at checkpoints C4 and C6). At 8.5 dBm the C3 OLED boards' link follows where they sit more than anything in the firmware. The RSSI they heard from the router ran from −65 to −81 dBm across positions (the C6 nearby: −62 to −66). At −65 and −70 the link was stable; at −76 to −78 OTAs were slower and, on a USB charger, sessions flapped and four OTA attempts were lost; at −81 pings were 100 % lost and sessions died every ~8 s. So below about −75 dBm these boards are marginal. The C6 gates saw the same: at −74 to −78 dBm (TCP flapping, about 8 % UDP retransmission) T-INPUT got late and lost events and one T-LAT run failed; at −61 to −67 dBm both passed ([spike](../spikes/2026-10-23-c6-apps-agents.md)). The cause is not settled: the cap is what lets board #2 associate at all, and whether a different cap (for example 11–13 dBm) does better on these boards is a question for spike S2 ([11 §11.2](11-roadmap.md); [spike](../spikes/2026-10-22-c4-ota.md)).
  - **Other caps** (spike S2 (a), M2-C4, [spike note](../spikes/2026-10-27-m2-c4-s2-gateway.md)): both C3s at 34, 44 and 52 qdBm (8.5, 11, 13 dBm) where the fixture's jumpers hold them (AP RSSI −66…−73 dBm): 0 % PING loss, 1,000/1,000 ESP-NOW unicasts to the gateway and no TCP close at every cap. Nothing gained, so 34 stays. Not measured: a spot near −75 dBm, where the cap matters.
- **C3 ADC noise with Wi-Fi on** (measured at M2-C3, T-ANALOG; [design m2-c3-inputs](../design/m2-c3-inputs.md) D3). On `esp32c3-oled042` ADC1 GPIO3 at 12 dB with curve fitting, one conversion at a steady 1,200 mV spread over about 25 mV on pad-c3 and about 60 mV on pad-c3b (p10–p90 1,189–1,203 and 1,176–1,223 mV over 60 reads), more than `fr.analog_in`'s default deadband (19.5 mV) and hysteresis band (39 mV). `adc_oneshot` therefore averages 8 conversions per reading: p10–p90 1,194–1,203 and 1,196–1,206 mV after. The C3's calibration logs `raw 4095 = 2915 mV`; the `full_scale_mv` trait stays 2,500 ([07 §7.3](07-capabilities-sdk.md)).
- **Internal RAM on the S3 display profiles** (measured at M2-C5, T-DISPLAY 3; [design m2-c5-display](../design/m2-c5-display.md) D3). With LVGL's 64 KB pool and the framebuffers in PSRAM, internal free heap was 30,436 B on pad-s3 (`s3l-pad`) and 26,696 B on pad-s3t (`s3t-pad`), against 36,684 B on pad-c3b (`c3o-pad`, with the OLED); LVGL's pool reached 7,108 / 7,136 B. So about 27–30 KB of internal headroom is left on the S3 display profiles: what goes there next (draw buffers, task stacks, Wi-Fi) needs measuring. HEARTBEAT `free_heap_kb` and diag `info` `heap` report internal RAM since M2-C5 ([05 §5.7](05-network.md)).
- **WS2812** draws about 0.6–1.5 mA even when dark (battery nodes). `led_ws2812` defaults `max_brightness` to 64 of 255.
- **S3 as a USB HID gamepad** (a likely future input-device mode). TinyUSB takes the shared PHY, so the native USJ console and agent channel are lost. Such nodes must be managed over Wi-Fi/ESP-NOW or through a UART bridge. C3 and C6 cannot be USB devices at all.
- **The HIL fixture board** (`esp32s3-devkitc1-n16r8`, since M2-C1): an ESP32-S3-DevKitC-1-style board with a WROOM-1-N16R8 (S3R8: octal PSRAM, so GPIO35–37 are unusable), device `e8f60a81bc48`, alias `fix-s3`, profile `s3k-fixture`, on its native USB port only ([design m2-c1-hil](../design/m2-c1-hil.md) D2, §2.2).
  - **The RGB LED pin depends on the version:** GPIO48 on DevKitC-1 v1.0, GPIO38 on v1.1 (Espressif user guides); clones vary. This unit's is on GPIO48: its identify blink (3 blinks at each fixture WELCOME) was seen at the bench step. GPIO38 stays reserved (`rgb_alt`), so no fixture line binds it.
  - **The power-up glitch rule.** At chip power-up GPIO1–20 glitch for about 60 µs: 1–17 low; 18 and 19 low and high; 20 pulled down, then high; 19 and 20 have two highs each, over 3.2 ms and 2 ms (S3 datasheet Table 2-2, as the `esp32s3-devkitc1-n16r8` manifest's `pins.power_up_glitch` comment cites it; §4.3). A direct BOOT line fears the low glitch (a 60 µs press, download mode if a DUT samples its straps then), an `nfet_gate` line the high one. Only J3's GPIO21, 38–42, 47 and 48 have neither, so the four BOOT lines sit on GPIO39–42 and the reserved pad-s3 EN line on 21. Input taps may sit on glitch pins; the bench validator allows the ones that reach a DUT's GPIO8 strap only as a documented exception, printed as a note.
  - **Never wired:** the straps 0, 3, 45, 46; USB 19/20; UART0 43/44 (the ROM log, to the COM bridge); GPIO48 and 38; EN. The COM port stays unplugged (inferred: its auto-program circuit can pulse EN and GPIO0).
  - **Power order** (direct BOOT wiring). An unpowered fixture clamps each DUT's BOOT toward 0.6 V through its pin protection diodes (inferred), and a DUT chip reset then latches download mode. The fixture is powered first and unplugged last. After any fixture power loss (on the desk hub: a hub power cut or replug, a Mac reboot, a sleep that cuts its ports), `fr bench` runs before anyone touches a DUT.
- **DevKitC-1** exposes two serial ports for one chip. Deduplicate them by `read_mac`: the bridge's serial number is not the chip MAC.
- **MAC normalisation.** The USB serial is uppercase with colons. esptool prints lowercase, and on the C6 it also prints an EUI-64 `MAC` alongside the 48-bit `BASE MAC`. The registry key is 12 lowercase hex digits of the base MAC.
