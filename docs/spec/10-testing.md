## 10.2 Why not simulators as the primary gate

| Tool | Verdict |
|---|---|
| QEMU (IDF) | Supports esp32, C3 and S3; no Wi-Fi; **no C6**. Not useful for a radio-centric framework |
| esp-emulator (Espressif, beta v0.50, closed-source core) | Runs C3/C6/S3 with Wi-Fi STA, which can reach the host hub. But: no ESP-NOW; every instance defaults to the same MAC unless it gets its own eFuse file; the bridge is UART0-only; there are open S3-OTA and C6-USJ bugs. **Optional smoke tier** for Wi-Fi link and OTA flows, version-pinned |
| Wokwi | GPIO-level button and LED checks (`set-control` / `expect-pin`). Has a CI-minute quota and needs a paid private gateway to reach the hub. **Optional** |

The value of the framework is ESP-NOW flooding, node ↔ node behaviour and input latency. No simulator covers these. Our own core tests (T0, then T2 at scale) cover the logic, and real boards (T3/T4) cover the RF.

## 10.3 `fr_net` core on the host

- **Structure.** `fr_net` core (`src/core`, `Net`) has no IDF includes. Link drivers implement one envelope-level interface; the link adds and strips its own framing:
  ```cpp
  class Link {
   public:
    virtual LinkKind kind() const = 0;                            // serial, tcp, udp (espnow = 3: the AirLink below)
    virtual bool up() const = 0;                                  // TCP connected, USB host present, UDP bound
    virtual Status send(std::span<const uint8_t> envelope) = 0;   // never blocks the core task
    virtual void drop(DropReason) {}                              // session lost: TCP closes and reconnects
    virtual void hold(bool) {}                                    // drop_hub_link: no reconnect while held
   protected: ~Link() = default;
  };
  ```
  Received envelopes reach `Net::receive(LinkKind, envelope, at)` on the core task, `at` being the link task's `esp_timer` stamp at receipt (C6, [05 §5.12.4](05-network.md)); the two-argument overload, which stamps on the core task, stays for tests and core-task links. Time, timers and posting come from `fr::Core`, and dispatch and identity from `fr::net::Host` (implemented by `fr_core`).
- **ESP-NOW (C5)** has its own interface, since a send names a MAC and completes later:
  ```cpp
  class AirLink {                     // fr_net/src/esp/espnow.cpp; fakes in the host suite and fr_net_node
   public:
    virtual bool up() const = 0;      // started and channel C known
    virtual Status send(const Mac& dst, std::span<const uint8_t> env, AirPrio prio, uint32_t token) = 0;
    // busy only for a full queue or a peer table whose every slot was used within 1 s;
    // the completion comes back as Net::air_sent(token, mac_acked) on the core task
  };
  ```
  Received frames reach `Net::receive_air(envelope, RxMeta {src_mac, to_broadcast, rssi, channel})`. The directory and binding stores are interfaces too (`attach_stores`), so the core persists nothing itself.
- **M1 (T0).** `FakeLink` and `FakeCore` (fake clock and timers) give deterministic unit tests of every rule in [05 §5.8–5.11](05-network.md) (`firmware/test/host/tests/net_*.cpp`).
- **`fr_ota` (C4).** The same fakes plus `FakeWorker` and fake `Flash`, `Fetch`, `Store` and `Host` test the node rules of [06 §6.6](06-identity-ota.md) (`ota_check_test`, `ota_job_test`, `ota_boot_test`, and `ota_net_test` over the real `Net`): every REJECT code, CHECK on resume, Range re-issues and their exhaustion, resume offsets and the 64 KB cadence, VERIFY mismatch, flash errors, DEFER_COMMIT/COMMIT, STATUS cadence, lost pokes, inline steps on a full worker queue, the health gate (HUB_ACK only with `hub_seen`, a fault build never valid, deadline → rollback, mark-valid racing the deadline), reports sent once, and the ABORT races (a re-OFFER while aborting, ABORT after VERIFY, before and during `set_boot`, a staged end racing an ABORT). `ota_http_test` runs `HttpGet` against a scripted loopback server (206 and Range, a 200 skipped up to the offset, bodies to the close, short bodies, 404/416/500, a wrong or missing Content-Range, chunked, bad heads, timeouts, a refused connection).
- **Interop (C3).** `fr_net_node` (`firmware/test/host/tools`, built by `pnpm test:host`) runs the real `fr_net` core, button and LED services and descriptor builder over POSIX TCP/UDP. `packages/hub/test/interop.test.ts` runs it against the hub's router on loopback: handshake with `describe`, `udp_ok`, commands through the response cache, reboot → RESULT then BYE (also with a serial session and slow UDP), silence → suspect/offline, `udp_block` → `udp_blocked` with no false offline, `drop_hub_link` (no reconnect until it ends), a hub restart, a USB node whose Wi-Fi goes silent (both ways, or only its uplink: a request over USB answered over USB), and an unprovisioned node. The suite skips when the binary is absent.
- **OTA interop (C4).** `fr_net_node` also runs the real `fr_ota` core on an OTA fake (memory flash persisted in `--ota-dir`, the same `HttpGet` over POSIX sockets) and makes test images (`--make-image`) that the hub's own ingest parser registers. `packages/hub/test/interop-ota.test.ts` runs it against the real router, orchestrator and 7422 listener; a `CppBoard` power-cycles the process at each restart, and a pass-through proxy paces or cuts the body. It covers success (`pending_verify` → `valid` → RESULT success), a health-fault image rolled back with `health_timeout` (then REJECT `same_fw`), REJECT `identity` decided from the image's first bytes, a connection cut mid-body (a Range re-issue in the boot), a power cut mid-download (the retried OFFER ACCEPTed `resumed` from a 64 KB stride), and a USB node whose Wi-Fi stalls (`ip_block`).
- **ESP-NOW host tests (C5).** `net_air_window_test` (windows per source, epochs, the LRU and a new source's floor, the receive filter, LATEST, neighbour learning, the ESP-NOW heartbeat and its `wifi_up` note, the jitter seed, directory sets and RESOLVE answers, persistence), `net_window_test` (`raise_floor` never moves back), `net_flood_test` (every row of the [05 §5.9](05-network.md) pseudo-code: K by air copies only, hub copies never counting or re-seeding, a same-run WELCOME keeping the BCAST window, K = 1 and K = 0, TTL, jitter bounds, RSSI bias, a flooded unicast's target, gateway, `ota_busy`, the flood rate, the watermark), `net_air_send_test` (the fallback chain, a busy peer table, Q1 retries and their end, answers and their fallback, an answer overtaking the send completion, forwarded frames, MSG, a fast frame with no path answering BUSY), `net_bind_test` (fast, reliable `rtt_us`, self, broadcast MSG, MSG trigger, no hub, the loop guard, persistence, the 1,400 B table), `air_sched_test` (the guard hold, a late verdict releasing only the held send, the 1 s loss), `esp_sta_rules_test` (the three sweep cases, `Pins` across a trial, its revert and confirm, a channel change, a second `net_set`), `core_node_net_test` (fr.node `bind_*`, the NVS stores, MSG handlers).
- **Simulated medium (C5).** `net_air_medium.hpp` puts three real `Net`s on one air (carrier sense, airtime, MAC ACKs, link retries, seeded loss): 1,000 hub broadcasts with one node's hub link dropped (at 0.1 %, 1.5 % and 5 % loss: 1,000, 1,000 and 997 of 1,000 at the cut-off node, no duplicate delivery, 2.00 transmissions per broadcast), the bench case (1.5 % loss: 1,000/1,000, worst 999 over 20 seeds, ≈ 1 − PER²; the old K rule gave 983), T-FLOOD-B, T-NN and Q1 at 20 % and 40 % loss. It was the seed of the T2 medium below, and since M2-C2 stays unchanged as that medium's C5 regression ([design m2-c2](../design/m2-c2-t2-fleet.md) D23, approved).
- **Air interop (C5).** `fr_net_node --air-dir` joins a fake air medium (UDP on loopback: each node registers `<mac>.port`; broadcast = every registered port; unicast = the MAC's port, with an ACK datagram as the MAC ACK; `--air-loss`, `--air-seed`, `--air-ack-ms`). `interop-air.test.ts` (rig `air-rig.ts`, three C++ nodes and the router) covers T-NN with the hub running (binding pushed by `binding_set`, presses on path espnow, `rtt_us`, `latency_stats`; on a loaded host at least three quarters espnow and none failed) and stopped, node MSGs (to the hub, to every node once, via the hub when ESP-NOW cannot reach), short T-FLOOD and T-FLOOD-B, a back-to-back run of the hub's flood burst reaching the node with no hub link whole, T-FLOOD-B with the router off (USB node on TCP and serial, the others `wifi_down`; then its Wi-Fi gone without a FIN), and a DIRECTORY pushed on a registry change. `interop-air-scale.test.ts` runs T-FLOOD at bench length (1,000 broadcasts 100 ms apart) and T-FLOOD-B at 1 Hz, printing `[measured]` lines.
- **C6 node interop.** `fr_net_node` gains:
  - stdin `loss <pct> <s> [both|tx|rx]`;
  - `fr.diag` on port 241, answering `fr.diag.exec` lines over the hub link: `pin_pulse <us>`, `net loss …`, `net drop_hub_link|udp_block|ip_block <s>`, `stats` with the C6 counters, `info` (`wifi_down` stays stdin only);
  - `--pin-target <udp port>` (a pulse sends a datagram there) and `--pin-listen <udp port>` (a datagram presses `boot` through the real debounce, released after the pulse): two nodes wired like the T-LAT rig;
  - hub CMDs with `exec_at` run through the real scheduler.

  Suites: `interop-app` (the SDK on `/app` with C++ pads: inject order on 3 pads, the relay → `effect_done`, `msg:ping`), `interop-input` (5 % `loss`), `interop-tlat` (both probe modes on the pin-wired pair; on loopback primary p50 0.27–0.34 ms, SDK hop p50 0.33–0.41 ms), `interop-node-c6` (diag over the link, the T-LAT wire, `net loss`).
- **Real-hub interop (C6).** `packages/hub/test/real-hub.ts` starts the hub's own `src/main.ts` on port 0: `--node-host 127.0.0.1 --node-port 0 --node-http-port 0 --no-serial --no-advert`, a temporary `FR_HOME` and `TMPDIR`, devices written into `hub.db` first. `restart()` reuses the same ports; SIGTERM exits 0. `interop-hub.test.ts` runs against it:
  - the SDK on `/app` with C++ pads: T-INPUT `sim` in order, the relay never negative, `msg:ping` once per pad, `node.identify`, `loss 5 900` with every out-of-order event flagged and none falsely, convergence and forced resyncs, and a hub restart (the SDK back on the new run, `gap {lost: true}`);
  - `latency_probe`, and `test_run` of the `t-lat` gate;
  - `fr mcp` over stdio: `tools/list` = OPS, a binding round trip, `prompt_human` matched and cancelled, the token never returned;
  - the T-PORTS orphan release with a `/ws ports` subscriber;
  - `/ws` with the dashboard's LiveClient, and gap backfill.

  The dashboard's `hub-live` suite runs its real LiveClient on a real hub, synced again after a restart.
- **Gate harnesses (C6).** `e2e-harness.test.ts` drives `tests/e2e`'s control flow against a scripted hub: the cleanup on failure or cancel (§10.5), T-PORTS's lend and tab-closed rule, and a standalone `--help`/`--list` of all twelve M1 gate modules (`run.ts --list` lists exactly them, with their needs).
- **Gate harnesses (M1 step 7).** `e2e-gates-a` (T-CODEC, T-LED, T-PRES), `e2e-gates-b` (T-PROV, T-OTA), `e2e-gates-c` (T-NN, T-FLOOD, T-FLOOD-B) and `e2e-gates-d` (T-AGENT) test each module's verdicts on the figures its spike note recorded, its flags, its cleanup against a scripted hub (a cancel or a failed board ends every hook, job and rename it started), and a dry run on a real hub (`real-hub.ts`) with `fr_net_node` pads. `fr_net_node`'s diag answers `stats [section]` as `fr_diag` does (dup, cached_replies, delivery_failed and the C5 sections) and takes `net wifi_down`, so the dry runs read and arm over the hub link; while a hook has a pad's hub link down, its lines go to its stdin, as a board's USB carries them.
- **M2 (T2), as built at M2-C2** ([design m2-c2](../design/m2-c2-t2-fleet.md); the departures from the M2-C2 row's text, D6, D23 and D24, approved 2026-10-26):
  - **The kit** (`firmware/test/host/sim/`, library `fr_sim`, namespace `frsim`):
    - `frsim::Medium`: a directed pair table (`one_room`, `two_rooms`, `matrix`; `positions` uncalibrated, published runs only) with per-pair reach, loss, RSSI, duplication and latency, and a counter-based RNG, so a frame's fate at a receiver does not move when N or an unrelated event changes. Airtime at 1 and 6 Mbps (design §2.1; it reproduces every row of [05 §5.15](05-network.md)); carrier sense with DCF backoff; collisions with 10 dB capture (`collisions: off` reproduces the C5 medium); a channel per radio; per-channel stats in 1 s windows (`busy_us`, and `planning_us`, the on-air-plus-contention unit 05 §5.15 plans in, read as `planning_pct`). The AP's IP traffic counts as airtime on its channel;
    - `SimAir`: each node's radio over the real `air::Scheduler` (16 frames, 4 kept for URGENT; 17 peers with a 1 s hold; guard and lost from late or lost callbacks);
    - one `SimCore` per node (EspCore's pools, queues and round order; a thread-safe `post`; a generation that drops a crashed node's queued events) and one `Executor`, in virtual time (the host suite: a seed gives one trace) or wall time (`fr_fleet`, with a lag histogram over every event);
    - the node classes taken out of `net_node.cpp` (Device, NodeDiag, NodeOtaHost, the blobs, the command table), which `fr_net_node` and `FleetNode` share; `fr_net_node`'s own I/O and `FakeAir` are unchanged for the 3-node interop suites;
    - links: `SimTcp` (non-blocking, the firmware's 0.25 to 5 s backoff, a 5,760 B lwIP send-buffer model; AP down, `wifi_down` and power off leave the socket silent, never a FIN, and an RST follows 8 s after its last frame, as keepalive would), `SimUdp` (one shared socket), `SimSerial` (USB nodes through the fleet's own `--serial-bridge` server, so they show as ports with their MAC); an AP model (on/off, latency, UDP loss, gaps; no CSA or channel change until C4/C6).
  - **`fr_fleet`** (`firmware/test/host/tools/fleet.cpp`): one process, one thread, N nodes, the medium, the AP and the executor in wall time against a hub over loopback. `fr_fleet --spec <file>` (`fractonica/fleet-spec@1`, written by the runner) prints one `ready` line; a control channel takes `[@rid] <alias|*|fleet> <command>` (the `net_node.cpp` stdin commands plus `diag`, `power off|on`, `usb attach|detach`, `log`; `fleet start|stats|medium|ap off|ap on|spawn|pace|quit`). It raises its own open-file limit. `node tools/host-test.mjs --fleet` builds it without sanitizers into `build/host-fleet` (`FR_FLEET_BIN` names another); the T2 gates time that build.
  - **T2-SCALE** (`net_t2_scale_test.cpp`): 10 and 30 nodes in virtual time against a C++ hub model, each case with collisions off and on; gates judged on one room, the 30-node bound tied to the frame size (design D10; §10.5 "T2 gates"). `sim_parity_test` runs the C5 medium's 3-node cases on the new medium.
  - **Scenarios** are YAML (`fractonica/sim-scenario@1`, `tests/sim/scenarios/*.yaml`, zod schema in `packages/protocol/src/sim.ts`), in the thin form of design D13: per run a bench module and its args (`runs[].run`, `runs[].args`), plus only what the fleet emulates (nodes, `usb`, spares, seed, medium, AP, storm, pacing). `published: true` marks a scenario (or a run) whose figures are reported and never gate. They run with `fr test run --tier sim [<scenario>] --json` (§10.5 "T2 gates").
  - **Suites:** `pnpm test:host` runs the kit's own tests (`sim_*_test`), `net_log_test` and T2-SCALE (§10.4). In `pnpm test`: `fleet-hub` (`fr_fleet` with 10 nodes against a real hub: `wifi_down` and `ap off` with no FIN, a USB node through the bridge, a hub restart, power cuts giving offline `timeout`), `sim-scenario`, `sim-runner`, `e2e-gates-f` (the T2 verdicts on recorded figures, the new T-FLOOD and T-FLOOD-B flags, a dry run of `t2-flood-30` at 10 nodes), `router-scale`, `router-describe`, `hub-status-scale`, `log-ingest`, `interop-log` (`fr_net_node`'s LOG frames into `logs_read`) and `t-ota-netlog`. `packages/hub/test/real-hub.ts` now re-exports `tests/sim/lib/private-hub.ts`, its API unchanged.
  - **The gateway role (M2-C4;** [design m2-c4-gateway](../design/m2-c4-gateway.md) D18**):** a fleet node with `role: gateway` (`FleetNodeSchema.role`, absent: node; it needs `usb`) runs `fr_gw`'s bridge over its `SimAir` as `core.cpp` wires it on target (`Net::air_send_raw`, Net's `AirTap`) and speaks GW_* to the hub on its bridge port; it associates with the AP for its channel but opens no TCP or UDP; `stats gw` answers its bridge's counters (`{"on":false}` on every other node). `fleet-gateway` (in `pnpm test`, with the binary): one gateway and three pads on a private hub, the pads under `wifi_down` HELLO over the gateway (links `[gateway]`, `gw` its alias), 100 `command_send` rounds all ok over it, 100 hub broadcasts on every pad (one GW_TX FF×6 each; the medium lossless and collision-free there), `hub_mute` on the gateway (LINK_PING unanswered: D15's 1 s timeout, which T-GW-LINK's real unplug does not exercise) and `usb detach` each give the gateway down ≤ 1.25 s, and the pads back on TCP after. Every radio's net is 0 there: a private hub has no network record, so its BEACONs and broadcasts say net 0. Scenario-level `gateways:` (T2-GW-*) come at C6/C8.
  - **Spike S2's harness (M2-C4; run 2026-10-27, [spike note](../spikes/2026-10-27-m2-c4-s2-gateway.md)):** `tests/spikes/s2.ts --q a|…|i|all` runs D20's questions against the lab hub (diag hooks `air bench|rate|txpower|churn`, `wifi proto`, `cpu`, `net stream` through `diag_exec`; `command_send` RTT/loss series; `ota_deploy` of `--build-a`/`--build-b` for (f); person steps with live readouts for (a) and (i), BOOT to confirm), writes one record per question to `docs/spikes/data/2026-10-27-s2/<q>.json` (atomically, a temp file then rename; an error record never replaces a good one and goes to `<q>.error.json` then; (h) never reads an error record) and prints a summary table; (b) runs node ↔ gateway both ways, node → node and one gateway → nodes broadcast, and its pass is M0's (broadcast ≥ 99 %, unicast ≥ 99.9 % after the link retries; the denominator is sent + refused, or sent alone at `--interval-ms 0`, where a refused frame is sent again with the same seq; received/sent is recorded beside it). - **cJSON for the host suite** (`diag_json.cpp`) is vendored in `firmware/test/host/third_party/cjson`: 1.7.19, unmodified, the version the firmware's `espressif/cjson` carries (its `PROVENANCE` lists the checksums; the two must stay in step). A fresh checkout needs neither an IDF install nor `managed_components`. `FR_CJSON_DIR` overrides it.
- **Golden vector files** (`schema/vectors/{header,envelope,messages,caps,serial}.json`, `schema: fractonica/vectors@1`) hold `cases: [{name, kind, type, value, hex}]`. `fr gen` writes them with a reference encoder that is independent of the generated codecs.
  - `value` is JSON-safe: integers as numbers, `u64` as a decimal string, bytes as lowercase hex, enums by member name. An envelope case carries `header`, `prefix`, `body` and, for a known body, `body_type`/`body_value`.
  - `decodeOnly: true`: the bytes only decode, because they are not what the encoder writes for `value` (unknown fields, field order, repeats, non-minimal varints, line terminators).
  - `error: <DecodeError>` with `value: null`: the bytes must fail to decode with that code.
  - `*.lenient_*` cases hold values the codec carries but the schema rejects (outside `range`, an unnamed enum value): the codecs round-trip them, while C++ dispatch and the TS JSON accessors refuse them ([07 §7.5](07-capabilities-sdk.md)).
- **Fuzzing.** Every decoder target (header, envelope, each system message, each capability struct, serial line) runs random buffers and mutations of the golden vectors from xorshift32 seeded with FNV-1a 32 of the target name, the same in TS and C++. Each target folds its outcomes (accept or the error code) into a digest. `FR_FUZZ_N` sets the cases per target (default 10⁴).
- **Digest parity.** Equal digests show that both decoders accept and reject exactly the same inputs with the same codes. The `wire.*` digests at 10⁴ are pinned in both suites. The gate compares every target both sides run at 10⁶: the TS suite writes its digests to `FR_FUZZ_DIGESTS`, and `host-test.mjs --fuzz N --expect <file>` checks the C++ ones against them, so the `gen.*` digests, which move with every schema or vector change, need no pins.

### Gate harnesses (`tests/e2e`, from C6)

**Module contract.** One module per gate, `tests/e2e/t-<gate>.ts`, exporting a Scenario as its default export (or as the named exports `gate`, `needs`, `run`):
- `{gate, title?, tier?, needs: {human?, wiring?, usb?, fixture?}, needsFor?(args), skip?(ctx), usage?, run(ctx) → {pass, measured, evidence}}`. `gate` is the id as the spec names it; `usage` lists the module's own flags. Since M2-C1: `tier` is `target` (the default) or `hil` (`needs.fixture`, the HIL fixture and its bench file, checked by the runner's `bench_get` preflight, never a person); `needsFor` narrows the needs for given args (T-INPUT `--phase human --press-by fixture` needs no person); `skip` gives a reason the gate cannot run on this bench (T-LAT while the bench file wires its rig's pins).
- `ctx`: `hub` (REST, with `X-Fr-Client` from `FR_CLIENT`), `hubUrl`, `sourceDir`, `allowHuman`, `signal` (aborted on a cancel), `args` (a standalone run's own flags), `log()`, and `measure()` (a `[measured]` line, kept in the report even if the run fails half-way).
- Loading a module runs nothing; it runs on its own under `import.meta.main`. Shared code is in `tests/e2e/lib/` (`scenario`, `runner`, `report`, `hub`, `tasks`; per gate family `led-pres-*`, `prov-ota-*`, `nn-flood-*`, `agent-evidence`); the Web Serial page is `tests/e2e/fixtures/web-serial.html`.
- **The twelve M1 gates** (11 §11.1), `run.ts --list`: `t-agent.ts` T-AGENT `{human, usb}`, `t-codec.ts` T-CODEC `{}`, `t-flood-b.ts` T-FLOOD-B `{usb}` (`{human, usb}` when `FR_T_FLOOD_B_ARGS` holds `--router-off`), `t-flood.ts` T-FLOOD `{}`, `t-input.ts` T-INPUT `{human, usb}`, `t-lat.ts` T-LAT `{wiring, usb}`, `t-led.ts` T-LED `{}`, `t-nn.ts` T-NN `{human}`, `t-ota.ts` T-OTA `{human, usb}`, `t-ports.ts` T-PORTS `{human, usb}`, `t-pres.ts` T-PRES `{human, usb}`, `t-prov.ts` T-PROV `{usb}`. M2-C1 adds `t-hil.ts` T-HIL `{fixture}` (tier `hil`; `run.ts --tier hil --list`); M2-C3 adds `t-analog.ts` T-ANALOG `{fixture}` (tier `hil`) and `t-vbat.ts` T-VBAT `{human}` (`{}` with `--meter-mv`: the reading is a person's). M2-C4 adds `t-gw-link.ts` T-GW-LINK `{human, usb}` (`{usb}` with `--no-unplug`, a dry run that cannot pass). M2-C5 adds `t-display.ts` T-DISPLAY `{human}` (`{}` with `--no-human`, or with no glass or touch phase: the automatic parts, which pass or fail on their own but are not the gate). A1 adds `t-audio.ts` T-AUDIO `{}` (`{human}` with `--voice`: the person's step, which the gate needs).
- **Bench conventions** every module keeps: `--devices` picks the boards (a board the hub does not know, such as an unprovisioned pad-s3, fails on its own and the others go on); each board's results carry its RSSI (`rssi_ap`, and ESP-NOW neighbours where the gate uses them), with a warning below −70 dBm (the C3s' 8.5 dBm TX cap); a physical step is asked with `prompt_human` (a dashboard toast) and on stderr as a `PLEASE:` line, and with `--say` also by `sk say`, repeated every 10 min until done; `--json` prints the report.

**Runner.** `tests/e2e/run.ts [suite…] [--suite a,b] [--tier target|hil|sim] [--allow-human] [--hub URL] [--json] [--list] [-- args…]` runs the gates of one tier (default `target`) one after another against `FR_HUB`. `--tier sim` (since M2-C2) hands over to the sim runner (`tests/sim/lib/runner.ts`), which loads scenarios instead of `t-*.ts` modules and starts its own hub ("T2 gates" below). Since M2-C4 ([design m2-c4-gateway](../design/m2-c4-gateway.md) D22) a target or hil run (`run.ts`, a module on its own) snapshots every online DUT but the fixture right before each gate's first hub call and after the gate (`diag stats` tcp_close_* and `stats espnow`, by device id; a gate that never calls the hub gets none) and publishes the deltas as `measured.stats_delta {devices, tcp_closes, tcp_close_seen}`; a counter that went down (a reboot) counts its after value and is named in `reset`, a DUT that did not answer is `unread`, and a failed snapshot never fails the gate. `--no-stats-delta` turns it off. An unexplained `tcp_close_*` gets a note before the M2 exit. In the M2-C4 round the deltas showed `tcp_close_*` 0 on every pad and ESP-NOW `tx_fail` 0.
- A gate that needs a person or wiring is `skipped` without `--allow-human`.
- `-- args…` (since M2-C1) go to the one suite named; `test_run`'s `args` arrive this way.
- The report, the last stdout line with `--json`: `{tier, pass, hub, allow_human, started_at, duration_ms, counts, gates: [{gate, file, title?, status: pass | fail | skipped | error, needs, reason?, code?, measured, evidence?, duration_ms}]}`; `tier` is the run's (no longer always `target`), and a hil run adds `preflight {ok, fatal[], notes[], bench?, fixture?}`. A sim run (since M2-C2) adds `conclusive` (false when a gated entry was not judged) and `not_judged`, and marks a published entry `published: true` (its status never fails the run).
- Exit 0 when every gate passed or was skipped, 6 a gate failed, 1 one errored, 3 no such suite, 4 a sim run that failed nothing but left a gated entry not judged, 64 usage, 130 cancelled. SIGTERM or SIGINT aborts the scenario's signal; 10 s later (5 s before M2-C1), or at a second signal, the process ends.

**Under `test_run`** ([09 §9.4](09-agent-api.md)). `tier: target` (or, since M2-C1, `hil`) starts `run.ts --json [--tier hil] [--suite <suite>] [--allow-human] [-- args…]` as a job of kind `test`, in its own process group, with `FR_HUB` = this hub (its bound port) and `FR_CLIENT` = the caller's origin.
- stderr lines `@e2e {"gate", "status"}` become the job's stage; a failed gate is `ASSERTION_FAILED` with the report in `details`.
- A cancel sends SIGTERM to the group and SIGKILL 10 s later (5 s before M2-C1), so releases, LED restores and binding restores finish.
- Since M2-C1 a run's `args` (with `suite`) go to that one gate; `--allow-erase`, `--allow-hub-stop` and `--router-off` are refused there. Otherwise a harness takes its own flags only from `FR_T_<GATE>_ARGS` in the hub's environment (`FR_T_AGENT_ARGS`, `FR_T_CODEC_ARGS`, `FR_T_DISPLAY_ARGS` (since M2-C5), `FR_T_FLOOD_ARGS`, `FR_T_FLOOD_B_ARGS`, `FR_T_HIL_ARGS` (since M2-C1), `FR_T_INPUT_ARGS`, `FR_T_LAT_ARGS`, `FR_T_LED_ARGS`, `FR_T_NN_ARGS`, `FR_T_OTA_ARGS`, `FR_T_PORTS_ARGS`, `FR_T_PRES_ARGS`, `FR_T_PROV_ARGS`; `test_run` passes its environment to the child), so `test_run` runs the gates at their defaults. The bench runs them standalone.
- Under `test_run` at the defaults: T-PROV runs reflash, ota and rename but neither erases nor provisions, so its verdict fails, unless `FR_T_PROV_ARGS` holds `--allow-erase`; T-NN never runs its stopped phase (stopping the hub would end the run that is its child), so its verdict fails there unless `FR_T_NN_ARGS` holds `--phase running`; T-AGENT ends as `error` with guidance unless `FR_T_AGENT_ARGS` holds `--since c:<run>.<seq>` (or `--prepare`); T-FLOOD-B needs a person only with `--router-off`.
- T-INPUT's loss phase cannot run on a `--no-serial` hub (its diag needs USB); `interop-hub` covers it with `fr_net_node` (§10.3). Since M2-C2 the fleet runs it too, on its private hub through the serial bridge (T2-INPUT-30).
- **Tier `sim`** (since M2-C2, [design m2-c2](../design/m2-c2-t2-fleet.md) D14) starts `run.ts --json --tier sim [--suite <scenario>] [-- args…]` the same way, with these differences:
  - no `FR_HUB`: each scenario starts its own private hub, and the runner refuses any hub that is not its own child on a port-0 address with a fresh temp `FR_HOME`; every `FR_T_*_ARGS` is stripped, so the run functions get the scenario's args only;
  - the `test:target` lock, as target and hil runs take: a 30-node wall-clock run and a bench run would skew each other's timing;
  - the refused flags govern test_run's `args` only (a scenario's own `--router-off` and `--allow-hub-stop` act on the AP model and the private hub); `allow_human` is ignored (the person bot is the person); the `args` are the runner's own (`--seed n`, `--nodes n` for published runs, `--time-scale 0.5`, `--keep`);
  - a tier-wide run takes the gated scenarios only; a `published: true` one runs only by its id and never fails the job;
  - no `fr_fleet` binary: `ENV_MISSING`, remediation `node tools/host-test.mjs --fleet`; a run that failed nothing but left a gated entry not judged ends `TIMEOUT` (retryable, no verdict), `test_report` then giving `pass: null` with the report.

**Standalone.** `node --conditions=@fractonica/source tests/e2e/t-<gate>.ts [flags] [--json]`, with `--allow-human` implied. `--help` (the scenario's `usage`, on stderr) and `--list` (the `run.ts --list` line) answer with exit 0, before any signal handler or hub call.

**No bench state left behind.** A gate run that fails or is cancelled restores the bench:
- `tests/e2e/lib/tasks.ts`: `allOrAbort` (one board's failure or a cancel aborts the others and waits for every cleanup before rejecting with the first real error), `retrying` (a transient error once more) and an abortable `sleep`. `Hub.call`, `ok` and `job` take the signal.
- T-INPUT arms `net loss` inside its try and always disarms it (`net loss 0 0`, retried once; else the log names `fr diag <alias> net loss 0 0`).
- T-LAT cancels its `latency_probe` job (else the log names `fr jobs cancel <id>`) and restores every parked binding (else it names the `fr bind …`, reported as `bindings_not_restored.<B>` without changing the verdict).
- T-PORTS releases its lend in a `finally`.
- T-LED puts each board's LED (`status.on`, and `status.color` after the visual check) back as it read it; a failure names the `fr send`.
- T-PRES ends `net udp_block` on every board (`net udp_block 0`, retried once) when one board fails or the run is cancelled.
- T-PROV undoes a rename that did not come back (else names `fr devices set`); a board erased and not provisioned gets `flash_start {plan: recover}`. A cancel never cuts a serial flash or a provisioning short (the board would be left without firmware); the log says how to finish by hand.
- T-OTA puts every board back on its normal firmware (the image it ran, or the one its wifi phase installed) with `ota_deploy` (via auto); a cancel cancels the OTA job (the node keeps its image) and logs the `fr ota … --build …` for each board.
- T-NN restores the binding it used (cleared if it made it) and every binding it parked; once it stopped the hub, every way out starts it again (`fr hub start`).
- T-FLOOD and T-FLOOD-B cancel their `message_send` job and end every hook they armed (`net drop_hub_link 0`, `net wifi_down 0`, retried once; else the log names the `fr diag <id> …`); a node not on USB comes back when its hook expires.
- T-CODEC kills its step's whole process group on a cancel. T-AGENT changes nothing (reads, and a selftest that puts the LED back); it prints the restoration steps for what the agent changed.
- T-HIL releases every line, sets each LED back to what it read (checked on the fixture, also after phase 4's reboots), restores its parked bindings, and checks that `bench_get` shows every line idle.
- The sim tier (since M2-C2) leaves no bench state: it never touches the lab hub or the boards. On a cancel the gate's per-node restores are skipped, since the fleet and the private hub are thrown away; the runner ends the person bot's waits, sends `fleet quit` (SIGKILL after 1 s) and stops the hub (SIGTERM, SIGKILL at 3 s). Both run in process groups of their own, so the job's group SIGTERM does not reach them first, and the sequence fits inside the 10 s grace.
- Limit (before M2-C1, when the grace was 5 s): `test_run`'s grace could cut off a slow cleanup (two binding restores to a node that does not answer, at up to 3 s each, or a disarm to an unresponsive node). Each request that reached the hub still completes there, and the logs name the manual commands.

A least-squares line `mv_dut = g · mv_set + o` over every read (`mv_set` the fixture's `applied_mv`): `|g − 1|` ≤ 0.05 (the fixture's 3.3 V rail tolerance), `|o|` ≤ 60 mV, every residual ≤ 25 mV, the step means strictly increasing. The line is the published figure, and maps phase 6's thresholds to setpoints.
- **3 step:** 400 mV for 500 ms, then 2,000 mV; from its `at_hub_us` to the first STATE within `deadband` of the settled value (`read.value` 700 ms later): ≤ 50 ms (5 τ) + 1/`report_hz` + 50 ms transport, 150 ms at 20 Hz.
- **4 quiet:** 1,200 mV, 1 s to settle, then 10 s: ≤ 2 STATEs.
- **5 rate** (one DUT at a time, so the fixture's serial line carries one stream): a 1 Hz triangle 300 ↔ 2,200 mV for 5 s, setpoints on a 20 ms grid, each waiting for its RESULT (the rate reached is published as `setpoint_hz`): the STATEs between the first and last setpoint's `at_hub_us` come at 0.8–1.1 × `report_hz`.
- **6 crossed:** 2 ramp pairs, 25 mV every 50 ms from 300 mV below the lowest threshold to 300 mV above the highest and back, each threshold's setpoint held 2 s on the way up and down. Before each 2 s window the setpoint is nudged (at most 4 times; each from the median of 3 `read.value`s 300 ms after the last setpoint, through the staircase's gain) until the DUT's value is within `hysteresis`/4 of the threshold, since the staircase allows 25 mV residuals and a value flips only `hysteresis`/2 (19.5 mV at 1024) off its threshold; the window starts at the last read's answer, and value − threshold per dwell is published (`dwell`). Pass: exactly 0, 1, 2 `rising` then 2, 1, 0 `falling` per pair, and none inside a dwell (hysteresis: a value on its threshold never flips it). A dwell still beyond ±`hysteresis`/2 after the nudges fails the phase as a setup failure ("dwell off threshold"), apart from chatter.
- **7 inject:** the fixture holds 600 mV; `input_simulate {layer: inject, value: 50000, hold_ms: 1000}`: a STATE ≥ 49,000 within 200 ms of the send, then one within `deadband` of the 600 mV value within 1,300 ms. The send is on the hub's clock, which the STATEs' `t_hub_us` run on: the inject result row's `t_hub_us` (its RESULT's arrival) less its `rtt_ms`. Never the harness's own wall clock: the hub's µs are its wall clock at start carried on by its monotonic clock, which drifts from another process's (about 20 ppm on the lab Mac).
- **8 cleanup** (`finally`): 0 mV on every DUT's line (allowed even when the hub refuses other setpoints), once more on a failure; the SDK client closed; with `--deploy` the bench profile back.
- **Gate:** every phase passes on both DUTs and cleanup completes; with the default `--devices` and `--phase` the run is the gate (`full_gate`), a narrowed one is partial.

### T2 gates (since M2-C2)

[Design m2-c2](../design/m2-c2-t2-fleet.md) §5; results in [11 §11.6](11-roadmap.md) "M2-C2 result". T2-SCALE runs in the host suite (§10.4). Each T2-*-30 gate is one scenario of `tests/sim/scenarios/`, run with `fr test run --tier sim <scenario>` (`test_run {tier: sim, suite}`). Its pass rule is the bench module's own verdict, run at 30 nodes on `fr_fleet` against a private hub, plus the sim tier's rules below. The run functions get a fleet diag (the hub's `diag_exec` while a node has a hub link, else the fleet's control channel, as a board's USB carries them), and a person bot answers every `PLEASE:` line through the control channel (presses, power, USB, the AP). No person, board or lab hub is involved.

**Per scenario, in order** (`tests/sim/lib/runner.ts`):
1. Validate: every alias the scenario names exists, every `--isolate` node is on USB, and every node that can lose its hub link has at least 2 seeders in reach.
2. Find `fr_fleet` (`FR_FLEET_BIN`, else `build/host-fleet/fr_fleet`; else `ENV_MISSING`). A run on a sanitized binary is reported `sanitized: true` and never counts. Since M2-C3 a checkout `fr_fleet` older than its sources is refused (`fleetStaleness`: `ENV_MISSING` "stale fr_fleet: <file> is newer…"; rebuild with `node tools/host-test.mjs --fleet`): T2-ANALOG-30's first dry run ran on one built before the kit's analog change, and every node was silent.
3. The preflight (below).
4. Start the fleet, then the private hub (its `--serial-bridge` pointing at the fleet), each in a process group of its own. Identities and images are provisioned before the hub starts: MACs `02:f2:00:00:xx:yy` (locally administered, never a bench MAC), aliases `sim-01`…, the scenario's profile (`c6-pad`; since M2-C3 also `c3o-analog`, the kit's two port tables).
5. The storm (below).
6. Each run, once every node is online: a node offline at a run's start errors the run, never drops out of its verdict.
7. The lag rule; then stop both and report.

Evidence goes to `build/sim-runs/<scenario>-<stamp>/` (git-ignored), appended line by line as the run goes, so a SIGKILL loses nothing already written: `scenario.json` (as run), `schedule.json` (T2-CHURN-30's drawn schedule), `fleet-spec.json`, `hub.jsonl` and `fleet.jsonl` (each process's output), `metrics.jsonl` (the `hub_status` snapshots), `gates.jsonl`, `runner.log`, `preflight.json`, `runner-lag.json`, `person.json`, `diag.jsonl`, `dashboard.json`, and `report.json` at the scenario's end. **T2-CHURN-30** (defined by design m2-c2 D12, approved 2026-10-26, §7 item 1):
- **Schedule:** drawn from the scenario's seed, about 10 min on 30 nodes plus 3 spare rows, with at least 2 events in flight at a time and no node in two events at once; written to the evidence before the run. Minimum counts: ≥ 5 BYE reboots (`fr.node.reboot`); ≥ 5 power cuts, 2 of them on USB nodes (`power off`, the port detached, `power on` 5–20 s later); ≥ 4 `net wifi_down 20`, at least 1 on a USB node; ≥ 4 `net udp_block 30`; 3 joins (`fleet spawn` of a spare row); 2 private-hub restarts, at about 3 and 7 min. USB nodes: `sim-05`, `sim-15`, `sim-25`.
- **Window:** from the runner's stamp at the action's send to its closing event (online again; `udp_blocked` cleared; back on TCP after the hook; the joined node online), plus 2 heartbeats. A hub restart is a window for every node, from the stop to all nodes online plus 2 heartbeats. A powered-off node's socket stays silent until its RST at +8 s, so the hub offlines it by `timeout`, never by a FIN.
- **Per event** (T-PRES's checks, `lib/led-pres-checks.ts`, plus new ones):
  - BYE: `byeProblems` (offline `reboot` within 1,000 ms of the send, `node.boot`, online again);
  - USB power cut: `unplugVerdict` (offline `timeout` 2.4–3.5 heartbeats after `port.detached`);
  - power cut without USB: offline `timeout` within `unplugBoundMs` of the runner's stamp, widened by 200 ms;
  - `wifi_down` on a TCP-only node: offline `timeout` within that bound plus `net wifi_down`'s 300 ms apply delay ([09 §9.7](09-agent-api.md)), 4,000 ms at a 1 s heartbeat (`wifiDownOfflineMaxMs`); online again on TCP < 10 s after the hook ends. **The +300 ms is a proposed correction, awaiting your approval:** D12 reused the power cut's bound (3,700 ms at 1 s), and the first 30-node run failed one event at 3,747.7 ms, because a heartbeat sent inside the 300 ms window moves the hub's timeout with it;
  - `wifi_down` on a USB node: `device.link {tcp, up: false}` within 10 s, no offline, back on TCP < 10 s after the hook ends;
  - `udp_block`: `udpProblems` (`udp_blocked` raised, no false offline, cleared within 5 s);
  - join: `device.online` within 15 s of the spawn with the provisioned alias, and within 2 s its own directory equal to the registry and its row in every other node's.
- **Run-wide:** no `device.offline` or suspect on a node outside its own windows; `device_list` and an SDK client's view agree with the fleet within 2 heartbeats of each event's end; every node's directory equals the registry within 2 s of a join or a restart; `binding_list --live` shows `same` for every row after each hub restart (5 bindings set at the start); all online within 15 s of each hub restart.

**The sim tier's rules** ([design m2-c2](../design/m2-c2-t2-fleet.md) D15, §5.3). **Their numbers are proposed, awaiting your approval**, and are to be calibrated against the first runs' histograms before they are final.
- **The storm** (every scenario, before its runs): `fleet start`, all at once by default, then every node online within 5 s at 30 nodes and 10 s at 60; `handshakes_restarted` 0; `describe_sent` ≤ 1 per descriptor hash; `time_samples_lost` 0 (from `hub_status.router.scale`, [08 §8.11](08-hub.md)). Counters that did not see the storm, or a `hub_status` snapshot that did not answer, make it `UNMEASURED` (an error), never a pass on zeros. A storm that fails while a lag figure exceeded the threshold is inconclusive, not failed.
- **Lag:** a run is inconclusive when the p99 over every probe of the run exceeds 100 ms for the hub loop (`router.scale.loop`, per hub process, summed across restarts), the fleet's executor lag or the runner's own 20 ms probe, or when one stall of 1 s or more (`hello_retry_ms`) falls inside a timing window or the storm. It is re-run once at half the time scale, and a second inconclusive run fails. This holds whether the run passed, failed or threw. A window whose `hub_status` snapshot did not answer (three tries of 10 s) is unmeasured, never a pass.
- **Preflight:** before the fleet starts, the runner samples 30 s: the 1-min load average against the core count, and its own lag p99 (≤ 20 ms). It waits up to 10 min for a quiet window. If none comes, the scenario is not run: its entries are `skipped` with `inconclusive.reason: host_load`, the report says `conclusive: false` (exit 4; `test_run` `TIMEOUT`), and that is neither a first run nor a pass.
- **Half the time scale** = half the scenario's rates, counts kept, per module (`TIME_SCALE` in `lib/verdict.ts`): t-flood `--interval-ms` ×2; t-flood-b `--rate` ÷2 and `--outage-s` ×2; t-nn and t-input `--gap-ms` ×2; t2-churn's event spacing ×2; the epoch step's rates ÷2; t-ota and t2-analog unchanged (the nodes' `report_hz` is the load under test). Count verdicts do not depend on wall time; timing figures are wall-clock.
- **Gate rule:** each T2-*-30 gate passes once, conclusively, on the unsanitized `fr_fleet`. T2-SCALE passes at 5 seeds. The published scenarios (`t2-flood-30-collisions`, `t2-flood-30-long-frames`, `t2-flood-30-two-rooms`, `t2-flood-60`, and since M2-C3 `t2-analog-30`, until its first gated run) and published runs are reported and never fail a job.
