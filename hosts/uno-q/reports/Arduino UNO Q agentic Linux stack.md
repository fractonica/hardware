# Layer the UNO Q for agentic control

As of November 2026, the Arduino UNO Q is an easier custom-Linux target than its pre-1.0 tooling suggests, and a harder agentic-control target than its marketing implies. **The board's device tree has been in mainline Linux since 7.0, Qualcomm maintains a Yocto BSP for it (`meta-qcom-arduino`, `MACHINE = "uno-q"`), and Armbian and a Buildroot-based Nerves system already boot it on mainline kernels.** Everything above Qualcomm's signed ABL loader can be replaced, and EDL mode lives in ROM, so a bad eMMC image can always be recovered. The difficult parts are elsewhere. The stock Linux-to-STM32 bridge is arduino-router speaking unframed MessagePack-RPC over a 115200-baud UART, and it has an acknowledged failure mode in which **one corrupted byte silently stalls all RPC traffic** until a restart. Any pipeline an agent drives therefore needs a supervisor daemon on Linux and failsafes on the MCU that keep working without Linux. Arduino's official MCP work is either development-time (App Lab Agent Mode and its internal `arduino-board` server) or client-side (the MCP Client Brick). **No official runtime MCP server lets an agent read sensors or drive actuators.** You have to build that layer, ideally against the stateless 2026-07-28 MCP specification. The agent's planning brain belongs off the board: the QRB2210's four Cortex-A53 cores generate about 5 tokens/s on the CPU alone, so one local tool-calling decision takes 11 to 83 seconds. The recommended stack is a minimal Yocto image with Mender A/B updates. It runs arduino-router, a privileged MCU supervisor, and an unprivileged Go MCP server that Claude Code reaches over Tailscale, with hard limits and a heartbeat watchdog on the STM32. Prototype that pipeline on stock Debian first, so the control path is proven before any distro work starts.

## Thirteen months after launch, the platform is open where it counts

The UNO Q (codename "Imola") pairs two chips. The first is a **Qualcomm Dragonwing QRB2210**: four Cortex-A53 cores at 2.0 GHz, an Adreno 702 GPU and a Hexagon DSP, from the same Agatti/QCM2290 family as Qualcomm's RB1 reference board. The second is an **STM32U585** Cortex-M33 at 160 MHz with 2 MB of flash and 786 KB of SRAM ([datasheet](https://github.com/arduino/docs-content/blob/main/content/hardware/uno/boards/uno-q/datasheet/en-datasheet.md); [CNX Software](https://www.cnx-software.com/2025/10/07/qualcomm-acquires-arduino-introduces-arduino-uno-q-dual-brain-sbc/)). It comes in two SKUs. ABX00162 has 2 GB RAM and 16 GB eMMC; ABX00173, added in January 2026, has 4 GB and 32 GB. After a July 2026 price rise they cost **$59 and $79** ([Arduino blog](https://blog.arduino.cc/2026/06/26/a-heads-up-on-the-arduino-uno-q-board-pricing-straight-from-marcello-majonchi/)).

The two chips split the hardware physically. **All 47 maker-facing digital pins belong to the STM32.** Linux owns USB-C, the MIPI camera/display connector, two RGB LEDs, and a handful of 1.8 V SoC lines that Arduino marks as interface-dedicated rather than general GPIO ([user manual](https://github.com/arduino/docs-content/blob/main/content/hardware/uno/boards/uno-q/tutorials/first-steps/user-manual/content.md); [datasheet](https://github.com/arduino/docs-content/blob/main/content/hardware/uno/boards/uno-q/datasheet/en-datasheet.md)). An agent that wants to touch a shield must go through MCU firmware, so the bridge matters as much as the distro. Reviewers put the Linux side at roughly Raspberry Pi 3B+ to Pi 4 performance ([Jeff Geerling](https://www.jeffgeerling.com/blog/2025/arduino-uno-q-weird-hybrid-sbc)).

The stock OS is **Debian 13 "trixie"**. The newest image in Arduino's Stable manifest is **20260528-558 with kernel 7.0.0**, up from 6.16.7 at launch. No newer image has appeared since May, even though Arduino's kernel fork now has branches through `qcom-v7.3.1-arduino` ([Arduino image index](https://downloads.arduino.cc/debian-im/Stable/info.json); [arduino/linux-qcom](https://github.com/arduino/linux-qcom)). On top sit App Lab, a Wails desktop IDE, and `arduino-app-cli`. Together they manage "Apps": a mandatory `python/main.py`, an optional Zephyr sketch for the MCU, and "Bricks" that run as Docker containers ([About Apps doc](https://github.com/arduino/docs-content/blob/main/content/software/app-lab/4.apps/1.about-apps/about-apps.md)). The Python side and the sketch talk through the Bridge, which arduino-router implements.

The tooling releases roughly monthly. `arduino-app-cli` v0.14.1 and arduino-router v0.11.0 shipped between late October and early November 2026. The MCU core, ArduinoCore-zephyr, reached its first stable release, **1.0.0, on 2 September 2026**, and 1.1.0 on 29 October ([app-cli releases](https://github.com/arduino/arduino-app-cli/releases); [router releases](https://github.com/arduino/arduino-router/releases); [ArduinoCore-zephyr releases](https://github.com/arduino/ArduinoCore-zephyr/releases)). Code built on App Lab internals should expect to break. Code built on the kernel and arduino-router's wire protocol stands on much firmer ground.

Openness survived the Qualcomm acquisition, which was announced alongside the board in October 2025. The app tooling and router are GPL-3.0, the Bricks MPL-2.0, the Zephyr core Apache-2.0, and Arduino's Yocto layer MIT ([arduino-router](https://github.com/arduino/arduino-router); [app-bricks-py](https://github.com/arduino/app-bricks-py); [ArduinoCore-zephyr](https://github.com/arduino/ArduinoCore-zephyr); [meta-arduino](https://github.com/arduino/meta-arduino)). The November 2025 Terms-of-Service rewrite drew a backlash. In response, Arduino said its reverse-engineering ban covers only Arduino Cloud and pledged that previously open components stay open ([Hackster](https://www.hackster.io/news/arduino-clarifies-terms-and-conditions-following-backlash-anything-that-was-open-stays-open-645e9ee9a51e)). Two things stay closed. The first is **the Qualcomm boot firmware bundle**, `unoq-bootloader-emmc-linux-251020.zip`, licensed `LicenseRef-LICENSE.qcom` ([firmware recipe](https://github.com/qualcomm-linux/meta-qcom-arduino/blob/main/recipes-bsp/firmware-boot/firmware-qcom-boot-qrb2210-arduino-imola_251020.bb)). The second is the set of GPU, DSP and Wi-Fi blobs, which are at least redistributable through linux-firmware ([linux-firmware](https://gitlab.com/kernel-firmware/linux-firmware/-/tree/main/qcom/qcm2290)). The real openness risk is therefore cloud services plus one boot blob, not the board's software.

## A custom distro is a kernel-and-rootfs job, not a board bring-up

### Mainline 7.2 covers a headless controller; audio and camera still need Arduino's fork

Arduino's Riccardo Mereu posted the board-support series in November 2025. Bjorn Andersson applied it in January 2026, and `qrb2210-arduino-imola.dts` **first shipped in Linux 7.0, released 2026-04-12** ([Armbian PR #9710](https://github.com/armbian/build/pull/9710); [patchew series](https://patchew.org/linux/20251120155825.121483-1-r.mereu.kernel@arduino.cc)). Follow-up commits through July 2026 fixed the spidev node, described the DSI-to-DisplayPort bridge, and corrected the PM4125 VBUS regulator ([DTS history](https://github.com/torvalds/linux/commits/master/arch/arm64/boot/dts/qcom/qrb2210-arduino-imola.dts)). Mainline spidev matches the MCU link's `arduino,unoq-mcu` compatible ([spidev.c](https://github.com/torvalds/linux/blob/master/drivers/spi/spidev.c)). Upstream U-Boot also carries the DTS ([u-boot dts/upstream](https://github.com/u-boot/u-boot/tree/master/dts/upstream/src/arm64/qcom)).

The best hands-on evidence for mainline comes from the Nerves system, which runs mainline 7.2 ([Nerves](https://github.com/jimsynz/nerves_system_arduino_uno_q)). On that kernel, GPIO, I2C and SPI work, as do the USB Ethernet gadget and the MCU link through arduino-router. Wi-Fi works through ath10k, with `wlan0` appearing about 13 seconds after power-on once `rmtfs` and `tqftpserv` have started the modem DSP. Bluetooth's `hci0` comes up, and the GPU kernel driver binds, although Nerves ships no Mesa. Three things fail. **Venus video does not probe**, because the driver asks for `qcom/venus-6.0/venus.mbn` while linux-firmware ships the file as `qcom/vpu/ar50lt_p1_gen2_s6.mbn`; with Venus unprobed, clock `sync_state` never completes and unused clocks stay on. There is no audio, because the mainline device tree has no sound card, and no camera, because CAMSS is disabled and the OPE ISP driver exists only in Arduino's kernel.

Armbian counted **48 commits** between v7.0 and Arduino's `qcom-v7.0.0-unoq` branch, covering audio, Type-C DisplayPort, DSI panels and media-carrier overlays ([Armbian PR #9710](https://github.com/armbian/build/pull/9710)). For a headless agentic controller this split is convenient: everything the control path needs is upstream (spidev, `/dev/ttyHS1`, GPIO, Wi-Fi, USB gadget). Only audio and camera push you onto Arduino's fork. The vendor setup passes `clk_ignore_unused pd_ignore_unused` on the kernel command line ([yoe](https://docs.yoebuild.org/machine-uno-q.html)), and Qualcomm's machine config adds `deferred_probe_timeout=30` ([uno-q.conf](https://github.com/qualcomm-linux/meta-qcom-arduino/blob/main/conf/machine/uno-q.conf)).

### Everything above ABL is yours, and EDL makes mistakes recoverable

The production boot chain runs from PBL in ROM through XBL, TrustZone/RPM/hypervisor and Qualcomm's ABL to U-Boot (packed as an Android boot image), which presents UEFI and hands off to systemd-boot or a direct kernel and then the rootfs. **Everything up to and including ABL is signed Qualcomm firmware**, which you reuse as a binary bundle. **U-Boot and everything after it can be replaced** ([Nerves](https://github.com/jimsynz/nerves_system_arduino_uno_q); [u-boot recipe](https://github.com/qualcomm-linux/meta-qcom-arduino/blob/main/recipes-bsp/u-boot/u-boot-arduino_git.bb)). Arduino's U-Boot fork (`qcom-mainline` branch, `qcom_defconfig`) presents UEFI 2.11 and loads the DTB from the EFI system partition ([yoe](https://docs.yoebuild.org/machine-uno-q.html)). No source confirms whether retail boards have secure-boot fuses blown, but custom U-Boot builds and kernels boot in practice.

Two operational rules are non-negotiable. First, ABL runs an A/B scheme, so **your image must run `qbootctl -m` after a successful boot**, or ABL halts in fastboot within seven boots ([Nerves](https://github.com/jimsynz/nerves_system_arduino_uno_q)); Qualcomm's machine config pulls in `qbootctl` for exactly this reason ([uno-q.conf](https://github.com/qualcomm-linux/meta-qcom-arduino/blob/main/conf/machine/uno-q.conf)). Second, flashing goes through EDL: short JCTL `USB_BOOT` to GND, the board enumerates as `05c6:9008`, and `qdl --storage emmc prog_firehose_ddr.elf rawprogram0.xml patch0.xml` writes the image. **EDL sits in ROM, so no eMMC contents can disable it** ([yoe](https://docs.yoebuild.org/machine-uno-q.html); [Nerves](https://github.com/jimsynz/nerves_system_arduino_uno_q)).

The partition layout leaves Qualcomm's A/B firmware pairs alone and adds a 512 MB `efi` partition and a roughly 10 GB `rootfs` partition. The Arduino SKU variant also adds `userdata` ([qcom-ptool](https://github.com/qualcomm-linux/qcom-ptool/blob/main/platforms/_common/qrb2210-abl-emmc.yaml)). The GPT has so many entries that fwup cannot write it, so Nerves writes the GPT with qdl and keeps partitions 1–66 untouched ([Nerves](https://github.com/jimsynz/nerves_system_arduino_uno_q)).

For bring-up, the serial console is the SE4 UART (`ttyMSM0`, 115200 baud) at **1.8 V** on the JCTL header, and there is no SD slot to fall back on ([yoe](https://docs.yoebuild.org/machine-uno-q.html)). A USB gadget is practically mandatory: Nerves warns that an image without one looks dead to the host even when it has booted ([Nerves](https://github.com/jimsynz/nerves_system_arduino_uno_q)). Arduino's Flasher CLI can flash a local qdl bundle, and `ARDUINO_FLASHER_ADDITIONAL_URLS` adds custom image indexes, so a custom distro can publish its own `info.json` and reuse the official flasher ([arduino-flasher-cli](https://github.com/arduino/arduino-flasher-cli)).

On firmware, everything the OS needs at runtime is in upstream linux-firmware: `qcom/qcm2290/{a702_zap,adsp,modem}.mbn`, `qcom/a702_sqe.fw`, and `ath10k/WCN3990/hw1.0` with `qcm2290` board data ([linux-firmware](https://gitlab.com/kernel-firmware/linux-firmware/-/tree/main/qcom/qcm2290)). **Wi-Fi depends on the modem DSP**, so the image must include `rmtfs`, `tqftpserv` and `qrtr`. The per-board Wi-Fi MAC and BT address live in eMMC `boot0`, and U-Boot patches them into the device tree ([Nerves](https://github.com/jimsynz/nerves_system_arduino_uno_q)). Armbian and Yocto both download the boot bundle at build time instead of committing it ([Armbian PR #9642](https://github.com/armbian/build/pull/9642)). A public distro should follow the same pattern.

**meta-qcom-arduino** was created 2026-08-19, and Qualcomm describes it as Qualcomm-maintained. Its **`main`** branch defaults to `linux-qcom-next`, while **`wrynose`** is the Yocto 6.0 LTS branch used by Qualcomm Linux 2.x, with linux-qcom 6.18 ([meta-qcom-arduino](https://github.com/qualcomm-linux/meta-qcom-arduino)). Its `uno-q.conf` pins `u-boot-arduino`, the Imola DTB, `qbootctl`, the ABL eMMC partition layout and the Imola boot-firmware package ([uno-q.conf](https://github.com/qualcomm-linux/meta-qcom-arduino/blob/main/conf/machine/uno-q.conf)). A `linux-arduino_7.2.bb` recipe builds Arduino's 7.2.11 kernel ([linux-arduino_7.2.bb](https://github.com/qualcomm-linux/meta-qcom-arduino/blob/main/recipes-kernel/linux/linux-arduino_7.2.bb)).

Arduino's own **meta-arduino** layer adds an `imola` machine that wraps `uno-q`, recipes for arduino-router, arduino-cli and the USB gadget, a PREEMPT_RT kernel that isolates cores 2–3, and committed kas lockfiles for reproducible builds. It has two drawbacks. Its only supported image for Qualcomm boards is the Docker-based `arduino-container-image`, and the build expects `kas-container` with 48 GB of memory ([DEVELOPERS.md](https://github.com/arduino/meta-arduino/blob/master/DEVELOPERS.md); [imola.conf](https://github.com/arduino/meta-arduino/blob/master/meta-arduino-qcom/conf/machine/imola.conf)). Use it as a recipe source, not a base. Note the naming split: **`uno-q`** is Qualcomm's machine name, and **`imola`** is Arduino's wrapper.

For OTA, a **Mender integration on `wrynose`/`uno-q` was verified on hardware in July 2026**, including rollback of a deliberately broken artifact. It reuses Qualcomm's A/B slots through a `qbootctl-rootfs` update module. Two caveats: firmware-level rollback is untested, and the integration inherits a CI default of an empty root password ([Mender Hub](https://hub.mender.io/t/arduino-uno-q-main-system-yocto/8321)). Qualcomm's documented update model is UEFI capsules for firmware plus OSTree for the OS ([Qualcomm OTA](https://docs.qualcomm.com/bundle/publicresource/80-70020-27/topics/ota_update_for_qualcomm_linux.md)). No RAUC or SWUpdate integration was found.

**The recommendation is Yocto on meta-qcom-arduino.** Use your own distro layer built from `core-image-minimal` and add Mender. If you want to validate mainline behaviour before learning Yocto, use an Armbian minimal image or a trimmed qcom-deb-images fork as a one-week stepping stone.

## The MCU bridge works at 8 ms per call, but it can fail silently

### Linux owns the STM32's reset, boot strap and debug port

The two chips are joined by four links. The main one is a UART: QRB2210 `/dev/ttyHS1` connects to STM32 **LPUART1** on PG5–PG8, the only MCU UART with RTS/CTS wired and one with no header pins, which the stock setup runs at 115200 8N1 without flow control ([Zephyr board DTSI](https://github.com/zephyrproject-rtos/zephyr/blob/main/boards/arduino/uno_q/arduino_uno_q-common.dtsi); [Derek Molloy](https://derekmolloy.ie/under-the-hood-of-the-arduino-uno-q-vanilla-zephyr-on-the-cortex-m33/); [router main.go](https://github.com/arduino/arduino-router/blob/main/main.go)). An SPI bus links the STM32's SPI3, configured as a Zephyr SPI slave, to a Linux spidev node, and the stock bridge leaves it unused ([core overlay](https://github.com/arduino/ArduinoCore-zephyr/blob/main/variants/arduino_uno_q_stm32u585xx/arduino_uno_q_stm32u585xx.overlay); [mainline DTS](https://github.com/torvalds/linux/blob/master/arch/arm64/boot/dts/qcom/qrb2210-arduino-imola.dts)). The remaining two are GPIO handshake lines on `/dev/gpiochip1` and SWD, which OpenOCD bit-bangs through its `linuxgpiod` driver.

Every sketch upload, whether from App Lab or `arduino-cli`, ends as an OpenOCD run on the QRB2210. The run is wrapped by `remoteocd`, which works locally, over adb, or over SSH ([remoteocd](https://github.com/arduino/remoteocd); [Molloy](https://derekmolloy.ie/under-the-hood-of-the-arduino-uno-q-vanilla-zephyr-on-the-cortex-m33/)). Because Linux can reflash, reset and debug the MCU without any external probe, any process that can reach these lines effectively controls the MCU.

**Reconciling the GPIO line mapping.** The two research sources looked at different files. The SWD pins (25/26/38) come from Arduino's Yocto OpenOCD config. Lines 37/38/70 come from arduino-router's systemd drop-in on the Debian image. The two sets fit together; the only overlap is line 38, which both treat as reset, and `arduino-app-cli` independently hard-codes it as the MCU reset pin. Two uncertainties remain: nobody retrieved the stock Debian image's `/opt/openocd/openocd_gpiod.cfg` to confirm it uses the same lines 25/26, and no pin table says what line 37 does. Both can be settled in an afternoon with `gpioinfo` and `cat` on the board.

| gpiochip1 line | Role | Evidence | Confidence |
|---|---|---|---|
| 25 | SWDIO | Arduino's Yocto OpenOCD config for Imola ([openocd_gpiod.cfg](https://github.com/arduino/meta-arduino/blob/master/meta-arduino-qcom/recipes-devtools/openocd/files/imola/openocd_gpiod.cfg)) | Medium. This is the Yocto config; the stock Debian config was not inspected. |
| 26 | SWCLK | Same file | Medium |
| 38 | MCU NRST | The same config uses it as `srst`/`trst`. `arduino-app-cli` hard-codes it as the reset pin ([platform.go](https://github.com/arduino/arduino-app-cli/blob/main/internal/platform/platform.go)). The router's stop hook pulses it to restart the boot animation ([10-imola.conf](https://github.com/arduino/arduino-router/blob/main/debian/arduino-router/var/lib/arduino-router/config/10-imola.conf)). | **High** (three independent sources) |
| 70 | "Linux is ready" signal to MCU pin PG13; ends the boot animation | The router sets it high after it is ready and low on stop ([10-imola.conf](https://github.com/arduino/arduino-router/blob/main/debian/arduino-router/var/lib/arduino-router/config/10-imola.conf)). Two consequences matter for control design.

First, **on the stock image, stopping or restarting arduino-router pulses MCU reset.** The drop-in's stop hook toggles line 38 and drops line 70 ([10-imola.conf](https://github.com/arduino/arduino-router/blob/main/debian/arduino-router/var/lib/arduino-router/config/10-imola.conf)). Arduino's documented fix for a stuck bridge, `systemctl restart arduino-router`, therefore also resets every actuator output to its hardware reset state. A custom distro should write its own unit and decide deliberately whether a router restart resets the MCU.

Second, libgpiod grants each line to only one consumer, so a live debug session blocks flashing ([Molloy](https://derekmolloy.ie/under-the-hood-of-the-arduino-uno-q-vanilla-zephyr-on-the-cortex-m33/)). Agent processes must be kept away from `/dev/gpiochip1` entirely.

### Arduino's Zephyr core trades control for convenience

ArduinoCore-zephyr 1.1.0 runs on an Arduino fork of **Zephyr 4.4.2** ([west.yml](https://github.com/arduino/ArduinoCore-zephyr/blob/main/west.yml)). A prebuilt loader sits at the start of flash. It reads the sketch from the second flash bank at `0x08100000` and either loads it as a Zephyr LLEXT executed in place from flash (dynamic link mode) or jumps straight into a fully linked image (static link mode) ([loader main.c](https://github.com/arduino/ArduinoCore-zephyr/blob/main/loader/main.c)). The board menu has a `wait_linux_boot` option with three settings: Wait for Linux, Immediate, and Wait for App. It replaced the launch-era RAM/Flash upload menu ([boards.txt](https://github.com/arduino/ArduinoCore-zephyr/blob/main/boards.txt); [boards.txt @0.53.1](https://github.com/arduino/ArduinoCore-zephyr/blob/0.53.1/boards.txt)). **This setting is safety-critical.** In the default mode the loader plays the boot animation and *does not start your sketch* until Linux raises line 70. MCU failsafes are therefore inactive during the roughly 20–30 seconds Linux takes to boot, and during any router outage before the sketch has started.

A controller should use **Immediate** mode. It must also start its control thread *before* calling `Bridge.begin()`, because `Bridge.begin()` blocks with no timeout until the router answers ([bridge.h](https://github.com/arduino-libraries/Arduino_RouterBridge/blob/main/src/bridge.h); [RouterBridge #30](https://github.com/arduino-libraries/Arduino_RouterBridge/issues/30)).

Core 1.1.0 added stack protection, null-pointer detection and crash blink codes ([1.1.0 release](https://github.com/arduino/ArduinoCore-zephyr/releases/tag/1.1.0)). Real constraints remain. `CONFIG_LLEXT_HEAP_SIZE=256` reserves a large share of SRAM before user code runs ([variant conf](https://github.com/arduino/ArduinoCore-zephyr/blob/main/variants/arduino_uno_q_stm32u585xx/arduino_uno_q_stm32u585xx.conf)). **No Watchdog library ships with the core** ([libraries](https://github.com/arduino/ArduinoCore-zephyr/tree/main/libraries)), even though mainline Zephyr's board file enables the IWDG as `watchdog0` ([Zephyr DTSI](https://github.com/zephyrproject-rtos/zephyr/blob/main/boards/arduino/uno_q/arduino_uno_q-common.dtsi)), and nobody has verified whether LLEXT sketches can reach Zephyr's `wdt` API. A `loop()` that never yields starves the bridge thread; one user needed `delay(5)` to unblock it ([RouterBridge #76](https://github.com/arduino-libraries/Arduino_RouterBridge/issues/76)). The exit is clean: mainline Zephyr supports the `arduino_uno_q` board as "Maintained". Molloy walked through vanilla Zephyr builds debugged through the on-board OpenOCD, and `arduino-cli burn-bootloader -b arduino:zephyr:unoq -P jlink` restores the Arduino loader ([Zephyr board doc](https://docs.zephyrproject.org/latest/boards/arduino/uno_q/doc/index.html); [Molloy](https://derekmolloy.ie/under-the-hood-of-the-arduino-uno-q-vanilla-zephyr-on-the-cortex-m33/)).

### arduino-router is a trust boundary with no timeouts and no framing

arduino-router is a Go daemon that implements a star-topology MessagePack-RPC router. Clients register method names with `$/register`. The router forwards each request to the client that owns the method, remaps message IDs, and drops a client's methods when it disconnects ([arduino-router README](https://github.com/arduino/arduino-router)). Besides routing, it exposes several built-in method families: `$/version`, `$/setMaxMsgSize`, `$/unregister` (new in v0.11.0), Monitor streaming (`mon/*`), TCP/UDP sockets on the MCU's behalf, and Bluetooth HCI passthrough ([main.go](https://github.com/arduino/arduino-router/blob/main/main.go)). Since v0.11.0 the socket `/var/run/arduino-router.sock` is mode 0660 and owned by an `arduino-router` group ([v0.11.0](https://github.com/arduino/arduino-router/releases/tag/v0.11.0)).

Arduino's Python client documents the security model plainly. Any process that can connect to the socket can call the MCU's methods and forge responses ([arduino-router-bridge-py](https://github.com/arduino/arduino-router-bridge-py)). The protocol's structural limits follow from that design. Each method name has exactly one owner and there is no pub/sub ([issue #71](https://github.com/arduino/arduino-router/issues)), while notifications sent to an unregistered method are silently lost ([router.go](https://github.com/arduino/arduino-router/blob/main/internal/msgpackrouter/router.go)). A single Linux process must therefore own the MCU's interface and fan it out. **Neither the router nor the MCU-side `RpcCall::result()` enforces a timeout**, so an MCU `Bridge.call()` toward a dead Linux service blocks forever ([bridge.h](https://github.com/arduino-libraries/Arduino_RouterBridge/blob/main/src/bridge.h)). RPClite's sources also size the MCU-side RPC buffer at 1024/4 bytes, which caps single messages at about **256 bytes**; that figure is derived from the source and untested on hardware ([Arduino_RPClite.h](https://github.com/arduino-libraries/Arduino_RPClite/blob/main/src/Arduino_RPClite.h)).

Community measurements give the speed of the link ([arduino-router #75](https://github.com/arduino/arduino-router/issues/75)):

| UART baud | Small-call p50 / p95 | Failures |
|---|---|---|
| 115200 (stock) | 18.07 / 19.04 ms | 0 of 5,000 |
| 230400 | 11.33 / 12.96 ms | 0 of 5,000 |
| **460800** | **8.32 / 8.88 ms** | 0 of 5,000 |
| 921600 | 5.58 / 6.43 ms | 486 of 500 |
| 2,000,000 | n/a | all failed |

Without flow control, **460800 baud is the practical ceiling**. That allows roughly 100 sequential synchronous calls per second. High-rate data should be batched or streamed as notifications.

The serious defect is reliability. Open RPClite issue #43 (filed 2026-06-15) documents that the wire protocol has no length prefix or delimiter. **A single dropped or corrupted byte can leave the decoder permanently desynchronized**, and certain garbage lengths can trigger huge allocations and a hard fault. The sketch keeps running while the bridge goes silent. The maintainer acknowledged this as a footprint trade-off. Core 1.0.0 enlarged the ring buffer to reduce the odds, and a `reset()` PR and an RPClite 0.4.0 release candidate are still open ([RPClite #43](https://github.com/arduino-libraries/Arduino_RPClite/issues/43); [RPClite PRs](https://github.com/arduino-libraries/Arduino_RPClite/pulls)). UART flow control has been an open router issue since November 2025 ([issue #16](https://github.com/arduino/arduino-router/issues)).

### Four ways to harden or replace the pipeline

| Option | What changes | What you keep | What you lose |
|---|---|---|---|
| 1. Harden the stock router and Bridge | 460800 baud on both ends; a single Linux supervisor owns every method name; periodic `ping` liveness probe; MCU failsafe on heartbeat loss | Arduino libraries, sketch-only LLEXT uploads, compatibility with App Lab and the stock image | Nothing. The no-framing, no-CRC risk remains. |
| 2. Keep the Arduino core, replace the transport | Stop arduino-router. Write your own `/dev/ttyHS1` daemon with COBS or SLIP framing, CRC, sequence numbers and acks, plus a matching sketch on LPUART1. | The Arduino API and loader | Bricks and tools that expect the router |
| 3. Vanilla Zephyr (C or Rust) | Your own protocol over LPUART1 with RTS/CTS, and/or SPI3 plus the PG13 ready line. nanopb is already in Arduino's west allowlist ([Molloy](https://derekmolloy.ie/under-the-hood-of-the-arduino-uno-q-vanilla-zephyr-on-the-cortex-m33/)). | Full control of threads, IWDG, DMA and priorities | Sketch-only uploads and the Arduino libraries. Reversible with `burn-bootloader`. |
| 4. Reference only: the Rust SPI router | MessagePack-RPC over SPI with a Linux `arduino-spi-router` ([FeurJak/arduino-libraries-rust](https://github.com/FeurJak/arduino-libraries-rust)) | n/a | Dormant since March 2026 |

RPMsg/OpenAMP does not apply here, because the chips share no memory. MessagePack is a fine payload format; the weakness is the unframed stream, not the encoding.

**Recommendation:** start with option 1 so the agent pipeline can be built immediately. Hide the transport behind the supervisor's own API, then decide between staying put and moving to option 3 based on a measured soak test, not on faith.

## Arduino ships MCP for building apps, not for driving pins

### Official pieces: a development agent and a client brick

**App Lab 0.10 (August 2026) introduced Agent Mode**, built on MCP and integrated with the App CLI. It is bring-your-own-key and supported Claude first ([Arduino blog](https://blog.arduino.cc/2026/08/12/arduino-app-lab-0-10-meet-agentic-mode/)). Current docs list Claude Code and an OpenCode preview, with Codex coming. The agent runs wherever App Lab runs, and Arduino does not host the model ([Agent Mode docs](https://docs.arduino.cc/software/app-lab/integrations/agent-mode/)).

Internally, the `arduino-board` server is built on the official Go MCP SDK. It serves **stateless Streamable HTTP on a random localhost port behind a per-run 32-byte bearer token** ([server.go](https://github.com/arduino/arduino-app-lab/blob/main/standalone-apps/app-lab-desktop/internal/boardmcp/server.go)). It exposes 17 read-only tools that are auto-approved and 17 mutating tools that need approval. **None of them reads a sensor or writes a pin** ([server.go](https://github.com/arduino/arduino-app-lab/blob/main/standalone-apps/app-lab-desktop/internal/boardmcp/server.go)).

Several of its patterns are worth copying. The shell tool `board_exec` requires a stated reason and can never be granted "Always allow" ([toolpolicy.go](https://github.com/arduino/arduino-app-lab/blob/main/standalone-apps/app-lab-desktop/internal/agent/toolpolicy.go)). Wi-Fi passwords are typed into the UI and never reach the agent ([access.go](https://github.com/arduino/arduino-app-lab/blob/main/standalone-apps/app-lab-desktop/internal/boardmcp/access.go)). The authors are candid that all of this gating is best-effort rather than a sandbox ([agent README](https://github.com/arduino/arduino-app-lab/blob/main/standalone-apps/app-lab-desktop/internal/agent/README.md)).

The second official piece, the **MCP Client Brick**, works in the opposite direction. It lets App Lab apps *consume* MCP servers as LangChain tools for the cloud or local LLM bricks, and it can bundle a FastMCP server as a Docker brick ([mcp_client README](https://github.com/arduino/app-bricks-py/blob/main/src/arduino/app_bricks/mcp_client/README.md)). Arduino also documents running Claude Code, OpenCode or Codex directly on the board. That tutorial warns that the agent inherits the `arduino` user's permissions and that ADB is enabled over USB by default ([AI coding agents tutorial](https://github.com/arduino/docs-content/blob/main/content/hardware/uno/boards/uno-q/tutorials/use-cases/ai-coding-agents/ai-coding-agents.md)). `arduino-app-cli` itself contains no MCP server ([arduino-app-cli](https://github.com/arduino/arduino-app-cli)).

The community fills the runtime gap only thinly. The best UNO Q template is **Volt23's `uno-q-mcp-blink-ai`**, a one-star project: an OAuth 2.1-gated FastMCP server that reaches the STM32 over the Router Bridge, is exposed through Tailscale Funnel or Cloudflare Tunnel, and has been tested with Claude.ai, VS Code Copilot, Cursor and Zed ([Volt23](https://github.com/Volt23/uno-q-mcp-blink-ai)). **Orbit OS's MCP server** is the cautionary counterpart. It exposes 84 GPIO, I2C, SPI and power tools, and its own README warns that it has no authentication, so anyone on the LAN can reboot or factory-reset the device ([Orbit OS](https://github.com/OrbitOS-org/orbit-os-app-mcp-server)). Classic arduino-cli MCP wrappers assume a USB-attached MCU flashed from the host and transfer poorly, although the best of them, `hardware-mcp/arduino-mcp-server`, contributes a useful idea in its blocking `safety_preflight` electrical check ([hardware-mcp](https://github.com/hardware-mcp/arduino-mcp-server)). Outside Arduino, ros-mcp-server (about 1.5k stars) shows the generic pass-through style ([ros-mcp-server](https://github.com/robotmcp/ros-mcp-server)), while Home Assistant's core MCP integration shows the safer alternative: device control limited to explicitly exposed entities, plus a read-only mode ([Home Assistant](https://www.home-assistant.io/integrations/mcp_server/)).

### The 2026-07-28 spec makes the server stateless and the hardware state explicit

MCP's current revision, **2026-07-28**, is a major break ([MCP blog](https://blog.modelcontextprotocol.io/posts/2026-07-28/); [changelog](https://github.com/modelcontextprotocol/modelcontextprotocol/blob/main/docs/specification/2026-07-28/changelog.mdx)). Sessions and the initialize handshake are gone, so state that spans calls now travels as server-minted handles passed in tool arguments, and `server/discover` is mandatory. `subscriptions/listen` replaces resource subscriptions, Tasks move to a polling extension, and Multi Round-Trip Requests (MRTR) replace server-initiated elicitation. SSE resumability is removed, so **a broken stream loses the in-flight request**. Roots, Sampling and Logging are deprecated, Dynamic Client Registration gives way to Client ID Metadata Documents, and Streamable HTTP requests now carry `Mcp-Method` and `Mcp-Name` headers.

The Tools page says there should always be a human able to deny invocations. It also says clients must treat tool annotations as untrusted hints, and servers must validate inputs, enforce access control, rate-limit and sanitize outputs ([Tools spec](https://modelcontextprotocol.io/specification/2026-07-28/server/tools)). Tier 1 SDKs are TypeScript, Python, C#, Go, Rust and Ruby; there is no C or C++ SDK ([SDKs](https://modelcontextprotocol.io/docs/2026-07-28/sdk.md)). Go's support for 2026-07-28 was reportedly still in pre-release at launch, so pin and test your SDK version ([SDK betas](https://blog.modelcontextprotocol.io/posts/sdk-betas-2026-07-28/)).

These changes map well onto hardware. **Long actuator moves** become Tasks, or a "start, return job ID, poll" tool, instead of a held-open stream that a Wi-Fi blip would kill. **Exclusive control of an actuator** becomes an explicit lease handle with an expiry, since the protocol no longer has sessions to hang it on. **Server-enforced confirmation** of a dangerous call becomes an MRTR form elicitation issued by the board itself, independent of the client's permission UI; keep a `confirm` argument or a physical button as a fallback, because client support varies. Sensor streams fit best as pull-style "read since sequence N" tools or snapshot resources, which work with every client. Because Sampling is deprecated, an on-board server should never depend on borrowing the client's LLM. Finally, the `Mcp-Name` header lets a reverse proxy rate-limit or block specific tools without parsing JSON.

### Claude's cloud connectors need a public endpoint; Claude Code does not

| Topology | Where the agent runs | Working example | Fit for this project |
|---|---|---|---|
| A. MCP server on the board, agent remote | Laptop or cloud | Volt23, Orbit OS | **Primary choice** |
| B. Agent on the board | UNO Q Linux | Claude Code/OpenCode on Debian; LLM brick plus MCP Client Brick | For autonomous, unattended loops only. Credentials live on the board. |
| C. Dev-time agent through App Lab's channel | Host | App Lab Agent Mode | Building apps, not runtime control |
| D. MCU speaks MCP itself | Microcontroller | ESP32 `mcp-c-sdk` | Not applicable. The STM32 has no network. |

The deciding constraint is how Claude connects. **Custom connectors in claude.ai, Desktop, Cowork and mobile call the MCP server from Anthropic's cloud.** The server must therefore be publicly reachable, or allow Anthropic's IP ranges. Local servers configured in `claude_desktop_config.json` use the local network but are unavailable in claude.ai and Cowork ([Claude Help Center](https://support.claude.com/en/articles/11175166-getting-started-with-connectors-on-claude-ai)). Claude Code (or a Desktop local config) talking over a tailnet is therefore the simplest secure setup. A tunnel plus OAuth 2.1 is needed only if you want claude.ai or mobile access. Volt23 needed about 260 lines of Python for its OAuth layer ([Volt23](https://github.com/Volt23/uno-q-mcp-blink-ai)).

### Safety comes from layers the model cannot talk its way past

The most concrete UNO Q precedent is Mischianti's local thermostat agent, which compresses the design into one line: "The model proposes, the code limits, the STM32 has the last word" ([Mischianti](https://mischianti.org/arduino-uno-q-a-local-ai-agent-that-drives-the-hardware/)). The STM32 forces the fan on above 45 °C regardless of Linux, and **a 2-second loss of heartbeat turns the sketch into a plain 35 °C thermostat**. In between, Python rules refuse no-op switches, refuse to override an active reflex, and refuse any switch within 60 seconds of the last one, returning each refusal to the model as text so it can explain itself.

On tool design, the MCP-GRANITE study ran 8,748 trials on edge models. **A roughly four-tool interface beat fine-grained primitives by 16.4% and a single monolithic tool by 33.6%**, and a 3.2B model at the right granularity outperformed a 20.9B model at the wrong one ([arXiv:2609.24161](https://arxiv.org/abs/2609.24161)).

Threat research identifies the gap such layering closes. A STRIDE analysis of an LLM-driven robot traced its attack chains to the lack of any independent semantic check between user input and actuator dispatch ([arXiv:2604.27267](https://arxiv.org/abs/2604.27267)), and perception-based prompt injection has been shown to steer robots into adversarial actions ([arXiv:2608.00747](https://arxiv.org/abs/2608.00747)). OWASP's draft MCP Top 10 adds tool poisoning as a risk ([OWASP MCP03](https://owasp.org/www-project-mcp-top-10/2025/MCP03-2025%E2%80%93Tool-Poisoning)). The practical response is to return numeric, structured results rather than free text, to treat any sensor-derived string as hostile, and to put the last line of enforcement in MCU code that no prompt can reach.

## On-board LLMs think at five tokens per second

Arduino's own local LLM brick runs `Qwen3.5-0.8B-Q4_0` through a **CPU-only llama.cpp build** (`--device none`, 4 threads) inside a container capped at 2,500 MB ([brick_config.yaml](https://github.com/arduino/app-bricks-py/blob/main/src/arduino/app_bricks/llm/brick_config.yaml); [service_compose.unoq.yaml](https://github.com/arduino/app-bricks-py/blob/main/src/arduino/app_services/llamacpp/service_compose.unoq.yaml)). Measured on a 4 GB board, Qwen 0.8B prefills at **9.8 tokens/s and generates at 4.6 tokens/s**, and Gemma 3 1B manages 10.0 and 5.3 ([Mischianti](https://mischianti.org/arduino-uno-q-a-local-ai-agent-that-drives-the-hardware/)). On a 2 GB board, TinyLlama 1.1B averaged 5.44 tokens/s, and a 1.5B model failed to load because it needed 1.5 GiB with only 1.0 GiB free ([Geerling sbc-reviews #83](https://github.com/geerlingguy/sbc-reviews/issues/83)).

Decode speed is bounded by memory bandwidth. sysbench shows 5,041 MiB/s on the UNO Q against 11,837 on a Pi 5 ([raspberry.tips](https://raspberry.tips/en/arduino/arduino-uno-q-review-vs-raspberry-pi-5)), so tuning will not change the picture much. One author's report of about 8 tokens/s is unverified and sits 1.6× above every other measurement ([dev.to](https://dev.to/david_laurenvil_5d43bea48/i-built-the-unoqs-claw-a-tiny-agentic-ai-assistant-that-lives-inside-an-arduino-uno-q-g48)).

Agent latency is what kills the on-board brain, and slow prefill is the cause. In the only published tool-calling test, the model saw a two-tool prompt of 386 tokens. **The first decision took 49 seconds cold and 11 seconds with the KV cache warm**, and a background decision involving two tool calls took **83 seconds**. Qwen chose the right action in **14 of 16** prompts, Gemma 3 1B never saw the tools at all because its chat template drops them, and Qwen's server memory grew to the 2.5 GB container cap over many requests ([Mischianti](https://mischianti.org/arduino-uno-q-a-local-ai-agent-that-drives-the-hardware/)).

From those measurements, every 100 uncached prompt tokens cost about 10 seconds and every 100 generated tokens about 20. An ordinary MCP catalog of 1–3K schema tokens would therefore cost minutes per cold turn (my estimate). One builder reported 10–20 minutes per cold iteration for an 8-tool agent ([dev.to](https://dev.to/david_laurenvil_5d43bea48/i-built-the-unoqs-claw-a-tiny-agentic-ai-assistant-that-lives-inside-an-arduino-uno-q-g48)).

No accelerator rescues this. The QRB2210 has no dedicated NPU ([raspberry.tips](https://raspberry.tips/en/arduino/arduino-uno-q-review-vs-raspberry-pi-5)), and every one of Arduino's QNN-accelerated bricks is restricted to the VENTUNO Q ([app-bricks-py](https://github.com/arduino/app-bricks-py/tree/main/src/arduino/app_bricks)). Arduino's Hexagon llama.cpp build targets `armv8.7a+dotprod+i8mm`, which an A53 cannot execute ([build-llamacpp.yml](https://github.com/arduino/app-bricks-py/blob/main/.github/workflows/build-llamacpp.yml)). Vulkan through Mesa Turnip returned garbage on the Adreno 702, and the llama.cpp issue was closed as not planned ([llama.cpp #25906](https://github.com/ggml-org/llama.cpp/issues/25906)).

Power and heat are not a reason to move the brain either way. The board draws about 0.5 W idle and 3.5 W at most under HPL ([Geerling](https://github.com/geerlingguy/sbc-reviews/issues/83)), and it peaked at 61–69 °C with no heatsink and no reported throttling during a 300-second stress test ([element14](https://community.element14.com/products/roadtest/rv/roadtest_reviews/1920/roadtest-of-arduino-uno-q-4gb-ram-32-gb-emmc-storage-single-board-computer)).

The conclusion is unambiguous: **put the planner off-board.** A frontier model through Claude Code on your laptop, or a cloud API called by a thin on-board loop, answers in seconds and handles a full tool catalog. Arduino's own Cloud LLM brick defaults to Claude Sonnet 5.5, GPT-6 Luna and Gemini 3.5 Flash Lite ([cloud_llm/models.py](https://github.com/arduino/app-bricks-py/blob/main/src/arduino/app_bricks/cloud_llm/models.py)).

Keep the board's CPU for what it does well. Edge Impulse perception models run fast enough to serve as event sources: about 10 FPS live object detection ([raspberry.tips](https://raspberry.tips/en/arduino/arduino-uno-q-review-vs-raspberry-pi-5)) and about 6 ms per inference for a FOMO model ([Hackster](https://www.hackster.io/sologithu/running-local-vlms-on-arduino-uno-q-with-the-app-lab-70e8e3)).

A local Qwen 0.8B earns a place only on the 4 GB board, as an offline fallback or a fixed-choice classifier. In Mischianti's test, "choice mode" (the model picks from a list) was as accurate as tool calling and took 6.9 seconds per message instead of 16 ([Mischianti](https://mischianti.org/arduino-uno-q-a-local-ai-agent-that-drives-the-hardware/)). On a 2 GB board, skip local LLMs entirely. If the agent loop itself must live on the board, choose Go or Rust runtimes: PicoClaw claims under 10 MB, against more than 1 GB for OpenClaw. Both figures are self-reported ([CNX Software](https://www.cnx-software.com/2026/02/10/picoclaw-ultra-lightweight-personal-ai-assistant-run-on-just-10mb-of-ram/)).

## Recommended architecture: an off-board planner over a guarded tool server

The design puts each decision where its latency and trust requirements fit. Each layer enforces limits that the layer above cannot override.

| Layer | Runs on | Component | Non-negotiable rules |
|---|---|---|---|
| Planner | Laptop (or cloud) | Claude Code with a frontier model; later an optional thin on-board loop calling a cloud API for unattended jobs | Mutating tools are never auto-approved. The planner never holds board credentials beyond the MCP token. |
| Transport | Tailnet | MCP Streamable HTTP (2026-07-28) over Tailscale with a bearer token. A tunnel plus OAuth 2.1 only if claude.ai or mobile access is required. | No LAN-wide or public listener by default |
| MCP gateway | UNO Q, unprivileged user | Go server on the official SDK, modelled on Arduino's `arduino-board` design | 4–10 intent-level tools, typed and bounded schemas, `structuredContent` outputs, honest annotations, MRTR or `confirm` on destructive calls, Tasks for long operations, append-only audit log. **No access to the router socket or gpiochip1.** |
| MCU supervisor | UNO Q, `arduino-router` group | Go daemon that owns every Bridge method name and exposes a narrow typed API to the gateway over its own Unix socket | Range and units validation, per-tool rate limits, actuator leases, a 10–20 Hz heartbeat with sequence numbers and TTLs, a `ping` liveness probe with 100–500 ms timeouts, and a recovery ladder (router restart, then NRST pulse, then known-good reflash). Sole owner of `remoteocd` flashing. |
| Router | UNO Q | arduino-router v0.11 at 460800 baud, run by your own systemd unit | You decide explicitly whether restarting the router resets the MCU. Replaceable by a framed transport later. |
| MCU firmware | STM32U585 | Arduino Zephyr core in **Immediate** boot mode first; vanilla Zephyr if the soak test demands it | Control loop in its own high-priority thread; hard clamps and slew limits in code; stale or out-of-order commands dropped; heartbeat loss → latched safe state; IWDG fed only from the healthy control path; no `Bridge.call` on the control path; hardware E-stop |
| Perception (optional) | UNO Q | Edge Impulse models publishing events through the supervisor | Numeric outputs only; never raw strings to the model |
| Offline fallback (optional, 4 GB only) | UNO Q | llama.cpp Qwen 0.8B in choice mode | Picks only from a fixed list of supervisor intents |
| OS | UNO Q | Yocto `wrynose` + meta-qcom-arduino `uno-q`, own distro layer, systemd, Mender A/B | No Docker, no App Lab, `adbd` disabled in production ([security hardening guide](https://github.com/arduino/docs-content/blob/main/content/hardware/uno/boards/uno-q/tutorials/linux/security-hardening-guide/content.md)). Includes `rmtfs`, `tqftpserv`, `qrtr`, `qbootctl -m` and a USB gadget. Venus disabled or its firmware path fixed. |

**Split the supervisor and the gateway into separate processes.** Router-socket access is total power over the MCU, so the internet-facing MCP process should never hold it. Arduino's own agent code follows the same principle when it keeps secrets and shells away from the model.

**Write both daemons in Go.** Go has a Tier 1 MCP SDK. It is what Arduino used for `arduino-board` (stateless Streamable HTTP, which is already aligned with 2026-07-28), arduino-router is itself Go, and a static binary drops cleanly into Yocto. Python with `arduino-router-bridge` and FastMCP, following the Volt23 pattern, remains the faster way to throw together a prototype.

**Run two MCP servers rather than one.** An **"operate"** server handles runtime control with a deliberately small catalog: a read-only `get_state` returning measured and last-commanded values, `read_sensors(since_seq)`, `set_target(actuator, value, units, ttl_s, reason)`, `run_sequence(name)` returning a task, `acquire_lease` and `release_lease`, and an `estop` that is always allowed. A separate **"develop"** server wraps compile and flash, so the agent can also write MCU firmware. Every flash on that server requires server-side confirmation, is hash-checked by the supervisor, and rolls back automatically to a known-good image. Because a flash resets the MCU, actuator hardware should default safe at reset, for example with pull-downs on driver enables.

## A phased plan that proves control before building the distro

The plan front-loads the risky, novel part, the agent-to-MCU control path, on the stock image. The distro is then built to carry a stack that already works. Durations are estimates for one experienced developer.

## Risks and open questions

| Risk | Why it matters | Mitigation |
|---|---|---|
| Bridge wedge after a corrupted byte | Control silently lost while the sketch keeps running | MCU heartbeat failsafe that does not depend on the bridge; supervisor liveness probe with automatic escalation; framed transport in Phase 5 |
| Agent reaches privileged paths (router socket, gpiochip1, SWD flashing, shell) | It could hold the MCU in reset, reflash it, or bypass limits | Process and group separation; udev rules on gpiochip1; flashing only through the supervisor with confirmation; no shell tool on the operate server |
| Router restart resets the MCU (stock unit) | A "recovery" step causes actuator glitches | Write your own unit; make reset an explicit, separate escalation step |
| MCU waits for Linux at boot (default mode) | Failsafes are off for about 20–30 seconds at every boot | Immediate boot mode; start the control thread before `Bridge.begin()` |
| Prompt injection through sensors or tool poisoning | Unsafe actuation chosen by a "convinced" model | Structured numeric outputs; pinned tool descriptions; MCU limits independent of Linux |
| `qbootctl -m` missing from the image | Board drops to fastboot after a few boots | Systemd unit after `boot-complete.target`; recoverable through EDL anyway |
| Dependence on an Arduino-hosted boot blob | Builds break if the URL moves; licence terms | Fetch at build time, keep a private mirror, read `LICENSE.qcom` |
| Vendor and spec churn (App Lab pre-1.0, a major MCP revision, Go SDK pre-release at launch) | Rewrites and broken clients | Avoid App Lab internals; pin router, core and SDK versions; keep a conformance test suite |
| 2 GB RAM, if that is your SKU | Local LLM plus anything else won't fit | No local LLM and no Docker on 2 GB; Arduino itself recommends 4 GB for standalone use ([standalone setup](https://github.com/arduino/docs-content/blob/main/content/software/app-lab/1.setup/5.standalone/standalone.md)) |
| Exposing actuators through a public tunnel | Internet-reachable hardware | Tailnet-only by default; OAuth 2.1 plus `Mcp-Name` filtering if exposed |
| Platform longevity under Qualcomm | Geerling raised the Intel Edison precedent ([Jeff Geerling](https://www.jeffgeerling.com/blog/2025/arduino-uno-q-weird-hybrid-sbc)) | Mainline kernel, U-Boot and Zephyr support limit the exposure to the boot blob |

| Open question | Why it matters | How to resolve |
|---|---|---|
| Stock SWD lines and the meaning of gpiochip1 line 37 | Supervisor reset and flash logic; keeping agents off critical lines | Read `/opt/openocd/openocd_gpiod.cfg` and run `gpioinfo` on the board (Phase 0) |
| Is U-Boot in `boot_a/b` or in ABL? | Where your bootloader updates land | Dump the GPT and inspect the partition contents |
| Is the radio WCN3980 or WCN3950? | Mostly documentation; drivers are unaffected | Firmware and chip-ID lines in `dmesg` |
| Does Linux `ttyHS1` support RTS/CTS? | Whether flow control could unlock speeds above 460800 baud | Enable `crtscts` with a vanilla Zephyr peer and measure |
| Does `wrynose`'s linux-qcom 6.18 cover every Imola feature you need, or do you need linux-arduino 7.2? | Kernel choice for the LTS branch | Build both and diff probe results |
| Secure-boot fuse state on retail boards | Long-term freedom to change U-Boot | Read boot logs on the 1.8 V console |
| Has App Lab 0.12 actually shipped? | Only matters if you keep App Lab for experiments | Check the GitHub releases page again |
| Can LLEXT sketches reach Zephyr's `wdt` API? | Whether a hardware watchdog works without leaving the Arduino core | Inspect `loader/llext_exports.c`, or test static link mode |
| How well do Claude Code and other clients support MRTR elicitation and the Tasks extension? | Whether server-side confirmation and long-job polling work end to end | Test against your Phase 2 server; keep the `confirm` argument as a fallback |
| Is `arduino-unoq-radio-firmware` needed beyond linux-firmware's `qcm2290` board data? | Wi-Fi calibration on a non-Arduino image | Compare RF performance with and without it |

## Conclusion

The UNO Q's ecosystem has moved in a way that rewards a custom build. A year ago the board needed Arduino's vendor image. Now the kernel, U-Boot, Zephyr board support and a Qualcomm-maintained Yocto BSP are all upstream, and the only binary dependency is a boot bundle you never modify. The engineering risk has therefore moved from the distro to two narrow seams: an 8-millisecond serial link with no framing, and the trust boundary between a language model and a microcontroller that Linux can reset and reflash at will. Both seams are design problems, not missing drivers, and they are solved with the same tools: a single privileged supervisor, an unprivileged MCP gateway, and MCU firmware that fails safe by itself.

The deeper implication is about what the board *is* in an agentic system. Treating the UNO Q as the agent's brain throws away its strengths and exposes its weakest specification: memory bandwidth, which caps it at 5 tokens per second. Treating it as a **tool server with reflexes** plays to everything it does well: deterministic MCU control, fast local perception, low power, and full software control of its own microcontroller. MCP's 2026 turn toward statelessness reinforces this. It forces leases, sequence numbers and confirmations out of the protocol and into the supervisor, which is exactly where physical safety wants that state to live. The most valuable and most dangerous capability on offer is letting the agent write and flash MCU firmware, not merely drive actuators. A separate "develop" plane, with confirmed and reversible flashing, is what turns that capability from a liability into the project's main advantage.
